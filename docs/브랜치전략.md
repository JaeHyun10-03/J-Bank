# 브랜치 전략

## 기본 모델

트렁크 기반. `main`은 항상 배포 가능한 상태를 유지한다. 짧은 수명의 기능 브랜치에서 작업하고 Pull Request로 병합한다.

git-flow의 `develop`·`release/*` 브랜치는 두지 않는다. 혼자 하는 프로젝트에서 릴리스 브랜치 관리 비용만 늘어난다(구현계획 3.2절).

## 브랜치 네이밍

커밋 컨벤션(`CONTRIBUTING.md`)의 type을 접두어로 그대로 쓴다. 커밋과 브랜치가 같은 어휘를 쓰면 지금 뭘 하는 브랜치인지 이름만 보고 안다.

| 접두어 | 용도 | 예 |
|---|---|---|
| `feat/` | 새 기능 | `feat/api-account-open` |
| `fix/` | 버그 수정 | `fix/api-idempotency-key-race` |
| `refactor/` | 동작 변경 없는 구조 개선 | `refactor/api-transfer-service` |
| `test/` | 테스트 추가·보강 | `test/api-concurrency-scenario` |
| `docs/` | 문서 | `docs/adr-lock-order` |
| `chore/` | 빌드·설정·잡무 | `chore/infra-compose-profile` |
| `ci/` | CI 파이프라인 | `ci/backend-openapi-drift-check` |
| `perf/` | 성능 개선 | `perf/w6-index-tuning` |

가능하면 스코프(api/frontend/infra)를 브랜치명에도 넣는다.

## 브랜치 수명

며칠 안에 병합하는 걸 기준으로 잡는다. W2처럼 작업량이 큰 주도 브랜치를 통째로 오래 열어두지 않는다. 이체 API처럼 큰 작업은 "락 획득 순서" → "원장 기록" → "멱등성 처리"처럼 Atomic Commit 단위로 쪼개 한 브랜치 안에 순서대로 쌓고, 전체가 끝나는 대로 병합한다. 브랜치가 일주일 넘게 열려 있으면 스코프를 잘못 잡은 신호로 보고 쪼갠다.

## main 보호

- `main`에 직접 push하지 않는다. PR만 허용한다.
- 경로 필터에 따라 `backend-ci` 또는 `frontend-ci`가 통과해야 병합 가능하다.
- 리뷰는 혼자 하는 프로젝트라 셀프 리뷰다. PR 템플릿(`.github/pull_request_template.md`)의 체크리스트가 그 역할을 대신한다.

## 병합 방식: rebase + fast-forward

Squash merge는 쓰지 않는다. Atomic Commit 원칙과 정면으로 부딪힌다 — 브랜치 안에서 이미 "하나의 논리적 변경 = 하나의 커밋"으로 쪼개둔 걸 squash가 한 덩어리로 뭉개버리면, 나중에 특정 변경만 찾아보거나 되돌릴 때 그 구분이 사라진다.

1. PR 브랜치를 `main` 기준으로 rebase해서 최신화한다.
2. `git merge --ff-only`로 병합한다. 머지 커밋 없이 브랜치의 커밋들이 `main`에 그대로 이어붙는다.

브랜치 안에서 커밋을 잘못 쪼갰다면 rebase 시점에 `git rebase -i`로 정리하고 `git push --force-with-lease`로 갱신한다. `main`에 이미 올라간 커밋은 절대 rebase하지 않는다.

## 태그

Phase 마감 시점마다 태그를 붙인다. 구현계획 문서의 마일스톤과 그대로 맞춘다.

| 태그 | 시점 | 근거 |
|---|---|---|
| `v0.1.0` | W3, Phase 1 마감(통합 시연 가능) | 구현계획 4절 |
| `v0.2.0` | W5, Phase 2 마감 | 구현계획 5절 |
| `v1.0.0` | W7, Phase 3 마감(무중단 배포 확인) | 구현계획 6절 |

## 긴급 수정

별도 `hotfix/` 브랜치를 두지 않는다. 트렁크 기반이라 `main`이 항상 배포 가능한 상태이므로, `fix/` 브랜치로 동일하게 처리하고 우선순위만 올려 먼저 병합한다.

## 브랜치 정리

병합 후 원격·로컬 브랜치를 즉시 삭제한다. `git branch --merged main`으로 주기적으로 남은 브랜치가 없는지 확인한다.
