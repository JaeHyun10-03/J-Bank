# J-Bank 프로젝트 작업 노트

세션 연속성용 내부 노트다. 설계 문서 본문에는 포함하지 않는다.

## 배경

금융권 IT 취업을 위한 포트폴리오 프로젝트. 프론트엔드에서 백엔드·데브옵스 역량 중심으로 전환하는 것이 목적이다.

## 프로젝트명

**J-Bank**(한글 표기 제이뱅크). 이름 "임재현"의 재현에서 J를 가져왔다.

표기 규칙은 다음과 같다.

| 맥락 | 표기 |
|---|---|
| 영문 브랜드, 워드마크 | J-Bank |
| 한글 브랜드, 화면 문구 | 제이뱅크 |
| 시스템명, 문서 제목 | J-Bank 코어시스템 |
| 저장소 | j-bank |
| Java 패키지 | com.jbank |
| 백엔드 앱 디렉터리 | apps/jbank-api |
| API 도메인 | api.j-bank.internal |
| 상품 브랜드 | J 시리즈 (J키즈 적금·통장, J팜 농장, J박스) |

## 주제 결정

업권을 특정하지 않고 어디에나 통하는 "계좌 원장 + 이체 시스템"을 코어로 채택했다. 복식부기, 동시성 제어, 멱등성 처리가 핵심 어필 포인트다.

## 범위와 일정

Phase 1~3 전 범위를 7주, 주당 40~50시간으로 확정(구현계획 v2.1). 총 작업량 약 315시간.

- 처음에는 14주, 주당 20~25시간으로 산정했다가 사용자 요청으로 주당 투입을 상향해 7주로 압축했다. 주차 구성을 2대 1로 접었고 범위는 줄이지 않았다.
- Phase 1 단독 시연 시점은 W3. 뒤의 어떤 주차가 밀리더라도 이 목표는 지킨다.

## 작업 방식 결정

- 실제 금융권 서비스 수준으로 설계하고 대한민국 금융 관련 법과 규정(금융실명제, 특정금융거래정보법 등)을 준수하는 방향으로 기능을 설계한다.
- 실제 방식(A)이 개인 개발자가 접근 불가능한 외부 국가기관 전산망, 물리적 인프라 투자, 규제기관 승인 등의 이유로 어려우면, 안 되는 이유를 먼저 설명하고 대안(B)을 적용한다. 이 규칙은 요구사항·설계·인프라 전 영역에 동일하게 적용한다.
- 고객 대상은 개인 고객으로 한정하고 법인·단체 고객은 범위에서 제외한다.
- 문서는 전부 .md로만 작성한다.
- "한글단어(영문번역)" 같은 불필요한 괄호 병기를 쓰지 않는다. 영어 기술 용어는 필요하면 문장에 자연스럽게 녹여 쓴다.
- 요구사항명세서 본문에는 포트폴리오·취업 관련 언급을 넣지 않는다. 그런 맥락은 이 노트에만 기록한다.
- 개발 환경 세팅과 코드 작성은 사용자가 직접 진행하며, 이 세션은 계획·설계 문서와 디자인만 담당한다.

### 성능 전략

사용자가 "처음엔 성능 고려 없이 짜야 나중에 최적화 개선 폭이 커진다"는 아이디어를 제시했다. 방향은 수용하되 "최적화를 미루는 것"과 "일부러 비효율적으로 만드는 것"을 되돌리는 비용 기준으로 구분해 문서화했다. 판단 기준은 한 문장이다. 나중에 바꿀 때 이미 쌓인 데이터나 이미 붙은 클라이언트를 건드려야 하는가.

- 처음부터 지킬 항목: 락 획득 순서, 트랜잭션 경계, 추가 전용 원장, 멱등성 키 유니크 제약, NUMERIC 금액 타입, 발신함 구조, API 응답 계약, 요청추적 식별자, 발신함 부분 인덱스, 지급정지 컬럼, 거래 상태 기계 전체 정의
- 측정 후 손댈 항목: 복합 인덱스, 반복 쿼리 해소, 커넥션 풀, Redis 캐시, 키셋 페이지네이션, 발신함 폴링 주기, 배치 청크 크기, 파티셔닝, 가상 스레드, 로그 레벨

- k6 베이스라인을 W2로 전진 배치하고 매주 동일 조건 재측정 후 `perf/results`에 커밋. 최종 산출물은 7주치 성능 추이 그래프

## 2026-07-26 착수 전 문서 정합성 보정

폴더구조안을 설계 문서 전체와 대조 검토하면서 시작했다. 충돌 2건과 누락 4건을 발견해 폴더구조 v2.0으로 보정했고, 그 과정에서 문서 간 불일치 6건을 잡아 전부 해소했다.

### 폴더구조 보정

- **저장소 전략 충돌**: 구현계획은 2개 저장소, 폴더구조안은 모노레포. 모노레포 채택하고 구현계획 3.1절 개정
- **모듈 구조 충돌**: 구현계획은 단일 모듈 + ArchUnit, 폴더구조안은 Gradle 멀티모듈 6개. 단일 모듈 유지로 결론. 폴더구조안의 "domain-* 간 의존 최소화" 원칙이 FR-TXN-003 구현 첫 순간에 깨진다는 점(transfer가 account와 ledger를 동시에 필요로 함)이 결정적이었다
- **누락 보정**: auth·support 도메인 패키지 추가(support가 없으면 감사로그·발신함·CTR 큐·FDS가 들어갈 곳이 없었다), batch 진입점 정의, Flyway 위치 확정, `perf/` 신설
- **덜어낸 것**: `packages/api-client`, `turbo.json`, `pnpm-workspace.yaml`, 프론트엔드용 Dockerfile·Helm 차트, `frontend-cd.yml`, `docs/api`
- **방향 수정**: `openapi.yaml`을 계약 원본에서 코드 덤프 스냅샷으로 재정의. 기존 문서가 코드 우선이라 원본을 yaml로 두면 두 곳이 어긋난다
- **의존 방향 확정**: transfer → account·ledger, product → account·ledger, auth → customer, batch → 도메인, support는 common만. **account와 ledger의 상호 의존 차단**이 W7 분리의 전제

### 문서 보정 6건

| 항목 | 반영 |
|---|---|
| 토큰을 쿠키로 발급 + 위조 방지 규칙 | API설계 v1.1 |
| 지급정지 금액 + 출금 가능 금액 정의 | ERD v1.2, 요구사항명세서 v1.6 |
| 이벤트 발신함 테이블 | ERD v1.2, 요구사항명세서 v1.6 |
| 단일 저장소 전환 | 구현계획 v2.1, 폴더구조 v2.0 |
| 거래 상태 기계 | ERD v1.2, 구현계획 W2 |
| 계좌 해지 시 지급정지 조건 | 요구사항명세서 FR-ACC-004, API설계 ACC_010 |

뒤의 두 건은 지급정지 개념을 반영하는 과정에서 드러났다. API설계는 `PENDING_OTP`를 응답 계약으로 쓰는데 ERD 상태 목록에는 그 값이 없었고, 계좌 해지는 잔액 0원만 확인해서 인증 대기 중인 이체가 남은 계좌가 해지될 수 있었다. 한 개념을 넣을 때 그 개념이 닿는 모든 절을 함께 훑어야 한다.

교차 검증에서 프론트엔드기술스택도 v1.3으로 보정했다. 7절의 미해결 표기를 확정 서술로 바꾸고, 동시 401 처리 규칙을 신설했다. 여러 요청이 각자 재발급을 시도하면 갱신 토큰 로테이션 때문에 두 번째부터 이미 사용된 토큰을 제출해 서버가 탈취로 판단하고 토큰 계열 전체를 폐기한다. 정상 사용자가 강제 로그아웃되는 사고이므로 재발급을 하나로 합치고 나머지는 대기시켜야 한다.

## 2026-07-26 J-Bank 개명

프로젝트명을 J-Bank로 확정하고 문서·코드 식별자·디자인 전체에 적용했다. 이전 디자인은 외부 앱을 레퍼런스로 삼아 만든 것이었는데, 자체 제품으로 전환하면서 레퍼런스 브랜드와 상품 표기를 전부 제거했다.

### Figma 적용 결과

| 대상 | 처리 |
|---|---|
| 브랜드 문자열 | 텍스트 노드 41개(디자인 토큰 12 + 앱 화면 29), 프레임명 1개 |
| 상품명 | 텍스트 노드 31개, 프레임명 8개, 레이어명 10개 |
| 제휴·광고 표기 | 무신사 → 스타일랩, K-패스 → 그린패스 |
| 플로우 시작점 | 3개 이름 교체 |
| 좌표 정리 | 부동소수점 잔여가 있던 프레임 3개를 x=0으로 스냅 |

상품명은 J 시리즈로 통일했다. 어린이 적금과 통장은 J키즈 적금·J키즈 통장, 게이미피케이션 자유적금은 J팜 농장, 파킹통장은 J박스다. 브랜드 일관성이 부각되고 교체 범위가 최소로 유지된다는 점에서 택했다. 게이미피케이션 상품은 "농장"을 일반명사로 유지해 "농장 만들기" 같은 화면 문구가 자연스럽게 읽히도록 했다.

타행으로 등장하는 이름(토스뱅크 9건, 농협 3건)은 유지했다. 실제 은행 앱도 이체·가져오기 화면에서 타행을 그대로 표시하므로 자연스럽다.

개명 후 재스캔 결과 잔여 문자열 0건을 확인했고, 스플래시·홈·이체확인·상품상세·가입 화면을 렌더링으로 검증했다.

### 개명 중 걸린 함정

### 이전 와이어프레임 트랙에 대한 기록

이전 세션들에서 코어시스템용 반응형 와이어프레임 36종(모바일 18 + 데스크탑 18)을 `[02] - GUI`, `[03] - 컴포넌트`, `[04] - 와이어프레임 모바일`, `[05] - 와이어프레임 데스크탑` 페이지에 만들었다는 기록이 있었으나, **현재 파일에는 이 페이지들이 존재하지 않는다.** 원격 조회로 확인했다.

현재 기준 디자인은 `00. Design Tokens`와 `01. App Screens` 두 페이지이며, 앱 화면 41종이 J-Bank의 디자인이다. 와이어프레임 트랙은 이 앱 디자인으로 대체된 것으로 정리한다.

와이어프레임 트랙에서 얻은 재사용 가능한 지식은 남겨둔다.

- 컴포넌트-인스턴스 구조를 쓰면 마스터 1회 수정으로 배치된 전 화면에 즉시 반영된다. 대량 수정은 이 방식이 압도적으로 효율적이다
- 국내 은행 사이트를 조사한 결과 공통적으로 border-radius가 작고(4px 이하 다수) 그림자 의존도가 낮으며, 균일한 카드 그리드보다 비대칭 히어로 + 섹션 구분선 구조를 쓴다. 카드에 그림자와 큰 라운드를 두르는 방식은 국내 금융권 톤과 거리가 있다
- 디자인 리뷰 → Spacing → Typography → Hierarchy → Color → Interaction → Component 정리 → Auto Layout 정리 8단계 순서로 파일 전체를 훑으면 파편화된 값이 드러난다. 실제로 폰트 사이즈가 11~14종으로 파편화되어 있었고 8단계 스케일로 통합했다
- 폼 중심 금융 서비스에서 입력 필드에 에러·검증 상태가 없는 것은 치명적 공백이다. 마스터 컴포넌트에 헬퍼 텍스트를 기본 숨김으로 넣어두면 기존 인스턴스 레이아웃에 영향 없이 추가할 수 있다
- 자동 레이아웃 감사 스크립트는 부모의 `layoutMode` 방향에 따라 primary·counter axis를 구분해야 한다. 축을 잘못 잡으면 정상 노드를 버그로 잡아낸다

## 참고 배경지식

- 국내 6대 은행은 계정계 DBMS로 Oracle을 사용해온 역사가 있으며, ULA 계약 비용 부담으로 2020년 11월경 개별 라이선스로 전환했다. 이 프로젝트에서 PostgreSQL을 선택한 것은 오픈소스 전환 흐름과 맞닿아 있어 면접에서 어필할 수 있다.
- 공동인증서는 2020년 12월 전자서명법 개정으로 공인인증서 제도가 폐지되며 명칭이 바뀐 것이다. 기존 발급기관 5곳(한국정보인증·코스콤·금융결제원·한국전자인증·한국무역정보통신)이 그대로 발급한다. 금융인증서와 민간인증서도 전자서명인증사업자 인정을 받은 사업자만 제공할 수 있다.
