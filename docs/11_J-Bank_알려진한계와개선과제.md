# J-Bank 알려진 한계와 개선 과제

> 작성일: 2026-09-02
> 목적: 코드베이스·ADR·devlog·커밋 이력을 근거로 현재 구현의 한계를
> 정리하고, 면접 등에서 공격받을 만한 지점을 우선순위별로 파악한다.
> "몰라서 못 고친 것"과 "트레이드오프로 인지하고 넘어간 것"을 구분해
> 각 항목마다 근거와 예상 공격 질문을 남긴다.
>
> 갱신 2026-09-17: EKS·ArgoCD 구성을 EC2 단일 인스턴스로 낮췄다(ADR 0010).
> 6·10·11번은 다루던 구성 자체가 사라져 **해소**로 표시했고, 그 대신 생긴
> 한계는 12~14번에 추가했다. 2번은 교훈이 남아 있어 유지한다.

## 우선순위 기준

- **P0** — ADR/devlog/커밋 이력에 자기고백성 근거가 이미 남아 있어
  회피 답변이 통하지 않는 항목. 왜 그렇게 했는지 + 다음에 어떻게
  고칠지 한 문장씩 미리 준비해야 한다.
- **P1** — 트레이드오프로 설명 가능하지만, 근거를 대며 방어할 논리를
  준비해야 하는 항목.
- **P2** — 이미 스코프 아웃을 문서에 명시했거나 발생 확률이 낮아,
  인지하고 있다는 사실만 보여주면 되는 항목.

## P0 — 즉시 답변 준비 필수

### 1. 관리자 역할 모델 자체가 없음
고객 상세(API-004), 감사로그(API-020), FDS 이상거래 조회(API-022)
전부 "인증된 고객이면 누구나 호출 가능", 별도 admin role 없음.
(`todo/W4.md:11`, `docs/adr/0009:528-531`)
→ "일반 고객이 남의 감사로그·이상거래 내역을 볼 수 있는 거 아니냐"에
실제로 그렇다고 답해야 함.

### 2. IaC 정적 검증을 전부 통과했는데 실배포에서만 발견된 결함
보안그룹이 워커노드 ENI에 연결되지 않아 RDS 접속이 막혔다. 정적 검증은 통과했지만 실제 파드의 네트워크 경로에서 결함이 드러났다. (`docs/adr/0008`)
→ "왜 처음부터 실제 통합 환경에서 검증 안 했냐"가 가장 방어하기
어려운 질문. 회피 불가, 원인·재발방지책만 명확히 답해야 함.

## P1 — 트레이드오프로 설명할 항목

### 3. CDD 위험도가 사실상 항상 LOW로만 판정
직업/거래목적 분류 규칙표 없이 하드코딩.
(`CustomerService.java:57-59`, `CddGradeCalculator.java:9-10`)
→ "FDS는 만들면서 최초 KYC 리스크 분류는 왜 스킵했냐."

### 4. EDD 완료 판정이 전용 컬럼 없이 휴리스틱
"이력이 더 쌓였는가"로 판단. (`AccountService.java:64-66`) 데이터
상태가 우연히 조건을 만족하면 오탐 가능한 구조.

### 5. PII 검색용 해시가 결정론적이라 오프라인 브루트포스에 취약
주민등록번호 등은 AES-GCM으로 암호화해 저장하면서, 조회용으로는 별도
HMAC 해시(`HmacKeyHolder`)를 같이 저장. 해시가 결정론적이라 `hash-key`
유출 시 주민등록번호 형식(제한된 키스페이스)을 오프라인으로 전수
대입해 원문 복원 가능.
→ 금융 앱에서 제일 예민한 개인정보 항목이라 파고들기 좋은 지점.
암호화 자체(AES-GCM, GCMParameterSpec)는 정석대로 되어 있어 이 부분만
방어 논리 준비하면 됨.

### 6. ~~HPA가 CPU 기준만, RPS 기준 없음~~ — 해소(ADR 0010)
HPA 자체가 없어졌다. 대신 12번(수평 확장 없음)으로 질문이 바뀐다.

### 7. 배치 잡 분산 락 리스타임 30분이 실측 없이 설정됨
(`docs/adr/0005:160-162`, ponytail 주석 있음) 프로세스 비정상종료 시
최대 30분간 재실행 불가.

## P2 — 인지 정도만 하면 충분

### 8. 로그인 실패 잠금이 loginId 기준만, IP 기준 아님
`LoginAttemptService.java:9-13`(MAX_ATTEMPTS=5, 30분 잠금)는 계정당
잠금이라 여러 계정을 동시에 낮은 빈도로 시도하는 분산 브루트포스에는
무력. 다만 Redis 기반이라 인스턴스 확장 시 동작 자체는 일관됨(락
상태가 공유됨).

### 9. 추가한 복합 인덱스 효과가 실측되지 않음
계좌 3개짜리 데모 데이터라 옵티마이저가 실제로 안 씀. "나중에 계좌
수 늘면 쓰일 것"이라는 미검증 가정으로 유지.
(`docs/devlog/2026-08-21_복합인덱스반영과재측정.md`)

### 10. ~~prod가 별도 클러스터가 아니라 같은 EKS의 네임스페이스 분리~~ — 해소(ADR 0010)
클러스터가 없어졌다. 환경은 `envs/dev` 하나뿐이고 prod 분리는 스코프 밖으로
명시했다.

### 11. ~~실행된 적 없는 CD 스텝이 문서상으로만 존재하다가 방치됨~~ — 해소(ADR 0010)
해당 CD 자체를 GHCR + SSM 흐름으로 교체하고, 2026-09-17 첫 실배포에서 실패 2회
(OIDC sub 형식, SSM root 소유권)를 거쳐 성공까지 실행·기록했다
(`docs/devlog/2026-09-17_EC2첫배포검증.md`). infra-cd는 아직 게이트가 꺼져 있어
미검증 — 켤 때 같은 방식으로 기록할 것.

### 12. 단일 인스턴스 — 수평 확장·AZ 장애조치 없음
(`docs/06` 6절, ADR 0010) 인스턴스 하나, AZ 하나. 앱은 무상태라 확장 경로는
있지만 지금 구성에서 인스턴스가 죽으면 서비스가 죽는다.
→ "은행 시스템인데 SPOF를 두는 게 맞나"에 "트래픽이 없는 단계에서 이중화는
비용만 낸다. 조건이 생기면 이 경로로 올린다"를 비용 수치와 함께 답할 것.

### 13. DB 백업 없음
(`docs/06` 3.2절) postgres 데이터가 EBS 한 장에만 있다. RDS가 해주던 자동 백업·
PITR이 사라졌다.
→ 가장 먼저 채울 항목. 일 1회 `pg_dump` → S3, EBS 스냅샷 라이프사이클.

### 14. 배포 중 수 초 다운타임
(`infra/compose/deploy.sh`) api 컨테이너를 내리고 올리는 사이 caddy가 502를 낸다.
W7에 검증한 무중단 배포는 파드 2개 이상을 전제했다.
→ 1대에서도 blue/green 컨테이너 + caddy upstream 전환으로 가능. 필요해지면.
