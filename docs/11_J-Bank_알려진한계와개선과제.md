# J-Bank 알려진 한계와 개선 과제

> 작성일: 2026-09-02
> 목적: 코드베이스·ADR·devlog·커밋 이력을 근거로 현재 구현의 한계를
> 정리하고, 면접 등에서 공격받을 만한 지점을 우선순위별로 파악한다.
> "몰라서 못 고친 것"과 "트레이드오프로 인지하고 넘어간 것"을 구분해
> 각 항목마다 근거와 예상 공격 질문을 남긴다.

## 우선순위 기준

- **P0** — ADR/devlog/커밋 이력에 자기고백성 근거가 이미 남아 있어
  회피 답변이 통하지 않는 항목. 왜 그렇게 했는지 + 다음에 어떻게
  고칠지 한 문장씩 미리 준비해야 한다.
- **P1** — 트레이드오프로 설명 가능하지만, 근거를 대며 방어할 논리를
  준비해야 하는 항목.
- **P2** — 이미 스코프 아웃을 문서에 명시했거나 발생 확률이 낮아,
  인지하고 있다는 사실만 보여주면 되는 항목.

---

## P0 — 즉시 답변 준비 필수

### 1. 서비스 간 인증이 정적 공유 비밀키 하나
`X-Internal-Api-Key` 헤더 + `constantTimeEquals` 비교뿐, mTLS·키
로테이션 없음. `/internal/**`는 SecurityConfig에서 `permitAll`.
(`InternalApiKeyFilter.java:104-145`, `docs/adr/0007:324-329`)
→ 키 하나 유출 시 고객 인증 우회하고 `withdraw-by-number`, `deposit`
등 임의 계좌 출금/입금 API를 직접 호출 가능. "blast radius 얼마나
되냐"에 답이 궁색해짐.

### 2. 관리자 역할 모델 자체가 없음
고객 상세(API-004), 감사로그(API-020), FDS 이상거래 조회(API-022)
전부 "인증된 고객이면 누구나 호출 가능", 별도 admin role 없음.
(`todo/W4.md:11`, `docs/adr/0009:528-531`)
→ "일반 고객이 남의 감사로그·이상거래 내역을 볼 수 있는 거 아니냐"에
실제로 그렇다고 답해야 함.

### 3. DB는 공유, 서비스만 분리
jbank-product/jbank-api가 `products`/`product_contracts` 테이블을
공유(jbank-api가 Flyway 소유, product는 `ddl-auto: validate`로 읽기만
가능). (`docs/adr/0007:286-292`)
→ "이거 MSA 아니라 프로세스만 나눈 모놀리스 아니냐"는 정면 공격에
데이터 결합이 그대로 남아 있다는 사실 자체는 부정할 수 없음.

### 4. IaC 정적 검증을 전부 통과했는데 실배포에서만 발견된 결함
보안그룹이 워커노드 ENI에 안 붙어 RDS 접속 자체가 막힘, Kafka
호스트명 하드코딩(`kafka-not-provisioned:9092`)으로 앱 컨텍스트 기동
자체가 실패. `terraform plan`/`validate`, `helm template` 전부
무력했다고 ADR에 직접 적어둠. (`docs/adr/0008` 전체)
→ "왜 처음부터 실제 통합 환경에서 검증 안 했냐"가 가장 방어하기
어려운 질문. 회피 불가, 원인·재발방지책만 명확히 답해야 함.

### 5. 사가 로직을 새로 만든 모듈인데 테스트 밀도가 가장 낮음
jbank-product main 38파일 : test 5파일(≈13%) vs jbank-api
143파일 : 61파일(≈43%). 돈이 실제로 움직이는 신규 모듈의 테스트
비율이 오히려 제일 낮음.
→ "왜 돈 옮기는 새 모듈 테스트가 더 적냐"에 준비된 답 필요.

## P1 — 트레이드오프로 방어 가능, 논리 준비 필요

### 6. CSRF 필터가 서비스 간 내부 API를 막던 회귀
로컬/통합테스트로는 안 잡히고 실 클러스터 배포에서만 발견(커밋
`0e552ca`, 08-31 당일 수정).
→ 테스트 환경과 실제 배포 환경 간극을 보여주는 사례. "설계 단계에서
못 잡은 이유"를 설명해야 함.

### 7. CDD 위험도가 사실상 항상 LOW로만 판정
직업/거래목적 분류 규칙표 없이 하드코딩.
(`CustomerService.java:57-59`, `CddGradeCalculator.java:9-10`)
→ "FDS는 만들면서 최초 KYC 리스크 분류는 왜 스킵했냐."

### 8. EDD 완료 판정이 전용 컬럼 없이 휴리스틱
"이력이 더 쌓였는가"로 판단. (`AccountService.java:64-66`) 데이터
상태가 우연히 조건을 만족하면 오탐 가능한 구조.

### 9. 인증·CSRF·공통 응답 포맷 코드를 두 서비스에 그대로 복제
공유 라이브러리로 안 뽑음. (`docs/adr/0007:331-338`) 6번(CSRF 버그)이
이 복제 코드 동기화 실패의 실제 증거.

### 10. 이자 지급 배치의 트랜잭션 원자성 소실
이자 입금(jbank-api)과 만기 확정(jbank-product) 호출이 분리되며
트랜잭션 경계가 사라짐. `idempotencyKey`를 계약당 1개로 두고 재시도로
땜질. (`docs/adr/0007:361-368`)
→ "확정 호출이 계속 실패하면? 무한 재시도인가, 알림은 누가 받나"는
미검증 영역.

### 11. 사가 검증이 WireMock 대역 기반 3경로뿐
정상/출금실패/확정실패만 검증(`ProductSubscriptionSagaIntegrationTest`,
`docs/adr/0007:314-318`). 네트워크 타임아웃·부분응답 같은 실제
분산시스템 실패모드는 미검증.

### 12. PII 검색용 해시가 결정론적이라 오프라인 브루트포스에 취약
주민등록번호 등은 AES-GCM으로 암호화해 저장하면서, 조회용으로는 별도
HMAC 해시(`HmacKeyHolder`)를 같이 저장. 해시가 결정론적이라 `hash-key`
유출 시 주민등록번호 형식(제한된 키스페이스)을 오프라인으로 전수
대입해 원문 복원 가능.
→ 금융 앱에서 제일 예민한 개인정보 항목이라 파고들기 좋은 지점.
암호화 자체(AES-GCM, GCMParameterSpec)는 정석대로 되어 있어 이 부분만
방어 논리 준비하면 됨.

### 13. HPA가 CPU 기준만, RPS 기준 없음
Prometheus Adapter 미배포로 스코프 아웃. (`todo/W7.md:26-28`)
→ "CPU는 안 뛰는데 큐만 쌓이는 I/O bound 트래픽 폭주는 못 잡는다."

### 14. 배치 잡 분산 락 리스타임 30분이 실측 없이 설정됨
(`docs/adr/0005:160-162`, ponytail 주석 있음) 프로세스 비정상종료 시
최대 30분간 재실행 불가.

## P2 — 인지 정도만 하면 충분

### 15. 로그인 실패 잠금이 loginId 기준만, IP 기준 아님
`LoginAttemptService.java:9-13`(MAX_ATTEMPTS=5, 30분 잠금)는 계정당
잠금이라 여러 계정을 동시에 낮은 빈도로 시도하는 분산 브루트포스에는
무력. 다만 Redis 기반이라 인스턴스 확장 시 동작 자체는 일관됨(락
상태가 공유됨).

### 16. 프론트/게이트웨이 라우팅 미완성
프론트가 두 백엔드(jbank-api/jbank-product)를 구분 라우팅하지 않음,
ALB/Ingress도 자리표시자 단계. (`docs/adr/0007:397-399`)

### 17. 추가한 복합 인덱스 효과가 실측되지 않음
계좌 3개짜리 데모 데이터라 옵티마이저가 실제로 안 씀. "나중에 계좌
수 늘면 쓰일 것"이라는 미검증 가정으로 유지.
(`docs/devlog/2026-08-21_복합인덱스반영과재측정.md`)

### 18. prod가 별도 클러스터가 아니라 같은 EKS의 네임스페이스 분리
(`todo/W7.md:29-31`) 노이지 네이버·블라스트 레디어스 관점에서
지적받을 수 있음.

### 19. 실행된 적 없는 CD 스텝이 문서상으로만 존재하다가 방치됨
`backend-cd.yml`에 `helm upgrade` 스텝 자체가 없었는데 문서에는 있는
것처럼 기록돼 있었음. (`docs/adr/0006:196-203`) "검증 안 된 설계를
그대로 두고 다음 단계로 넘어간 전례가 있다"는 패턴 증거로 쓰일 수
있음.

## 요약

가장 날카로운 질문이 나올 지점은 **P0의 5개** — 내부 API 정적 키
인증, admin role 부재, DB 공유형 "MSA", IaC-실배포 검증 간극, 사가
모듈 테스트 부실. 전부 ADR/devlog/커밋 이력에 자기고백성 근거가 이미
남아 있어서 "몰랐다"는 답이 통하지 않는다. 각 항목은 "왜 그때 그렇게
결정했는지"와 "다음엔 뭘 어떻게 바꿀지" 한 문장씩 준비해두는 것을
권장한다. P1·P2는 트레이드오프로 방어 가능한 영역이므로, 근거만
정확히 대면 충분하다.
