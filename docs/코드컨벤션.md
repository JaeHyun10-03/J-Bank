# 코드 컨벤션

이 문서는 스타일 취향이 아니라 리뷰에서 반복 지적되지 않도록 미리 합의해두는 규칙이다. 자동 검사로 강제 가능한 것은 강제하고, 강제 불가능한 것만 이 문서에 남긴다.

## 백엔드 (`apps/jbank-api`)

### 포맷

`google-java-format`을 Spotless로 강제한다. `./gradlew spotlessApply`로 맞추고, CI의 `spotlessCheck`가 병합을 막는다. 수동으로 들여쓰기·줄바꿈을 고민하지 않는다.

### 패키지 계층

도메인 패키지(`customer`, `account`, `ledger`, `transfer`, `product`, `auth`, `support`, `batch`)는 각각 `controller`, `service`, `domain`, `repository`, `dto`를 가진다.

- `controller`는 자기 도메인의 `service`만 호출한다. `repository`를 직접 호출하지 않는다.
- `domain`은 `service`와 `controller`를 모른다.
- `global`은 도메인 패키지를 모른다. `common`만 의존한다.

도메인 간 허용 의존 방향은 `docs/10_J-Bank_폴더구조.md` 4절의 표가 원본이다. `apps/jbank-api/src/test/java/com/jbank/architecture/DependencyDirectionTest.java`가 ArchUnit으로 강제하므로, 이 문서에 규칙을 다시 나열하지 않는다. 새 도메인 간 의존이 필요하면 폴더구조 문서 4.2절 표를 먼저 고치고 ArchUnit 테스트를 갱신한 뒤 코드를 짠다.

### 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| 엔티티 | 단수 명사 | `Account`, `LedgerEntry` |
| 리포지토리 | `{Entity}Repository` | `AccountRepository` |
| 서비스 | `{Domain}Service`, 구현이 하나뿐이면 인터페이스 분리하지 않는다 | `TransferService` |
| 컨트롤러 | `{Domain}Controller` | `AccountController` |
| 요청 DTO | `{Action}Request` | `AccountOpenRequest` |
| 응답 DTO | `{Action}Response` | `AccountOpenResponse` |
| 도메인 예외 | `{Domain}Exception`, `ErrorCode`를 생성자로 받는다 | `InsufficientBalanceException` |

DTO는 record로 작성한다. 불변이어야 하고 getter 보일러플레이트가 필요 없다.

### 계층별 규칙

- 컨트롤러는 검증(`@Valid`)과 서비스 호출, 응답 변환만 한다. 비즈니스 로직을 넣지 않는다.
- 트랜잭션 경계는 서비스 계층에 둔다. `@Transactional`을 리포지토리나 컨트롤러에 걸지 않는다.
- 예외는 도메인별 예외를 던지고 `global.exception`의 `@RestControllerAdvice`가 `ApiResponse` 포맷으로 변환한다. 컨트롤러에서 try-catch로 직접 처리하지 않는다.
- 금액은 어디서도 `double`/`float`을 쓰지 않는다. `BigDecimal` 고정이고 컬럼은 `NUMERIC`이다(구현계획 7.2절, 되돌릴 수 없는 항목).
- 원장(`LedgerEntry`)에는 수정·삭제 메서드를 리포지토리에 노출하지 않는다. 추가만 가능하다.

### 테스트

- 단위 테스트: 대상 클래스와 같은 패키지, `{ClassName}Test`
- 통합 테스트: `test/java/com/jbank/integration`, Testcontainers로 실제 PostgreSQL·Redis를 띄운다. H2로 대체하지 않는다(비관적 락 동작이 실제와 다르다).
- 동시성 테스트: `test/java/com/jbank/concurrency`
- given-when-then 3단 주석으로 테스트 본문을 나눈다. 각 단이 한 줄을 넘어가면 테스트가 너무 많은 것을 검증하고 있다는 신호다.

## 프론트엔드 (`apps/frontend`)

### 린트

`next/core-web-vitals` 기반 ESLint를 그대로 쓴다. `npm run lint`가 CI를 막는다. 별도 Prettier는 추가하지 않는다. ESLint의 포맷 규칙으로 충분한 범위이며, 필요성이 확인되면 그때 추가한다.

### 파일·컴포넌트 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| 라우트 디렉터리 | kebab-case, 동적 세그먼트는 대괄호 | `accounts/[accountId]/transfer` |
| 컴포넌트 파일·함수 | PascalCase | `TransferConfirmDialog.tsx` |
| 훅 | camelCase, `use` 접두 | `useAccountBalance.ts` |
| 유틸리티 함수 | camelCase, 순수 함수 | `formatAmount()` |
| Zod 스키마 | `{Action}Schema` | `transferRequestSchema` |

라우트 구조는 `docs/05_J-Bank_프론트엔드기술스택.md` 8절의 표가 원본이다.

### 컴포넌트 규칙

- 서버 데이터는 TanStack Query, 클라이언트 전용 상태는 Zustand. 이 둘을 섞어 같은 값을 두 곳에서 관리하지 않는다.
- 폼은 React Hook Form + Zod. 서버 도메인 에러코드는 `lib/error-map.ts`의 매핑 테이블을 거쳐 폼 필드 에러로 변환한다. 컴포넌트 안에서 에러코드를 직접 분기하지 않는다.
- 금액·계좌번호·날짜 표시는 `lib/format.ts`의 공통 함수를 쓴다. 컴포넌트에서 직접 포맷하지 않는다.
- API 호출은 `lib/axios.ts` 인스턴스 하나만 쓴다. 컴포넌트에서 `fetch`를 직접 호출하지 않는다.
- API 타입은 `types/api.ts`(생성물)에서 가져온다. 요청·응답 타입을 손으로 다시 정의하지 않는다.

### 테스트

- 컴포넌트·유틸: Jest + React Testing Library, `{name}.test.tsx`를 대상 파일 옆에 둔다.
- E2E: Playwright, `e2e/` 아래. 화면플로우차트 문서의 흐름 이름을 시나리오 파일명으로 쓴다.
