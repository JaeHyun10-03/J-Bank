# 2026-09-16 Archify로 서비스 아키텍처 다이어그램 생성

`tt-a1i/archify` 스킬(`npx skills add tt-a1i/archify -g`)을 설치해서 j-bank
서비스 레벨 아키텍처를 다이어그램으로 정리했다. `docs/infra_arichtecture.jpeg`가
이미 AWS 인프라(EKS·ALB·RDS·MSK 등) 레벨을 다루고 있어서, 이번 건 겹치지
않게 frontend/jbank-api/jbank-product 모듈 간 실제 통신 경로에 집중했다.

## 코드 근거 조사

추측 없이 실제 코드를 grep해서 관계를 확인했다.

- `apps/frontend/app/api/proxy/[...path]/route.ts` — 브라우저는 항상
  same-site `/api/proxy`만 호출하고, 여기서 서버 대 서버로 백엔드(jbank-api,
  기본 `:8080`)를 호출한다. Vercel/AWS 오리진이 달라 쿠키 기반 인증이
  그대로 안 먹히는 문제를 이 프록시로 우회한다.
- `MaturedContractApiClient`(jbank-api) → `InternalContractController`
  (jbank-product) — 이자 만기 배치가 `X-Internal-Api-Key`로 인증된 내부
  API(`/internal/v1/contracts/matured`)를 호출한다.
- `InternalAccountController`(jbank-api) ← jbank-product 상품가입 사가 —
  계약 생성 후 출금/보상 출금(입금)을 같은 내부 API-key로 jbank-api에
  요청한다(`ProductSubscriptionSagaIntegrationTest` 참고).
- `apps/jbank-product/src/main/resources/application.yml` 주석 — products/
  product_contracts 테이블은 jbank-api의 Flyway 마이그레이션이 만들었고,
  jbank-product는 그 이력을 모른 채 `ddl-auto: validate`로만 스키마를
  확인한다(W7에서 분리된 이후에도 DB는 계속 공유).
- `jbank-api` `build.gradle.kts`/`application.yml` — Redis(Redisson, 분산락·
  OTP), Kafka(`jbank.events` 아웃박스 발행/구독)는 jbank-api만 쓴다.

## Archify 사용기

`architecture` 스키마로 컴포넌트 9개, 관계 8개를 작성. `validate` →
`deliver` → `visual-check` 3단계 파이프라인을 돌리면서 겪은 문제:

- 같은 노드의 같은 변(side)에서 나가는 edge가 2개 이상이면 자동 포트
  분산이 안 먹혀서 라벨이 겹쳤다(`fromSide`/`toSide`를 명시하면 특히
  더 심함). Redis·Kafka를 "Redis + Kafka" 한 노드로 합쳐서 해결 —
  둘 다 jbank-api 전용 인프라라 의미 손실이 크지 않았다.
- jbank-api ↔ jbank-product 양방향 호출도 라벨 2개짜리 화살표 2개로
  그리면 겹쳐서, "internal API (API-key)" 단일 관계로 합치고 방향별
  detail은 카드 텍스트로 옮겼다.
- `meta.repository`(정확한 40자리 revision)를 지정해야 컴포넌트
  `sources` 필드(코드 근거 링크)가 통과한다.
- showcase 프로파일 데스크톱 가독성 체크가 뷰박스 폭 대비 서브라벨
  글자 크기를 실측 계산해서 막았다 — sublabel을 줄이고 컬럼 간격을
  좁혀서 통과시켰다.

최종 산출물은 `docs/architecture/jbank-service-architecture.html`
(단일 파일, pan/zoom·테마전환·검색 내장)과 재편집용
`jbank-service-architecture.spec.json`. `visual-check`가 만든 스크린샷/
디버그 파일은 검증 후 삭제하고 커밋에서 제외했다.
