# 2026-09-17 EKS를 EC2 단일 인스턴스로 다운사이징

## 배경

"걷어낼 것 3개" 중 마지막. 1번(상품 서비스 통합)·2번(Kafka 제거)은 PR #2에서 끝냈고,
남은 것이 EKS·ArgoCD·HPA 중심의 배포 구조였다. 처음 제안은 "Compose를 기본으로 낮추고
k8s는 실험 트랙으로 보존"이었는데, 논의하면서 목표가 선명해졌다.

- "Terraform도 k8s 안 쓰면 필요 없나?" — 아니다. Terraform은 AWS 리소스, k8s는 그 위의
  컨테이너 실행. 질문의 핵심은 **AWS에 올릴 것인가**였다.
- 올린다. 다만 EKS 과금이 심해서 EC2로 낮추는 것. 즉 "인프라 제거"가 아니라
  **"EKS → EC2 1대 다운사이징"**.
- Grafana·Prometheus도 AWS에 올린다. Loki는 "Prometheus만 있어도 Grafana 대시보드는 다
  돈다"를 확인한 뒤 제거로 결정.

결정 근거는 ADR 0010, 현재 구성은 인프라아키텍처 v2.0.

## 사전 확인 — AWS에 뭐가 살아 있나

코드를 먼저 지우면 리소스가 고아가 되어 과금만 남는다. 읽기 전용으로 확인했다.

```bash
terraform workspace list          # default, * demo
terraform state list | wc -l      # 0
aws eks list-clusters / rds describe-db-instances / elasticache describe-cache-clusters
aws ec2 describe-nat-gateways / elbv2 describe-load-balancers / ecr describe-repositories
aws secretsmanager list-secrets / kms list-aliases / wafv2 list-web-acls
```

전부 비어 있었다. 남은 것은 기본 VPC와 `jbank-terraform-state-*` 버킷(유지). W7 검증 후
destroy한 상태여서 바로 진행할 수 있었다.

## 진행 순서와 발견한 것

### 1. Dockerfile이 이미 깨져 있었다

아침에 CI 수정으로 `gradle.properties`를 지웠는데(2026-09-17 devlog 앞 건) Dockerfile의
`COPY build.gradle.kts settings.gradle.kts gradle.properties ./`가 그 파일을 참조하고
있었다. 그 커밋 시점에 `docker build`를 안 돌려봐서 놓쳤다. Compose `api` 서비스를
만들기 전에 먼저 고쳤다. 교훈: 파일을 지울 땐 `git grep`으로 참조부터 본다 — CI에는
Docker 빌드 단계가 없어서 이 회귀를 아무도 잡지 못했다.

### 2. Compose에 `api` 서비스가 없었다

로컬 Compose는 postgres·redis·관측 스택만 있고 앱은 항상 `gradle bootRun`이었다.
컨테이너로 앱을 띄우는 경로가 Helm 차트 하나뿐이었다는 뜻이다. `api` 프로파일을 추가해
`scripts/dev.sh core api`로 빌드된 이미지가 뜨는지 확인할 수 있게 했다.
`dev` 프로파일(env 기반)에 서비스명(`postgres`, `redis`)을 넘기면 그대로 붙는다.

### 3. 배포용 Compose는 오버라이드가 아니라 별도 파일

처음엔 `docker-compose.yml` + `docker-compose.prod.yml` 오버라이드를 생각했다. 안 된다 —
Compose 병합은 리스트를 이어붙이기만 해서 `profiles`를 "빼거나" 호스트 포트를 "없애는"
게 불가능하다. 로컬과 배포는 프로파일·포트·빌드 컨텍스트·비밀값 주입이 전부 다르므로
독립 파일이 맞다. 폴더구조 문서의 "compose는 단일 파일" 원칙에 예외를 명시했다.

검증은 `.env.example`을 임시로 `.env`로 복사해 `docker compose config --quiet`,
Caddyfile은 `docker run caddy:2 caddy validate`.

`.gitignore`의 `.env*` 패턴이 `.env.example`까지 무시하고 있었다. `!.env.example` 추가.

### 4. Terraform: 추가 → 교체 → 삭제 순서

"각 커밋은 빌드 가능" 원칙 때문에 삭제를 먼저 하면 `envs/dev`가 존재하지 않는 모듈을
참조하게 된다. 그래서 `ec2` 모듈을 먼저 추가(validate 통과), 다음 커밋에서 `envs/dev`를
그 모듈로 바꾸면서 여섯 모듈과 Helm을 지웠다. 43파일 1,964줄 삭제.

`ec2` 모듈에서 걸린 것 하나: 보안그룹 `description`에 `Let's Encrypt`의 아포스트로피가
AWS 허용 문자 정규식에 걸려 validate가 실패했다. `ACME challenge`로 바꿨다.

설계 선택:
- **SSH 포트 없음.** 운영 접근은 SSM Session Manager, 배포는 SSM Run Command. 인스턴스
  역할은 `AmazonSSMManagedInstanceCore`만.
- **`ignore_changes = [ami, user_data]`.** 데이터가 루트 볼륨에 있으므로 AMI가 새로
  나왔다고 인스턴스를 갈아엎으면 안 된다.
- **GHCR.** 저장소가 public이라 무료·인증 불필요. ECR과 그 푸시 역할이 통째로 사라진다.
  AWS 쪽 배포 역할에 남는 권한은 "이 인스턴스에 `AWS-RunShellScript` 보내기 + 결과
  조회"뿐이다.
- **x86(t3.small).** t4g가 $3 싸지만 Dockerfile이 이미지 안에서 gradle 빌드를 하므로
  CI에서 QEMU 크로스 빌드가 필요해진다. 그 시간이 $3보다 비싸다.

### 5. 배치 잡을 잊고 있었다

인프라 문서를 쓰다가 "배치 잡은 API 프로세스 안의 스케줄러가 돈다"고 적었는데, 확인해
보니 틀렸다. 네 배치 잡(interestMaturity·ctrDetection·ledgerReconciliation·fdsDetection)은
k8s CronJob이 같은 이미지를 `--spring.profiles.active=prod,batch
--spring.batch.job.name=<job> runDate=<오늘>`로 띄우던 것이었고, Helm을 지우면서
스케줄러가 통째로 사라진 상태였다.

호스트 crontab(`/etc/cron.d/jbank`, `CRON_TZ=Asia/Seoul`)이 `infra/compose/run-batch.sh`를
부르게 했다. 스크립트는 `docker compose run --rm --no-deps api java -jar /app/app.jar
<인자>`로 api 서비스의 이미지·env_file·네트워크를 그대로 쓰는 일회성 컨테이너를 띄운다.
명령행 인자가 환경변수 `SPRING_PROFILES_ACTIVE=prod`보다 우선하므로 `prod,batch`로
덮인다. 문서 쓰다 잡은 누락이라, 문서를 "구현 검증" 단계로 쓰는 게 실제로 효과가 있었다.

### 6. Loki 제거

`loki4j` 의존성, logback `LOKI` appender, Compose `loki` 서비스·config, Grafana datasource.
대시보드 JSON에 Loki 참조가 0건이라 영향 없음을 미리 확인했다. 컴파일·Spotless·
`compose config` 통과.

### 7. 문서

인프라아키텍처는 243줄 → 157줄로 전면 재작성. v1.x의 "실제 금융권 방식(A) vs 대안(B)"
표는 취지를 살려 "A / v1.x / 현재 / 낮춘 이유" 네 열로 갱신했다. 구현계획(W6·W7 서술)은
실행된 역사라 본문을 고치지 않고 버전 이력에만 주석. ADR 0006·0008은 폐기 상태로
표시하되 교훈은 남겼다. 알려진한계 문서는 EKS 항목 3개를 해소 처리하고 새 한계
3개(SPOF, 백업 없음, 배포 중 다운타임)를 추가했다.

| 월 고정비(시연 구성) | ~$200 | ~$20 |

## 남은 것 (직접 해야 하는 작업)

1. `infra/terraform/envs/dev`: 로컬 `terraform.tfvars`에서 `db_master_password` 줄 삭제
   (validate 경고). `.terraform/`을 지웠으므로 `terraform init -backend-config=...` 재실행.
2. `terraform apply` → `terraform output`으로 `public_ip`, `instance_id`, `deploy_role_arn`.
3. DNS: `api.j-bank.site`, `grafana.j-bank.site` A 레코드 → `public_ip`.
4. SSM 세션으로 접속해 `infra/compose/.env` 작성 후 `docker compose -f docker-compose.prod.yml up -d`.
5. GitHub Secrets `AWS_DEPLOY_ROLE_ARN`, `EC2_INSTANCE_ID`, Variables `EC2_DEPLOY_READY=true`.
   기존 `AWS_ECR_PUSH_ROLE_ARN`, `TF_VAR_DB_MASTER_PASSWORD`, `ECR_DEPLOY_READY` 삭제.
6. Vercel env `BACKEND_API_URL=https://api.j-bank.site`.
7. 첫 배포 후 실제로 돌았는지 devlog로 남길 것 — 알려진한계 11번의 "검증 안 된 CD"
   패턴이 반복되지 않았다는 증거가 필요하다.
8. 다음 우선 과제: DB 백업(`pg_dump` → S3).
