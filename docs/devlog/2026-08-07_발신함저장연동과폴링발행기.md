# 2026-08-07 이체 트랜잭션 내 발신함 저장 연동 + 폴링 발행기 + Kafka 프로파일 (W4 금)

목표: `todo/W4.md` 요일별 계획의 금요일분. 이체 트랜잭션 안에서 이벤트를
발신함 테이블에 함께 저장, 폴링 발행기로 미발행 레코드를 Kafka에 발행,
로컬 Compose 메시징 프로파일 활성화.

## `OutboxEvent` 상태 전이 메서드 + 조회 쿼리

목요일에 상태 전이 메서드 없이 만들어 둔 `OutboxEvent`에 `markPublished`
(status=PUBLISHED, publishedAt 기록)와 `markFailed`(재시도 횟수 증가,
오류 메시지 500자 절단 저장)를 추가했다. `markFailed`는 상태를 FAILED로
바꾸지 않고 PENDING을 유지한다 — 폴링 발행기가 다음 주기에 자동으로
재시도해서 최소 한 번 전달을 보장하기 위함이고, 이 덕분에 `idx_outbox_pending`
부분 인덱스도 실패한 레코드를 계속 담아 재시도 대상으로 유지한다. 재시도
상한을 넘겨 FAILED로 terminate하는 로직은 아직 없음(ponytail 주석으로
남겨둠) — 필요해지면 그때 추가한다.

`OutboxEventRepository`에는 `findByStatusOrderByOccurredAtAsc(status, Pageable)`를
추가해 폴링 발행기가 오래된 순서로 배치 조회할 수 있게 했다.

## 이체 트랜잭션 내 발신함 저장 연동

`TransferService.transfer()`에 직접 `OutboxEventRepository`를 주입하는
대신, `AuditLogListener`와 같은 패턴으로 `OutboxEventListener`를 만들어
`TransferCompletedEvent`를 구독하게 했다. `@Transactional` 없이 순수
`@EventListener`만 붙이면 `eventPublisher.publishEvent(...)`를 호출한
스레드의 진행 중인 트랜잭션에 그대로 참여한다(REQUIRED와 동등) — 감사
로그 리스너가 이체 완료 이벤트에 쓰는 것과 정확히 같은 방식이다. 이렇게
하면 발신함 저장이 원장 반영·거래 완료 처리와 한 트랜잭션으로 묶여서,
저장이 실패하면 이체 자체도 롤백된다(발신함 패턴이 요구하는 커밋-발행
원자성).

`TransferService`가 `support.outbox` 패키지를 몰라도 되게 유지했다는
점이 감사 로그 때와 같은 이유로 중요하다 — 폴더구조 4.2절의 의존 방향
규칙(`support`만 도메인 이벤트를 구독하고, 도메인은 `support`를 모른다)을
그대로 지킨다.

## 폴링 발행기(OutboxPublisher)

`support.outbox.service.OutboxPublisher`를 `@Scheduled(fixedDelayString)`로
`jbank.outbox.poll-interval-ms`(기본 1000ms)마다 돌게 했다. 한 번에
`jbank.outbox.batch-size`(기본 100)건까지 PENDING을 오래된 순으로 읽어,
건별로 `@Transactional` 메서드(`publishOne`) 안에서 Kafka에 동기 발행
(`kafkaTemplate.send(...).get(5, TimeUnit.SECONDS)`)하고 성공하면
`markPublished`, 실패하면 `markFailed` 후 저장한다. 페이로드는 이미
`Map<String,Object>`로 들어있어 `ObjectMapper`로 JSON 문자열 직렬화만
하면 됐다.

`spring-kafka`는 이미 의존성에 있었지만 producer key/value serializer가
설정돼 있지 않아 `KafkaTemplate` 빈 생성 시 필요해서 `application.yml`
공통 설정에 `StringSerializer`로 추가했다. `@Scheduled`를 쓰려면
`@EnableScheduling`이 필요한데 프로젝트 어디에도 없어서
`JbankApiApplication`에 붙였다.

컨슈머는 이번 범위 밖이다(todo상 토요일분) — 토픽 이름(`jbank.events`)만
정하고 소비자 구현은 손대지 않았다.

## 검증

이 세션은 Docker Desktop이 꺼져 있어서 시작할 때는 testcontainers 기반
통합 테스트(19개)가 전부 "Could not find a valid Docker environment"로
실패했다 — 사용자에게 확인 후 Docker Desktop을 띄워서 이어갔다. Docker가
뜬 다음 `scripts/dev.sh core messaging`으로 Kafka/Postgres/Redis를 실제
기동하고, `./gradlew bootRun --args='--spring.profiles.active=local'`로
앱을 올려 `Started JbankApiApplication`까지 확인했다. 이어서
`outbox_event`에 PENDING 레코드를 직접 넣고 `kafka-console-consumer`로
`jbank.events` 토픽을 구독해서, 1초 폴링 주기 안에 실제로 페이로드가
발행되고 DB 레코드가 PUBLISHED로 바뀌는 것까지 눈으로 확인했다. 검증
후 컨테이너와 앱 프로세스는 정리했다.

`OutboxEventTest`, `OutboxPublisherTest`(Mockito 기반, Kafka 브로커
없이 `KafkaTemplate.send` 성공/실패 두 경로만 검증)는 통과. Docker
필요한 통합 테스트(`TransferServiceIntegrationTest` 포함)는 위 수동
검증으로 대신 확인했고, 별도로 `./gradlew test` 전체 회귀까지는
이번 세션에서 돌리지 않았다.
