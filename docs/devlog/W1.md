# W1 개발일지

## 2026-07-28 개발환경 세팅

목표: 설계 문서 11종을 기준으로 백엔드(Spring Boot)·프론트엔드(Next.js)·로컬 인프라(Docker Compose) 개발환경을 실제로 기동 가능한 상태까지 세팅.

### 1. Java 버전 불일치

**상황.** 로컬에 Java 17(Zulu)만 설치되어 있었는데, 구현계획 문서는 Java 21을 확정 버전으로 명시(가상 스레드를 W6 성능 최적화 지렛대로 쓸 계획이라서).

**해결.** `brew install openjdk@21`로 별도 설치. 문제는 그다음이었다 — `openjdk@21`은 keg-only라 시스템 PATH에 자동으로 안 잡힌다. brew가 제안하는 대로 `.zshrc`에 PATH를 추가하는 방법도 있었지만, 그러면 셸을 열 때마다 전역 Java 버전이 바뀌어 다른 프로젝트에 영향을 줄 수 있다. 대신 `apps/jbank-api/gradle.properties`에 `org.gradle.java.home=/opt/homebrew/opt/openjdk@21`을 넣어 이 프로젝트의 Gradle 빌드만 21을 쓰게 했다. 전역 셸 설정은 건드리지 않았다.

**배운 점.** 프로젝트 로컬 도구 버전 고정은 셸 프로필보다 빌드 도구 설정 파일 쪽이 안전하다. sdkman의 `.sdkmanrc`나 Gradle의 `org.gradle.java.home`처럼 저장소에 커밋 가능한 방식을 우선 고려한다.

### 2. Spring Boot 3.3이 Initializr에서 단종됨

**상황.** `start.spring.io`(Spring Initializr)로 프로젝트를 생성하려 하자 다음 에러가 났다.

```
{"timestamp":"2026-07-28T10:46:53.257Z","status":400,"error":"Bad Request","message":"Invalid Spring Boot version '3.5.16', Spring Boot compatibility range is >=4.0.0","path":"/starter.zip"}
```

Initializr 메타데이터(`/metadata/client`)를 확인하니 `bootVersion` 후보에 3.x가 전혀 없었다. 문서가 작성된 시점(2026-07-25) 이후 Spring Boot 3.3이 OSS 지원 종료로 Initializr 목록에서 빠진 것으로 보인다.

**시도한 것과 버린 것.** Initializr가 기본으로 주는 4.1.0을 그냥 쓸까 고민했지만, API설계·프론트엔드기술스택 문서가 Spring Security 6 필터체인 API를 전제로 서술되어 있다. Spring Boot 4.x는 Spring Framework 7 / Spring Security 7로 메이저가 올라가 인증 설정 API가 달라진다. 아직 인증 코드 한 줄도 안 쓴 시점에 이걸 올리면, W3(인증 구현)에서 설계 문서 서술과 실제 API가 어긋나는 위험을 떠안는다.

**해결.** Maven Central을 직접 조회(`maven-metadata.xml`)해서 3.x 라인의 최신 패치인 3.5.16을 확인했다. Initializr 대신 `build.gradle.kts`, `settings.gradle.kts`를 손으로 작성하고, `gradle wrapper --gradle-version 8.11`로 wrapper만 따로 생성했다(로컬에 Gradle 자체가 없어서 `brew install gradle`로 부트스트랩용 Gradle을 먼저 설치). 근거는 `docs/adr/0001-spring-boot-version.md`에 남겼다.

**배운 점.** 스캐폴딩 도구(Initializr, create-next-app 등)가 항상 "그 시점의 최신"을 기준으로 움직인다는 걸 잊기 쉽다. 문서에 버전을 못박아뒀어도, 실제 세팅 시점에 그 버전이 여전히 받을 수 있는 버전인지는 별도로 확인해야 한다. 패치 버전 차이는 그냥 따라가고, 메이저 버전 차이는 그 위에 쌓인 다른 설계 문서의 전제를 다시 검토해야 한다.

### 3. ArchUnit이 빈 패키지에서 실패

**상황.** 폴더구조 문서 4절의 의존 방향 규칙(`account`와 `ledger`는 서로 의존 금지, `support`는 `common`만 의존 등)을 ArchUnit 테스트로 작성했다. 아직 도메인 코드가 하나도 없는 상태(패키지는 있지만 클래스는 없음)에서 테스트를 돌리니 전부 실패했다.

```
DependencyDirectionTest > globalDoesNotDependOnDomainPackages() FAILED
    java.lang.AssertionError at DependencyDirectionTest.java:38
```

**원인.** ArchUnit은 기본적으로 규칙을 검증할 대상 클래스가 0개면 "규칙을 검증한 게 아니라 스코프가 잘못됐다"고 보고 실패시킨다(`archRule.failOnEmptyShould` 기본값 `true`). 오타로 패키지명을 잘못 적어 대상이 0개가 되는 실수를 잡기 위한 안전장치인데, 지금은 정말로 대상이 0개인 상황이라 이 안전장치에 걸렸다.

**해결.** `src/test/resources/archunit.properties`에 `archRule.failOnEmptyShould=false`를 넣었다. 지금은 그냥 통과하고, 도메인 코드가 실제로 쌓이기 시작하면 그때부터 이 테스트가 진짜 역할을 한다.

**배운 점.** 구조 테스트를 코드보다 먼저 세워두는 건 맞는 순서지만, "아직 아무것도 없다"는 상태 자체를 도구가 어떻게 취급하는지 확인해야 한다. 그냥 실패를 무시하고 넘어갔으면 나중에 이 설정을 까먹고 왜 테스트가 항상 초록불이었는지 헷갈렸을 것이다.

### 4. Tailwind v3 → v4 전환 중 shadcn/ui, 폰트가 연쇄로 깨짐

**상황.** `create-next-app@14`가 기본으로 Tailwind v3.4.1을 깔았다. v4가 최신이라 교체를 요청받았다.

**해결 순서.**
1. `tailwindcss` v3 제거, `tailwindcss`·`@tailwindcss/postcss` v4 설치, `tailwind.config.ts` 삭제
2. `shadcn@latest init`을 v4가 이미 설치된 상태에서 재실행 — CLI가 "Found v4"로 인식하고 `tailwind.config.ts` 없이 `app/globals.css`의 `@theme`/CSS 변수 기반으로 다시 세팅해줬다
3. `postcss.config.mjs`의 플러그인 키가 `tailwindcss: {}`로 남아있어서(shadcn이 자동으로 안 고쳐줌) `@tailwindcss/postcss: {}`로 직접 수정
4. 빌드하니 다른 에러: `next/font/google`의 `Geist` 폰트를 못 찾음(`Unknown font 'Geist'`). shadcn이 기본으로 넣은 폰트인데 이 프로젝트의 Next.js 14.2.35 번들에는 없는 폰트였다
5. 작업노트에 브랜드 폰트가 Gothic A1로 이미 정해져 있었다. 임시로 Geist를 고치는 대신 애초에 맞는 폰트로 교체 — `next/font/google`의 폰트 목록(`font-data.json`)에서 `Gothic A1` 지원 확인 후 적용

**배운 점.** 스캐폴딩 CLI를 여러 개 연쇄로 돌리면(create-next-app → tailwind 업그레이드 → shadcn init) 각 도구가 이전 도구의 산출물을 완전히 인식하지 못하는 지점이 생긴다. 매 단계 후 빌드를 돌려서 그 지점을 바로 잡아야지, 안 그러면 에러 3개가 한 번에 뒤섞여 나온다. 그리고 "일단 되게 만들기"용 임시값(Geist)을 프로젝트 고유값(Gothic A1)으로 바로 교체하는 게, 나중에 다시 손대는 것보다 지금 하는 게 싸다.

### 5. Docker 데몬 미기동

**상황.** `docker compose --profile core up -d`가 `Cannot connect to the Docker daemon`로 실패.

**해결.** `open -a Docker`로 Docker Desktop 실행 후, `docker info` 성공할 때까지 폴링(최대 90초). 이후 정상 기동, `pg_isready`·`redis-cli ping`으로 헬스체크 확인.

### 6. 프론트엔드 스캐폴딩이 중첩 git 저장소를 만듦

**상황.** `create-next-app`이 `apps/frontend` 안에 자체적으로 `git init`을 실행해서, 모노레포 안에 저장소가 두 개 생겼다.

**해결.** `apps/frontend/.git`을 삭제. 이 저장소는 단일 저장소 전략(구현계획 3.1절)을 쓰기로 확정했으므로 중첩 저장소가 있으면 상위 저장소가 이 디렉터리를 서브모듈처럼 취급해 파일이 하나도 안 잡히는 문제가 생긴다.

**배운 점.** 스캐폴딩 CLI가 기본으로 `git init`을 하는 경우가 많다. 모노레포에 하위 프로젝트를 추가할 때는 생성 직후 `.git` 존재 여부를 항상 확인하는 습관이 필요하다.

### 7. macOS 기본 셸에 `timeout` 명령이 없음

**상황.** 백엔드를 시간제한 두고 부팅 검증하려고 `timeout 90 ./gradlew bootRun ...`을 썼는데 `command not found: timeout`. GNU coreutils의 `timeout`은 macOS 기본 셸에 없다(brew의 `coreutils`를 깔면 `gtimeout`으로 들어간다).

**해결.** `nohup ... & echo $! > pid파일`로 백그라운드 실행 후 `sleep`으로 대기, PID로 직접 `kill`. 별도 패키지 설치 없이 셸 내장 기능만으로 해결.

### 요약: 이번 세팅에서 반복된 패턴

문제 7개 중 3개(Spring Boot 단종, Tailwind 자동 설정 잔재, macOS `timeout` 부재)가 "문서·가이드가 가정한 환경과 지금 이 순간의 실제 생태계가 다르다"는 같은 뿌리에서 나왔다. 스캐폴딩을 자동화 도구에 맡기더라도, 결과물이 실제로 빌드되고 뜨는지 매 단계 검증하지 않으면 이런 차이를 놓친다. 그래서 이번 세팅은 각 구성요소(백엔드 컴파일, 테스트, 프론트 빌드, 인프라 헬스체크, 백엔드 실제 부팅+DB 연결)를 전부 실행해서 확인한 뒤에 다음 단계로 넘어갔다.

## 2026-07-28 공통 응답 포맷 · 에러코드 · 전역 예외 처리기

목표: API설계 2.4/2.7절 기준으로 `global` 패키지의 공통 응답 봉투와 예외 처리 기반을 구현.

### 도메인 코드가 하나도 없는 시점에 예외 처리기를 어디까지 만들 것인가

**상황.** 코드컨벤션 문서는 도메인 예외를 `{Domain}Exception`, `ErrorCode`를 생성자로 받는 형태로 정의하라고 규정한다. 이 규칙을 그대로 따르면 모든 도메인 예외가 상속할 공통 베이스 클래스(예: `BusinessException`)가 자연스럽게 필요해 보였다.

**결정.** 지금은 만들지 않았다. `customer`, `account` 등 도메인 패키지에 예외가 하나도 없는 시점이라, 베이스 클래스를 먼저 만들면 실제 사용처 없이 형태부터 정하는 셈이 된다. 대신 `GlobalExceptionHandler`는 지금 존재하는 예외만 처리하게 좁혔다 — `MethodArgumentNotValidException` → `COMMON_001`(400), 그 외 `Exception` → `COMMON_006`(500). 첫 도메인 예외(W1 남은 작업인 고객 실명번호 중복등록 409 거부)가 생기는 커밋에서 베이스 클래스와 그 커밋 대상 예외 핸들러를 같이 추가하기로 미뤘다.

**배운 점.** 컨벤션 문서에 "이런 형태여야 한다"고 적혀 있어도, 그 형태를 요구하는 첫 번째 실사용 코드가 나오기 전에 미리 만들면 인터페이스가 추측성으로 굳는다. 공통 부모 클래스는 두 번째 구현체가 나오는 시점에 추출하는 편이 안전하다.

### 커밋 순서: ApiResponse를 ErrorCode보다 먼저

**상황.** `ApiResponse.error(code, message)`가 `ErrorCode` enum을 직접 받게 하면 더 타입 안전하지만, 그러면 `ApiResponse` 커밋이 아직 존재하지 않는 `ErrorCode`에 의존해 그 자체로는 컴파일이 안 된다.

**해결.** `ApiResponse.error`는 `String code, String message`만 받게 하고, 호출부(`GlobalExceptionHandler`)에서 `errorCode.name()`, `errorCode.getMessage()`를 풀어서 넘기게 했다. 커밋 3개(`ApiResponse` → `ErrorCode` → `GlobalExceptionHandler`)가 각각 단독으로 빌드되는 걸 유지하기 위한 선택.

**배운 점.** Atomic Commit을 지키려면 타입을 살짝 덜 엄격하게(enum 대신 String) 만드는 대가를 받아들여야 할 때가 있다. 지금은 그 대가가 작고(handler 쪽에서 `.name()` 한 번 더 부르는 정도), 이후 도메인 예외 처리가 늘어나면 그때 `ApiResponse.error(ErrorCode)` 오버로드를 추가해도 기존 호출부를 깨지 않는다.
