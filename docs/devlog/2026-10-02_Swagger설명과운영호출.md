# 2026-10-02 Swagger 설명 정비와 운영 Swagger 호출 복구

Swagger 첫 화면의 설명이 1주차 그대로("인증은 아직 없습니다", `customerId` 쿼리 파라미터, 버전 `v0 (W1)`)였다. 고치다 보니 운영 Swagger는
처음부터 아무 요청도 보낼 수 없는 상태였다는 것까지 드러났다. 명세: `.claude/tasks/openapi-description/task.md`.

## 한 일

- **설명·버전**: 쿠키 인증(`access_token`·`refresh_token`·`XSRF-TOKEN`), 상태 변경 요청의 `X-CSRF-TOKEN` 규칙과 예외, 401·403 코드,
  `Idempotency-Key`, 오프셋이 붙는 날짜를 실제 코드와 대조해 다시 썼다. 버전은 경로 접두사와 같은 `v1`.
- **요청 주소**: springdoc이 만든 `servers`가 운영에서 `http://api.j-bank.site`라 https 화면의 Try it out이 mixed content로 막혔다. 상대 경로 `/`로 고정.
- **CORS**: 그래도 운영 POST는 403 `Invalid CORS request`였다. 허용 출처에 `https://api.j-bank.site` 추가.
- **Authorize**: `X-CSRF-TOKEN` 헤더를 apiKey 보안 스킴으로 선언해 Swagger에서 로그인 뒤 `csrfToken`을 넣으면 모든 요청에 붙게 했다.
- 커밋마다 계약 스냅샷(`contracts/openapi/openapi.yaml`)을 다시 덤프해 같이 넣었다. CI의 `openapi-drift`가 이 파일과 기동한 API를 비교한다.

## 겪은 문제

- **스냅샷을 빼먹을 뻔함**: 처음 계획에 계약 스냅샷 갱신이 없었다. 하네스 verify에는 드리프트 검사가 없어 로컬 검사는 통과하고 PR CI에서야 실패했을
  것이다. 계획 리뷰에서 잡혔다.
- **같은 출처인데 CORS 403**: Caddy가 TLS를 끝내 앱은 요청을 http로 본다. 브라우저는 같은 출처 POST에도 `Origin: https://api.j-bank.site`를
  붙이는데, Spring은 Origin과 요청의 스킴·호스트·포트를 비교하므로 교차 출처로 판정하고 허용 목록(`http://localhost:3000`)에 없어 거절한다.
  빈 본문 로그인으로 확인했다: Origin이 있으면 403 `Invalid CORS request`, 없으면 400. 근본 원인은 프록시 헤더를 믿지 않는 것이지만,
  사용자 결정으로 영향 범위가 작은 허용 출처 추가를 택했다(도메인이 바뀌면 같이 바꿔야 한다는 주석을 남김).
- **8080이 이미 사용 중**: 로컬 8080을 다른 개인 프로젝트가 쓰고 있었다. 18080으로 띄우고, 스냅샷 덤프 때는 `Host: localhost:8080` 헤더를 줘서
  CI와 같은 자동 생성 서버 주소가 나오게 했다(커밋 2 이후는 `/` 고정이라 상관없음).
- **Swagger 입력이 안 지워짐**: 내장 브라우저에서 텍스트 영역 전체 선택이 먹지 않아 예시 JSON 뒤에 본문이 붙었고, 서버가 500을 냈다. 입력 이벤트로
  값을 넣어 해결했다. 이때 잘못된 JSON 본문이 400이 아니라 500 `COMMON_006`으로 떨어지고 로그도 안 남는다는 기존 결함을 찾았다(후속 작업).
- 로컬 확인 결과: Authorize 없이 계좌 개설 403 `COMMON_007` → `csrfToken`을 Authorize에 넣은 뒤 같은 요청 201, curl에 헤더가 자동으로 붙음.

## 다음에 볼 것

- 운영 반영 뒤 Swagger에서 실제 로그인·상태 변경 요청은 사용자가 본인 계정으로 확인한다.
- 쿠키가 하나도 없는 상태 변경 요청은 401이 아니라 CSRF 403이 먼저 난다. 설명의 401 문구는 GET 기준이다.
- 프록시 헤더 신뢰(`server.forward-headers-strategy`)는 스킴 오인 자체를 고치는 방법으로 남아 있다.
