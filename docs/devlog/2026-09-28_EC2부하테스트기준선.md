# 2026-09-27~28 EC2 부하 테스트로 운영 사양의 한계와 병목 찾기 (개선 전 기준선)

## 배경

로컬 k6 측정은 NFR-PERF-001(이체 p95 200ms, 초당 100건) 대비 16~20배 여유로 통과만 해 왔다. 한계에 닿은 적이 없으니
병목도, 개선 전후를 비교할 기준도 없었다. 운영과 같은 t3.small 한 대를 따로 띄우고, 같은 AZ의 별도 EC2에서 부하를 올려
실제로 무너지는 지점과 원인을 지표로 남겼다. 후속 작업(핫 계좌 입금 비동기 반영)의 변경 전 기준선이다.
명세·결정: `.claude/tasks/ec2-load-test/task.md`, 결과: `perf/results/ec2-baseline/`, 절차: `perf/README.md` "EC2 부하 테스트".

## 만든 것

- `infra/terraform/modules/perf`·`envs/perf`: 대상(t3.small·크레딧 unlimited)과 부하 발생기(c7i.large). 공개 인바운드 없음, SSM만. 측정 때만 apply, 끝나면 destroy.
- `infra/compose/perf/`: 대상 스택(운영 이미지·JVM 그대로 + exporter 3종, 내부 TLS, PG 느린 쿼리·락 대기 로그, 관리 포트 분리, 지표 프록시)과 부하 발생기의 Prometheus·Grafana·대시보드.
- `perf/k6/s1-mixed.js`·`s2-hot-account.js`·`s3-spike.js`, 고객 준비 `perf/prepare-accounts.py`.
- `perf/run-ec2.sh`(→ `run-ec2.py`)와 `perf/ec2/`: 회차마다 PG 복사본 복원 → 예열 → 측정 경계 → 단계별 무너짐 판정(무너진 뒤 한 단계 더 가고 중단) → 지표 원자료·결측 검사 → 실패 이체 멱등키 DB 대조 → 대사·정합성 → 로그 발췌를 SSM으로 조율하고 결과를 SSM 출력으로 나눠 받는다.

| S1 혼합(조회 70·이체 20·로그인 10) | 초당 100건에서 무너짐(3/3), 최대 지속 50 | CPU 포화. 로그인 서버 p95 315ms로 이체·잔액의 8~26배 |

원장·잔액 정합성은 모든 회차에서 유지됐다. 하지만 **클라이언트가 타임아웃(실패)을 받은 이체는 멱등키 대조 결과 사실상 전부 실제로
완료**됐다(S3는 완료 이체의 약 89%가 고객에게 실패로 보임). 반대로 caddy 502는 한 건도 반영되지 않았다. 고객이 재시도 대신 새로
이체하면 중복 송금이 되는 금융 위험이다.

## 과정에서 부딪힌 것

- **인증이 걸린 `/actuator/prometheus`**: 인증 없이 긁으면 401. 앱 코드를 바꾸지 않으려고 perf 전용 계정으로 로그인하는 지표 프록시를 두었다. 운영 Prometheus도 같은 이유로 api 지표를 못 받고 있을 가능성이 있어 별도 작업으로 넘겼다.
- **IP 접속 TLS 실패**: 사설 IP로 접속하면 SNI가 없어 caddy가 인증서를 못 골랐다. `default_sni`로 해결. 로컬 스모크는 `localhost` 이름이라 드러나지 않았다.
- **메모리 스래싱 사고**: 첫 S1 시도에서 무너진 뒤 정합성 확인용 대사 잡 JVM이 더 뜨자, 약 1GB로 불어난 api와 겹쳐 2GB 대상이 스래싱(가용 807→127MB, 메이저 폴트 초당 169건)으로 약 50분 멈췄다. OOM 킬 없이 멈춰 자동 복구도 안 됐다. 운영 cron 배치도 같은 위험을 안고 있다. 이후 대사 전에 api를 멈추고 배치에 시간 제한을 두었다. 사고 자료는 `first-pass/s1/incident-r1-memory/`.
- **로그 경쟁 조건**: 백그라운드로 띄운 k6가 로그를 비우기 전에 옛 `SCENARIO_START`를 읽어 단계 시각이 틀렸다. 회차 디렉터리를 먼저 비워 해결.
- **k6 결과에 로그인 토큰**: `--summary-export`에 setup 반환값(토큰)이 직렬화됐다. 결과에서 지우고 자동 제거를 넣었다. `.gitignore`의 `*.log` 때문에 로그 발췌가 커밋에서 빠진 것도 뒤늦게 잡아 강제 추가했다.

## 1차 측정을 버리고 재측정한 이유

1차 측정 결과 리뷰(verifier)에서 네 가지 결함이 나왔다.
1. 지표 프록시가 포화된 본 포트 Tomcat을 거쳐 S1 후반·S3 스파이크 구간 api 지표가 비었다.
2. setup 토큰이 같은 기준 시각이라 S5 12분 시점에 약 200 VU가 동시에 BCrypt 재로그인해 포화가 생겼다.
3. "실패 응답인데 반영" 수치에 k6를 멈춘 순간 처리 중이던 요청이 섞였다(1차 S2 723건은 대부분 이것).
4. 배치 처리 건수를 적지 않았다.

관리 포트(9095) 분리와 프록시 백그라운드 재로그인, 재로그인 9~12분 분산, 실패 멱등키 기록·DB 대조, 수집 대상별 결측 검사(gaps.txt)를
넣고 S1·S2·S3·S5를 다시 쟀다. 재측정은 모든 회차 결측 0, 무효 회차 없음. 1차 결과는 `perf/results/ec2-baseline/first-pass/`에 보존했다.
계획 리뷰는 한도 3회를 넘겨 사용자 허락으로 3회 더(총 6회), 결과 리뷰는 3/3에서 통과했다.

## 후속

1. 입금(수신 측) 비동기 반영 — S2 기준(무너짐 80, 최대 지속 60, 이체 p95 1,561ms, 조회 전파)과 같은 절차로 비교.
2. CTR 배치 인덱스 — CTR 쿼리 9,105ms 기준.
3. 과부하 시 빠른 거절·처리 시간 상한 — S3 회복 100초, 실패 응답 반영 2,672건 기준.
4. 운영 cron 배치의 2GB 메모리 위험, 로그인 CPU 분리 측정(S4).
5. 문서 정리: 요약에 드롭 수 열, S5 메모리 열 이름, first-pass 머리말 결함 표시. 후속 측정 전 정합성 스냅샷을 api 정지 뒤로.
