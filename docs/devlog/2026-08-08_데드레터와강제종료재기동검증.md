## 재시도 + 데드레터(`KafkaConsumerConfig`)

리스너가 예외를 던지면 컨테이너가 무한정 재시도하거나 메시지를 그냥
커밋해버리는 게 기존 기본 동작이었다. `global.config`에
`DefaultErrorHandler` 빈 하나를 추가했다 — Spring Boot의
`KafkaAnnotationDrivenConfiguration`이 `ObjectProvider<CommonErrorHandler>`로
단일 빈을 자동으로 찾아 `ConcurrentKafkaListenerContainerFactory`에
연결해주기 때문에, 리스너 컨테이너 팩토리를 직접 정의할 필요는 없었다.

`DeadLetterPublishingRecoverer(kafkaTemplate)` + `FixedBackOff(backoffMs,
maxAttempts - 1)`로 고정 간격 재시도 후 원본 토픽명에 `-dlt`가 붙은
토픽(예: `jbank.events-dlt`)으로 원본 레코드를 전송하게 했다. 재시도
횟수·간격은 `jbank.kafka.consumer.retry.max-attempts`(기본 3),
`jbank.kafka.consumer.retry.backoff-ms`(기본 1000)로 뺐다 — 발신함
설정들과 같은 패턴.

한 가지 정정: 처음엔 데드레터 접미사가 `.DLT`인 줄 알고 주석·테스트에
그렇게 적었는데, `DeadLetterPublishingRecoverer`의 실제 기본 접미사는
`-dlt`(소문자, 하이픈)였다. 테스트가 바로 이 착오를 잡아줬다.

테스트(`KafkaConsumerConfigTest`)는 브로커 없이 Mockito로 `KafkaTemplate`을
목킹하고, `DefaultErrorHandler.handleRemaining(...)`을 직접 호출해
데드레터 토픽으로 전송되는지만 확인한다. 재시도 횟수를 1로 줘서 즉시
소진시켰다 — 백오프 타이밍 계산 자체는 스프링이 이미 검증한 영역이라
우리 책임 범위(레코버러 배선)만 좁게 확인했다.

## 강제 종료 → 재기동 검증

`scripts/dev.sh core messaging`로 Kafka/Postgres를 띄우고
`./gradlew bootRun --args='--spring.profiles.active=local'`로 앱을
기동한 뒤, `kill -9`로 강제 종료했다. **앱이 죽어 있는 상태에서** psql로
`outbox_event`에 PENDING 레코드를 직접 삽입해 "커밋은 됐지만 발행 전에
프로세스가 죽은" 상황을 재현했다. 앱을 다시 기동하자 폴링 발행기가
기존 PENDING 레코드를 찾아 1초 주기 안에 `jbank.events` 토픽으로
발행했고, DB 상태가 PUBLISHED로 바뀌었다. `kafka-console-consumer`로
직접 구독한 로그와 `NotificationEventConsumer`가 남긴 알림 로그
양쪽에서 메시지 도달을 확인했다.

이걸로 발신함 패턴의 핵심 전제 — 이벤트가 비즈니스 트랜잭션과 같은
커밋에 저장되기만 하면, 발행 시점에 프로세스가 어떻게 되든 재기동 후
반드시 발행된다 — 가 실제로 성립함을 확인했다. 검증 후 앱 프로세스와
컨테이너는 모두 정리했다.
