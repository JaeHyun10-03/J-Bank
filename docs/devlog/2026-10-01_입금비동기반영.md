# 2026-09-30 ~ 10-01 핫 계좌 입금 비동기 반영

한 계좌로 이체가 몰리면 받는 계좌 행 락에서 줄을 서다 커넥션 풀이 고갈돼 초당 80~100건에서 무너지던 문제를, 받는 쪽 반영을 입금 대기 +
계좌별 묶음 반영으로 바꿔 풀었다. 명세: `.claude/tasks/async-credit/task.md`, 결정: [ADR 0012](../adr/0012-async-credit.md),
결과: `perf/results/ec2-async-credit/summary.md`.

## 한 일

- **구조**: 이체는 보내는 계좌만 `FOR NO KEY UPDATE`로 잠그고 받는 계좌는 `FOR KEY SHARE`로 존재·상태만 본다. 차변 원장·입금 대기
  (`pending_credits`, V18)·`COMPLETED`를 한 트랜잭션에 쓰고, 워커가 200ms마다 계좌별로 최대 500건을 모아 잔액과 대변 원장을 쓴다.
- **해지 경합**: 해지·상태 변경이 락 없이 읽은 옛 잔액으로 전체 컬럼을 덮어써 동시 입금을 없앨 수 있던 기존 문제를 찾았다. 첫 로드를
  `FOR UPDATE`로 바꾸고, 처리 중인 입금(미반영·OTP 대기)이 있으면 `ACC_012`로 거절한다. 수정 전 코드로 되돌리면 실패하는 테스트로 재현했다.
- **조회·대사**: 반영 전 입금은 받는 사람의 거래내역에서 뺐다. 대사는 차변 = 대변 + 미반영으로 바꾸고 REPEATABLE READ 한 트랜잭션에서 돈다.
- **측정 도구**: 측정 경계 전에 미반영 0을 기다리고, 정합성 식에 api 정지 시점의 미반영을 넣고, DB 시각으로 단계별 반영 지연을 낸다.

## 겪은 문제

- **락 모드 확인**: JPA `PESSIMISTIC_WRITE`가 PostgreSQL에서 `FOR UPDATE`면 입금·출금 경로가 이체의 `KEY SHARE`와 충돌한다. 프로브로
  `KEY SHARE`를 쥔 행에 잠금을 걸어 보니 32ms 만에 통과해 Hibernate가 `FOR NO KEY UPDATE`를 만든다는 것을 확인했다. 이체 경로는 SQL에
  기대지 않으려고 네이티브 쿼리로 락 모드를 고정했다.
- **테스트 트랜잭션**: 반영 서비스를 `REQUIRES_NEW`로 두니 테스트 트랜잭션 안에서 만든 대기가 안 보였다. 워커는 트랜잭션 밖에서
  부르므로 `REQUIRED`로도 계좌마다 새 트랜잭션이 된다. 같은 트랜잭션에서 만든 대기는 DB 기본값인 생성 시각이 엔티티에 없어 null을 막았다.
- **정합성 SQL 24분 멈춤**: r5 후처리에서 이체마다 `ledger_entries`(transaction_id 인덱스 없음, 1천만 건)를 훑는 상관 서브쿼리가 끝나지
  않았다. 경계 이후 원장만 한 번 모아 조인하도록 고치고, 실행 중 쿼리를 취소한 뒤 후처리만 다시 돌렸다(api는 이미 멈춰 DB 상태 고정).
  검사 스크립트에 경계 이전 원장 행을 넣어, 필터를 `>=`로 바꾸면 실패하는지도 확인했다.
- **반영 지연 목표 초과**: r5의 160 단계에서 p95 2,046ms로 1초 목표를 넘었다(CPU 평균 74%, 커넥션 대기 148). 결과 리뷰에서 지적받고,
  재측정 대신 판정 범위를 기준선이 무너진 최대 요청률 바로 위인 초당 150건 이하로 좁혔다. 측정 뒤 기준을 바꾼 것이라 원래 기준과
  초과값을 요약·ADR에 그대로 남겼다.
- **요약 계산 실수**: 같은 부하 단계 비교표를 r6 추가 전 5회로 계산해 둔 채 "6회"라고 적었다(100 단계 28ms → 실제 33ms). 전파 6/6이
  그대로라는 불리한 항목도 빠져 있었다. 양쪽을 같은 규칙으로 다시 계산해 고쳤다.
- **지표 증거 공백**: 반영 지표 3종을 만들어 놓고 측정 대시보드에 패널을 안 넣어 EC2 원자료에 시계열이 없었다. 패널을 넣고, 로컬에서
  받는 계좌 UPDATE를 막는 임시 트리거로 적체를 만들어 미반영 10건·나이 증가·해제 후 0·지연 max 60.6초가 수집되는 것을 확인했다.
  워커가 락에서 멈추면 게이지도 굳고, 지연 히스토그램은 30초가 상한이라는 한계도 이때 드러났다.
- **대사 오탐 테스트**: "REPEATABLE READ라 괜찮다"를 테스트로 보이려고, 원장 합을 읽은 직후 다른 스레드에서 반영을 커밋하게 리포지터리
  스파이에 끼워 넣었다. 스파이가 인터페이스 프록시라 `callRealMethod()`가 안 돼 기본 응답(실제 빈 위임)을 호출했다. 격리를
  READ COMMITTED로 바꾸면 "캐시잔액=100.00, 원장합산=0"으로 실패하는 것도 확인했다.

## 결과

- 같은 부하에서 이체 p95가 초당 90건 238 → 35ms, 100건 395 → 33ms, 무관한 잔액 조회 p95가 100건 307 → 15ms. 110 단계 전까지 커넥션
  대기 중앙값 0.
- 무너짐 판정 중앙값 95 → 115, 최대 처리 TPS 103.8 → 115.1. 판정값은 t3 CPU steal과 겹친 일시 정지로 흔들려 단계 비교를 우선 근거로 쓴다.
- 무너질 때 무관한 조회로 번지는 것은 6/6으로 그대로다. 병목이 행 락에서 CPU로 옮겨 갔다.
- 6회 모두 중복·유실 0.

## 다음에 먼저 볼 것

- 지표를 추가하면 대시보드 패널도 같은 커밋에 넣는다. 측정 원자료는 패널 식만 저장한다.
- 측정 전에 판정 기준을 정할 때 "어느 부하 범위에서"까지 정한다. 측정 뒤에 좁히면 투명성 비용이 크다.
- 1천만 건 테이블에 대한 검사 SQL은 실행 계획부터 본다.
