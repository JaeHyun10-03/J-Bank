# 2026-09-10 대규모(계좌 10만·거래 1천만) 성능 측정

`perf/README.md` W6 화요일분에서 "로컬 계좌 3개로는 재현 불가"라며 보류했던
질문 — 계좌당 매칭률이 실제로 낮아지면 거래내역 조회(API-010)의 실행 계획이
바뀌는가, V13 복합 인덱스가 그때 값을 하는가, `Page` 총건수 `count(*)`가
병목이 되는가 — 을 실제 데이터 규모에서 확인했다.

시드·측정 하네스를 새로 만들었다: `perf/sql/seed-10m.sql`,
`perf/k6/read-endpoints.js`, `perf/run-10m.sh`. 실행 절차와 재실행 전 정리
방법은 `perf/README.md`의 "대규모 시드" 절에 있다.

## 거래내역 조회 EXPLAIN — 계좌당 131건 / 1천만

W6에서는 계좌 3개·매칭률 42%라 옵티마이저가 `transactions_pkey` 역순
스캔+필터를 골랐고, V13 복합 인덱스를 추가해도 계획이 안 바뀌었다.
이번에 매칭률을 0.001%로 떨어뜨리자 **예상대로 계획이 바뀌었다.**

```
-- SELECT ... WHERE from_account_id=8 OR to_account_id=8 LIMIT 20
Limit  (actual time=0.051..0.132 rows=20)
  ->  Bitmap Heap Scan on transactions  (actual time=0.050..0.130 rows=20)
        Recheck Cond: ((from_account_id = 8) OR (to_account_id = 8))
        Heap Blocks: exact=20
        ->  BitmapOr  (actual time=0.032..0.032)
              ->  Bitmap Index Scan on idx_transactions_from_account_id_transaction_id (rows=63)
              ->  Bitmap Index Scan on idx_transactions_to_account_id_transaction_id   (rows=68)
Execution Time: 0.159 ms
```

옵티마이저가 V13의 복합 인덱스 두 개를 `BitmapOr`로 결합해 쓴다. `OR`
조건이라 두 인덱스를 함께 못 쓸 거라던 W6의 우려는 틀렸다 — Bitmap
스캔은 `OR`를 `BitmapOr`로 자연스럽게 처리한다. **W6의 "인덱스는 남기고
쿼리(UNION 재작성)는 반려한다" 결정이 정확히 맞았다.** 재작성 없이
매칭률이 낮아지는 시점에 옵티마이저가 알아서 인덱스를 택했다.

| 쿼리 | 계획 | Execution Time |
|---|---|---|
| `LIMIT 20` (정렬 없음, JPA `findAll` 기본형) | BitmapOr → Bitmap Heap Scan | 0.159 ms |
| `ORDER BY transaction_id DESC LIMIT 20` | 위 + top-N heapsort | 0.395 ms |
| `count(*)` (Spring Data `Page` 총건수) | 위 + Aggregate | 0.298 ms |

`count(*)` 병목 우려도 해소됐다 — 같은 `BitmapOr` 계획으로 131건만 세고
0.3ms. 저매칭 계좌에서 seq scan을 하지 않는다.

## k6 부하 — 조회계 4종 + 이체

모두 100 iterations/s · 30초 · 3,000 iteration · **실패 0건**.

| 엔드포인트 | p95 | avg | max |
|---|---|---|---|
| 거래내역 조회 `/accounts/{id}/transactions` | 11.67 ms | 8.18 ms | 133 ms |
| 잔액 조회 `/accounts/{id}/balance` | 7.55 ms | 4.95 ms | 99 ms |
| 계좌 상세 `/accounts/{id}` | 7.91 ms | 4.84 ms | 87 ms |
| 고객별 계좌 목록 `/customers/{id}/accounts` | 7.68 ms | 5.47 ms | 115 ms |
| 이체 `/transfers` (W6 대비 재측정) | 12.89 ms | 9.35 ms | 219 ms |

NFR-PERF-001 기준(이체 200ms, 초당 100건) 대비 조회계 전부 16배 이상 여유.

이체 p95는 W6(8.34ms) 대비 12.89ms로 소폭 올랐지만, 거래내역 테이블
규모와는 무관하다(이체 경로는 `transactions`를 스캔하지 않고 계좌 락 +
멱등키 unique 삽입만 한다). max 219ms 한 건은 JIT/GC 아웃라이어로 보이며
그 외 구간은 W6과 오차 범위. 거래 1천만 건이 이체 성능에 주는 영향은
관측되지 않았다.

## 결론

**1천만 건 규모에서도 조회 경로에 새 병목이 드러나지 않았다.** W6가
"나중에 계좌 수가 늘면 필요할 것"이라며 근거 없이 남겨둔 V13 복합 인덱스가,
그 "나중"이 실제로 오자 옵티마이저 판단만으로 값을 했다. 코드 변경 0.

## 이번 측정에서 안 본 것 (다음 후보)

- **고매칭 계좌·필터 조합**: `account_id=8`(131건) 한 계좌만 측정. 매칭률이
  높은 계좌나 `type`/`from`/`to` 필터를 건 조회는 계획이 다를 수 있다.
- **고객당 계좌 수천 개**: `customer-accounts`는 고객당 2계좌라 가벼운 케이스.
- **CTR/FDS 배치**: `(transaction_type, status, processed_at)` 인덱스 부재 —
  1천만 건에서 seq scan. 이번엔 API 중심 측정이라 제외.
- **콜드 캐시**: PG 기본 설정에서 1천만 건이면 인덱스가 shared_buffers +
  OS 캐시에 다 들어간다. 디스크 IO를 타는 상황은 수치가 다를 수 있다.
