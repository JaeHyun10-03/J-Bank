# 2026-08-01 인증·보안, 상품 도메인, Phase 1 마감 (W3)

목표: `구현계획.md` W3 절 전체. 로그인 자격증명 스키마, JWT 쿠키 인증, CSRF 이중제출,
기존 엔드포인트 전체의 세션 기반 소유자 확인 재작업, 상품 도메인(가입·조회), Phase 1 마감
(시드 데이터, 전체 흐름 통합 테스트, `v0.1.0`).

5개 브랜치로 나눠 진행했고 각 브랜치는 `--ff-only`로 main에 순서대로 병합했다.

## 1. 로그인 자격증명 스키마 (`feat/customer-login-credentials`)

ERD에 로그인 자격증명 컬럼이 아예 없었다 — 문서 갭이라 ADR 0004로 결정을 남겼다.
`customers`에 `login_id`(UNIQUE)/`password_hash`를 추가하고(V6), 회원가입 API에
`loginId`/`password`를 받아 bcrypt로 저장하도록 `CustomerService`를 고쳤다. `Customer`
생성자 시그니처가 바뀌면서 테스트 파일 9곳 이상에 파급됐다.

## 2. 인증·보안 (`feat/auth-security`)

JWT 액세스(15분)·갱신(14일) 토큰, Redis 기반 갱신 토큰 화이트리스트(재사용 탐지 시 토큰
계열 전체 폐기), 로그인 실패 카운터(5회 잠금), 쿠키 3종(`access_token`/`refresh_token`/
`XSRF-TOKEN`) 발급, CSRF 이중제출 필터까지 한 번에 붙였다. W1의 permitAll `SecurityConfig`를
통째로 교체하다 보니 기존 `@WebMvcTest` 전부가 401/403으로 깨졌고, `AuthPostProcessors`
(`asCustomer`/`csrf` 헬퍼)를 만들어 일괄 수정했다.

CSRF 필터를 로그인만 예외 처리했다가 회원가입(`POST /customers`)이 막히는 걸 뒤늦게
발견했다 — 익명 사용자는 `XSRF-TOKEN` 쿠키 자체가 없어 이중제출 검증이 성립할 수 없다.
예외 경로에 추가해서 고쳤다.

## 3. 기존 엔드포인트 소유자 확인 전면 교체 (`feat/ownership-session-based`)

API-002~010, API-017까지 전부 `@RequestParam Long customerId`(문서상 "임시") 대신
`@CurrentCustomerId`(커스텀 애노테이션 + `HandlerMethodArgumentResolver`)로 바꿨다.
서비스 계층까지 `requestingCustomerId`를 관통시켜 이체·입출금·거래내역 조회 전부 소유자
검증을 새로 넣었다 — 기존엔 이체·입출금에 소유자 확인이 전혀 없었다.

테스트 파일의 다중 호출부를 스크립트로 일괄 치환하다가 정규식이 `new BigDecimal("2000.00")`
안의 `"2000.00")`을 호출부 닫는 괄호로 착각해 코드를 깨뜨린 적이 있다. `git checkout --`로
되돌리고 정확한 전체 블록 문자열 치환으로 다시 했다.

## 4. 상품 도메인 (`feat/api-product-domain`)

`Product`/`ProductContract` 엔티티, API-012(가입)·API-018(목록)·API-019(고객별 계약 조회)를
구현했다. 검증 순서는 상품 존재 → 판매중 → 최소금액 → 계좌 존재 → 계좌 소유자 → 계좌 상태.
API-019는 URL이 `/customers/{customerId}/contracts`지만 `customer` 패키지가 `product`를
의존할 수 없다는 ArchUnit 규칙 때문에 `CustomerAccountController`와 같은 패턴으로 `product`
패키지에 뒀다.

## 5. Phase 1 마감 (`feat/phase1-wrapup`)

OpenAPI 스냅샷을 재덤프하다가 실제 버그를 하나 찾았다 — `@CurrentCustomerId`는 인증
토큰에서 유도되는 값인데 springdoc이 이걸 몰라 여전히 필수 쿼리 파라미터 `customerId`로
문서화하고 있었다. 소유자 확인을 세션 기반으로 바꾼 취지가 공개 계약(OpenAPI 문서)에는
전혀 반영이 안 된 것. `@CurrentCustomerId`에 `@Parameter(hidden = true)`를 메타 애노테이션
으로 붙여 고쳤다.

시연용 시드 데이터는 `--spring.profiles.active=local,seed`로만 켜지는 `ApplicationRunner`
하나로 처리했다 — 고객 2명, 계좌 2개, 상품 4종. `customers` 테이블에 데이터가 있으면
아무 것도 안 해서 반복 실행해도 안전하다.

전체 흐름 통합 테스트(`FullFlowIntegrationTest`)는 이 프로젝트 최초의 `@SpringBootTest`다
— Postgres·Redis 컨테이너를 함께 띄우고 MockMvc로 실제 HTTP 요청을 순서대로 보낸다.
회원가입→로그인→계좌개설(2개)→입금→이체→잔액조회→거래내역조회→상품가입까지 검증한다.
계좌개설이 인증을 요구해서 실행 순서는 문서의 "회원가입→계좌개설→로그인"이 아니라
로그인을 계좌개설보다 앞에 뒀다.

작성 중 사소한 실수 하나: `BigDecimal` 필드가 커스텀 시리얼라이저로 JSON 문자열(`"400000.00"`)
로 나가는데, `JsonNode.decimalValue()`는 숫자 노드에만 동작해 문자열 노드에서는 조용히
`0`을 반환한다. `new BigDecimal(node.asText())`로 바꿔서 해결했다 — 애플리케이션 버그가
아니라 테스트 코드의 assertion 방식 문제였다.

## 6. 프론트엔드 라우트 트리와 API 연동 기반

Next.js 14 스캐폴딩 자체는 W1에서 이미 끝나 있었다(Tailwind v4, shadcn/ui, jest·playwright
설치까지). 이번엔 그 위에 세 가지를 얹었다.

`docs/04_J-Bank_화면플로우차트.md`의 화면 전환도를 그대로 App Router 경로로 옮겨 17개
페이지를 만들었다 — 전부 화면 이름만 표시하는 자리표시자다. 폼과 API 연동은 각 화면을
실제로 구현할 때 채운다.

`/api/proxy/[...path]` 라우트 핸들러로 same-site 프록시를 만들었다. 프론트(Vercel)와
백엔드(AWS)가 다른 오리진이라 브라우저가 백엔드 쿠키를 직접 받을 수 없어서다. 응답의
`Set-Cookie`에서 `Domain`을 제거하고 `Path`를 `/`로 정규화한다 — 로컬 환경은 둘 다 원래
비어 있어 지금은 사실상 no-op이지만, 운영 환경에서 백엔드가 `Domain`을 지정하는 순간
이 정규화가 없으면 쿠키 자체가 브라우저에 저장되지 않는다. 실제로 로컬 백엔드를 띄우고
프록시를 통해 로그인 요청을 보내 쿠키 3종이 정상적으로 내려오는 것까지 확인했다.

Axios 인스턴스에 인터셉터 두 개를 붙였다. 요청 인터셉터는 변경 요청에 `Idempotency-Key`를
자동 생성해 붙이는데, 이미 헤더가 있으면 덮어쓰지 않는다 — 그래야 401 재발급 후 재시도가
원래 요청과 같은 키로 나간다. `XSRF-TOKEN` 쿠키 값은 `X-CSRF-TOKEN` 헤더로 복사한다.
응답 인터셉터는 401을 받으면 재발급 요청을 하나로 합쳐서(동시에 여러 요청이 401을 받아도
재발급은 한 번만) 보내고, 성공하면 원 요청을 재시도한다 — 갱신 토큰이 로테이션되므로 각자
재발급을 시도하면 토큰 탈취로 오인되어 계열 전체가 폐기되기 때문이다(화면플로우차트 문서
3절에 이미 경고돼 있던 내용).

이 인터셉터 로직을 검증하려고 `jest`+`jest-environment-jsdom`을 처음 구성했다 — 설치는
W1부터 되어 있었는데 설정 파일이 없어 실제로 돌아간 적은 없었다. 커스텀 axios adapter로
실제 네트워크 없이 인터셉터를 거친 뒤의 요청 설정을 캡처해 검증한다.

## 남은 것

`v0.1.0` 태그는 로컬에 생성했다(원격 푸시는 별도 승인 필요). 각 화면의 실제 폼·API 연동은
Phase 2 착수 이전에 이어서 진행한다.
