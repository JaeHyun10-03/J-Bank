# 2026-07-31 원장·거래 코어와 동시성·멱등성 검증 (W2)

목표: `구현계획.md` W2 절 전체. LedgerEntry/Transaction 도메인, 입금·출금·이체 API 5개,
동시성 시나리오 5종, 분산 락 보류 ADR, CI 통합테스트 단계, k6 베이스라인까지.

브랜치 7개로 나눠 진행했고 각 브랜치는 rebase + `--ff-only`로 main에 순서대로 병합했다
(`docs/브랜치전략.md`).

## 1. 원장·거래 엔티티 (`feat/api-ledger-transaction-entity`)

`LedgerEntry`, `Transaction` 엔티티를 ERD 2.3·2.4절 그대로 옮겼다. `account`와 `ledger`
패키지가 서로 의존하면 안 된다는 ArchUnit 규칙 때문에, 두 엔티티 모두 연관 엔티티 대신
`accountId`/`transactionId`를 순수 `Long` 컬럼으로 뒀다 — 기존 `Account.customerId`가 이미
그렇게 되어 있어 컨벤션을 그대로 따랐다.

원장은 append-only라 이중으로 막았다. 리포지토리는 `JpaRepository` 대신 `Repository` 마커
인터페이스를 확장해 `save`/`findByAccountId`만 노출하고 delete류를 아예 빼버렸다. 엔티티
리스너의 `@PreUpdate`/`@PreRemove`가 2차 방어다.

거래 상태 기계는 5개 상태(PENDING/PENDING_OTP/COMPLETED/FAILED/CANCELLED) 전이 규칙을
`TransactionStatus.canTransitionTo()`에 전부 정의했다. PENDING_OTP 관련 전이는 W5에서야
실제로 쓰이지만, 규칙 자체는 지금 정의해야 나중에 되돌리는 비용이 없다.

## 2. 이체 코어 (`feat/api-transfer-core`)

FR-TXN-003 순서대로 `TransferService.transfer()`를 짰다. 두 계좌번호를 오름차순 정렬한 뒤
그 순서로 `SELECT ... FOR UPDATE`를 걸어 교착상태를 막고, 출금 가능 금액(잔액-지급정지금액)
기준으로 검증한 뒤 차변·대변 원장 두 건과 잔액 캐시 갱신을 한 트랜잭션에 커밋한다.

원래 4개 커밋으로 쪼갤 계획이었는데(락 순서/잔액갱신/출금가능금액검증/멱등성을 각각), 앞의
셋은 실제로는 분리할 수 없는 하나의 절차였다. 억지로 쪼개면 각 커밋이 그 자체로 동작하지
않는 반쪽짜리가 되어 Atomic Commit의 취지에 안 맞아서, 절차 하나 + 멱등성 하나로 2개 커밋에
합쳤다.

## 3. API 5개 (`feat/api-transaction-endpoints`)

API-006(입금)부터 API-010(거래내역 조회)까지. 진행하다가 버그 하나를 발견해서 별도 fix
커밋으로 뺐다 — `GlobalExceptionHandler`의 `Exception.class` 캐치올이 헤더 누락
(`MissingRequestHeaderException`)까지 가로채 항상 500을 내고 있었다. 입금·출금·이체가 전부
`Idempotency-Key` 헤더를 필수로 요구하는 이번 주에 처음 드러난 문제라 여기서 고쳤다.

API-009(잔액 조회)는 계획엔 `transfer` 패키지 몫이었지만, 실제로 다루는 값이 `Account`
엔티티 필드(잔액·지급정지금액·출금가능금액)뿐이라 `AccountService`에 넣었다. API 설계
문서의 섹션 분류보다 실제 데이터 소유권을 따랐다.

API-010(거래내역 조회)의 `type` 필터(TRANSFER_IN/OUT 방향 구분 포함)는 처음에 JPQL의
nullable 파라미터 패턴(`:param is null or ...`)으로 짰다가 PostgreSQL이 파라미터 타입을
추론 못 해 "could not determine data type of parameter" 오류로 막혔다. `Specification`
기반 동적 쿼리로 바꿔서 해결했다 — 필터가 없으면 그 조건 자체가 쿼리에 안 들어가니 타입
추론 문제가 원천적으로 안 생긴다.

## 4. 동시성 시나리오 5종 (`test/api-concurrency-scenario`)

Testcontainers로 실제 PostgreSQL을 띄워 검증했다(H2로는 비관적 락이 실제와 달라 의미
없음). `@DataJpaTest`의 기본 트랜잭션 롤백은 여러 스레드가 각자 커밋한 결과를 봐야 하는
동시성 테스트와 안 맞아 `@Transactional(propagation = NOT_SUPPORTED)`로 껐다.

시나리오③(멱등성 키 10건 동시 요청)을 진짜 동시 요청으로 돌리자마자 버그가 드러났다.
`DataIntegrityViolationException`을 잡고 같은 세션으로 원결과를 재조회하던 로직이
`org.hibernate.AssertionFailure`로 항상 깨졌다. PostgreSQL은 제약 위반 이후 그 DB
트랜잭션 전체를 포기 상태로 만들어 같은 세션의 추가 쿼리를 전부 거부하기 때문이다. 순차
재요청만 검증했던 기존 테스트로는 이 경로가 한 번도 실행된 적이 없어서 여태 발견되지
않았었다. `IdempotencyRecovery`라는 작은 공용 컴포넌트를 만들어 현재 트랜잭션은 롤백
대상으로 표시하고, 조회는 `TransactionTemplate`(`PROPAGATION_REQUIRES_NEW`)이 여는 새
물리 트랜잭션에서 하도록 Deposit·Withdrawal·Transfer 세 서비스를 전부 고쳤다.

시나리오①②를 이어서 돌리다가 두 번째 버그도 나왔다. `static PostgreSQLContainer` 필드를
추상 기반 클래스에 두고 `@Container`/`@Testcontainers`에 맡겼더니, 그 필드를 상속받는
서브클래스 각각이 자기 몫의 `@Testcontainers` 생명주기를 가져 먼저 끝난 시나리오가 공유
컨테이너를 종료시켰다. 컨테이너를 static 초기화 블록에서 직접 기동하는 싱글턴 패턴으로
바꿔 해결했다.

시나리오⑤(이체 도중 강제 예외 발생 → 롤백)는 Mockito로 `LedgerEntryRepository`를 spy해서
장애를 주입하려 했으나 Spring Data 프록시를 spy하는 조합이 `UnfinishedStubbingException`으로
계속 깨졌다. 프로덕션 코드에 테스트 전용 장애 주입 훅을 두는 것도 적절치 않아서, 대신
`TransferService`가 따르는 것과 같은 락→기록 순서를 `TransactionTemplate`으로 직접
재현하고 대변 엔트리 기록 직전에 예외를 던지는 방식으로 바꿨다.

## 5. ADR, CI, 성능 (`docs/adr-w2-no-distributed-lock`, `ci/backend-testcontainers`, `perf/w2-transfer-baseline`)

분산 락(Redisson) 도입을 W2에서 보류하는 근거를 ADR 0003으로 남겼다. 인스턴스가 하나뿐인
동안엔 DB 행 락이 모든 동시성을 이미 직렬화한다는 것, 그리고 분산 락이 실제로 필요해지는
지점은 W7의 다중 인스턴스가 아니라 DB 트랜잭션 경계 밖에서 조율해야 하는 W5 배치 잡의 단일
실행 보장이라는 것.

`backend-ci.yml`은 별도 손댈 게 없었다 — Testcontainers 테스트가 이미 같은 `test` 태스크로
돌고 있어서, 단계 이름만 실제 내용에 맞게 고쳤다.

k6로 이체 엔드포인트 베이스라인을 잡았다. 계좌 2개, 거래내역 0건, 인덱스도 캐시도 없는
상태에서 `constant-arrival-rate`로 초당 100건, 30초. p95 15.3ms, 실패율 0%로
NFR-PERF-001(200ms, 초당 100건) 기준을 큰 여유로 통과했다. 측정 조건 고정 규약을
`perf/README.md`에 남겨 다음 주부터 같은 조건으로 비교한다.
