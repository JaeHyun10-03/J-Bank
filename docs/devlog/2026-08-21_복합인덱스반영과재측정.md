# 2026-08-21 거래내역 복합 인덱스 반영과 재측정

목표: 지난 세션에서 확정한 "거래내역 조회 복합 인덱스" 병목 후보를
실제로 반영하고 재측정해 결정을 기록한다 (`todo/W6.md` "측정 결과로
병목 1건 이상 확정 → 수정 → 재측정" 항목).

## 반영

`V13__add_transaction_account_composite_indexes.sql` —
`idx_transactions_from_account_id_transaction_id`,
`idx_transactions_to_account_id_transaction_id` 두 개를
`(계좌id, transaction_id DESC)`로 추가했다. Docker core 프로파일과
백엔드가 이미 떠 있어(직전 세션 상태 그대로) 재기동만으로 Flyway가
V13을 바로 적용했다.

## 재측정 — 예상과 다른 결과

동일 계좌(`account_id=2`)·동일 조건으로 EXPLAIN ANALYZE를 다시
돌렸는데, **실행계획이 그대로였다**. 새 인덱스가 있어도 옵티마이저는
여전히 `transactions_pkey` 역순 스캔+필터를 고른다.

지난 세션에 "새 인덱스를 실제로 타게 하려면 `OR`을 `UNION`으로 쪼개는
재작성이 필요하다"고 결론 내렸던 걸 직접 검증해봤다. `UNION` 쿼리를
psql로 직접 짜서 실행했더니 — 그 경우에도 각 절반 쿼리가 여전히 PK
역순 스캔을 골랐고(단일 컬럼 매칭률도 여전히 약 20%라 PK 스캔이 더
쌈), 게다가 `UNION`의 중복제거·병합정렬 오버헤드까지 더해져 원래
쿼리보다 18배 느린 결과(0.069ms → 1.222ms)가 나왔다.

## 결정

- 인덱스는 유지한다 — 지금 데이터 규모(계좌 3개)에서 쓰기 비용이
  무시할 만하고, 계좌 수가 실제로 늘어 매칭률이 낮아지는 시점엔
  옵티마이저가 선택할 후보가 된다. 없으면 그 시점에도 못 고른다.
- `UNION` 재작성은 반려한다 — 코드 복잡도만 늘리고 지금 데이터
  규모에서는 실측으로 더 느려지는 게 확인됐다. "계좌 수가 늘면
  매칭률이 낮아진다"는 전제를 로컬 계좌 3개로는 재현할 수 없어,
  근거 없이 반영하지 않는다는 원칙(구현계획 7.5절)에 따라 지금은
  건드리지 않는다.
- 재검토 조건: 스테이징/운영처럼 계좌 수가 실제로 많은 데이터에서
  같은 EXPLAIN을 돌렸을 때 `Rows Removed by Filter`가 지금(22건)보다
  훨씬 크게 나오면 그때 다시 검토한다.

이번 사이클로 "측정 → 수정 → 재측정 → 결정 기록" 1바퀴가 끝났다 —
결론이 "예상한 개선이 없었고, 그래서 더 큰 변경은 반려한다"인 것도
유효한 결정 기록이다.

## 검증

- Flyway 마이그레이션 실제 적용 확인(`Successfully applied 1
  migration ... now at version v13`), `\di`로 인덱스 존재 확인.
- `ANALYZE transactions` 후 EXPLAIN ANALYZE 재실행 — 실제 실행계획
  비교(추정치 아님).
- API 응답시간도 재확인(11~15ms, 인덱스 반영 전과 동일 — 계획이
  안 바뀌었으니 당연한 결과).
