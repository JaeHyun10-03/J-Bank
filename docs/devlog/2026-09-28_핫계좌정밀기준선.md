# 2026-09-28 핫 계좌 정밀 기준선

입금 비동기 반영 작업의 개선 전 비교 기준을 만들려고 EC2 S2(핫 계좌)를 더 촘촘한 단계와 더 많은 회차로 다시 쟀다.
앱 코드는 바꾸지 않았다. 명세: `.claude/tasks/hot-account-baseline/task.md`, 결과: `perf/results/ec2-hot-account/summary.md`.

## 한 일

- **측정 도구**: S2 k6 스크립트가 시작 요청률·간격·상한을 환경변수로 받게 했다(기본값은 기존 S2와 같음). 부하 발생기가 그 값을 회차
  폴더 `ramp.json`에 남기고, 감시·분석이 같은 단계를 쓴다. 분석에 단계별 성공(201) 처리율, 최대 처리 TPS, k6 요약 교차 확인값을 더했다.
- **오케스트레이터**: `s2f` 시나리오(초당 40건 시작, +10, 상한 400)와 `s2f --dry-run`(상한 60), 결과 루트 `PERF_RESULTS`와 인스턴스
  체크아웃 브랜치 `PERF_GIT_REF` 환경변수를 추가했다. 기존 기준선 결과는 건드리지 않고 새 폴더에 쌓았다.
- **측정**: 드라이런 1회 뒤 s2f 7회. 유효 6회(r2~r7)에서 무너진 요청률 중앙값 95(80~140), 최대 처리 TPS 중앙값 103.8(87.7~140.6),
  무관한 잔액 조회 전파 7/7. 무너질 때 대상 CPU는 44~66%로, 핫 계좌 행 락 줄 서기 → 커넥션 풀 대기가 원인이다. 정합성은 전 회차 유지.

## 측정 중 만난 문제

- **로컬 맥 수면**: 덮개를 닫은 배터리 상태에서 로컬 오케스트레이터가 잠들어 SSM 명령 사이가 15~18분씩 벌어졌다. r1은 예열 후
  37분 뒤에 측정이 시작돼 참고 회차로 돌리고 r6로 대체했다. `caffeinate -i`는 덮개 수면을 막지 못한다. 전원을 연결하고 `-is`로 돌린다.
- **꼬리 구간**: 감시가 k6를 멈추기 전 다음 단계 앞부분(6~7초)의 처리율이 최대 TPS로 잡혔다. 단계를 다 채운 구간만 보도록 고쳤고,
  이미 받은 회차는 같은 규칙으로 요약에서 다시 계산했다.
- **실패 수**: Prometheus `increase()`가 새로 생긴 시계열의 첫 값을 세지 못해 단계별 실패가 0으로 나왔다. 요약은 k6 확정값을 쓴다.
- **변동폭**: r3만 140에서 무너졌다. 규칙대로 r7을 추가했고 원인은 단정하지 못했다(r3의 steal이 낮았던 상관만 관측).
  r3은 120 단계를 넘겨 재로그인 요청이 단계 통계에 섞인 유일한 회차다. 개선 후 비교에서 이 처리 방식을 정해야 한다.
