# 2026-08-18 Micrometer·Prometheus·Grafana·Loki 관측 가능성 구축

목표: `todo/W6.md` 월요일분 — Micrometer/Prometheus 지표 노출, Grafana
대시보드, 로그 JSON 구조화, Loki 연동 네 항목.

## Micrometer / Prometheus

`micrometer-registry-prometheus`를 추가하고 `/actuator/prometheus`를
열었다. `perf/README.md`의 k6 스크레이프 타깃이 처음부터
`host.docker.internal:8080/actuator/prometheus`를 가리키고 있었는데
실제로는 노출된 적이 없던 상태였다.

락 대기 시간은 `AccountRepository`의 `PESSIMISTIC_WRITE` 락 획득
지점(`findByAccountNumberForUpdate`, `findByIdForUpdate`) 두 곳에
`@Timed`를 붙이고 `TimedAspect`를 등록해 `db.lock.wait`로 노출했다.
이체 처리시간 백분위 패널이 동작하려면 히스토그램 버킷이 필요해서
`http.server.requests`에 `percentiles-histogram`도 켰다 — 엔드포인트
수가 적어 카디널리티 부담은 크지 않다고 판단했다.

## 로그 JSON 구조화

Spring Boot 3.4+ 네이티브 구조화 로깅(ECS 포맷)을 쓰려 했는데,
`application.yml`의 `logging.structured.format.console` 프로퍼티는
Boot가 기본 로깅을 초기화할 때만 적용되고, Loki 연동을 위해 커스텀
`logback-spring.xml`을 두는 순간 무시되고 평문으로 돌아갔다(직접
부팅해서 확인). `StructuredLogEncoder`를 CONSOLE 어펜더에 명시적으로
지정해 우회했다 — 이 부분만 별도 fix 커밋으로 뺐다.

`RequestTraceIdFilter`가 W1부터 MDC에 심어둔 `traceId`는 그대로
ECS JSON 필드로 남는다.

## Loki 연동

Promtail 컨테이너에 로그 파일을 공유 볼륨으로 태우는 방식 대신
`loki-logback-appender`로 `local`/`dev` 프로파일에서
`http://localhost:3100/loki/api/v1/push`에 직접 push하는 쪽을
선택했다 — 컨테이너 하나와 볼륨 마운트를 아낀다. `prod`는 대상에서
뺐다(운영 로그 수집 경로는 이 스코프 밖).

## Grafana 대시보드

Prometheus·Loki 데이터소스와 5패널 대시보드(이체 처리시간
p50/p95/p99, TPS, 에러율, DB 커넥션 풀 사용률, 계좌 락 대기 시간)를
provisioning으로 자동 등록되게 했다. 마지막 두 패널이 구현계획
문서가 명시한 동시성 설계 근거 지표다.

## 검증

- 백엔드: `./gradlew compileJava` 통과, `local` 프로파일로 직접
  부팅해서 콘솔 JSON 출력·Loki 어펜더 정상 작동(연결 거부는 로컬에
  Loki가 안 떠 있어서 나는 예상된 에러) 확인. DB가 없어 완전
  기동까지는 못 갔다.
- 인프라: `docker compose config`와 대시보드 JSON/데이터소스 YAML
  문법 검증까지만 했다 — Docker Desktop이 꺼져 있어 실제 Grafana
  기동과 대시보드 렌더링 확인은 다음 로컬 세션에서 해야 한다.

## 커밋

구조화 프로퍼티 무시 문제 fix → Loki 연동 → 백분위 히스토그램 노출
→ Grafana 프로비저닝, 7개로 나눴다. 원래 계획은 6개였는데, 구현

히스토그램 설정을 대시보드보다 앞에 독립 커밋으로 뺐다.
