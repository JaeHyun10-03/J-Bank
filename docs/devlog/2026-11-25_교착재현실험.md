# 2026-11-25 이체 교착 재현 실험

작업: `.claude/tasks/transfer-deadlock-experiment`. 결과: `perf/results/deadlock/README.md`.

## 계기

포트폴리오의 수정 전·후 근거가 부족했다. 이 저장소는 처음부터 두 계좌를 정렬해서 잠갔고(FR-TXN-003), 운영에서 교착을 겪은 적이 없다. 그래서 "겪었다"가 아니라 "일부러 재현했다"로 남겼다. 정렬 없는 `FOR UPDATE`로 교착을 만들고, 알림·로그·지표로 발견해, 락 순서 정렬과 현재 락 모드로 사라지는 것을 같은 조건의 수치로 비교했다.

## 바꾼 것

- 이체 락 전략 설정 `JBANK_TRANSFER_LOCK_STRATEGY`(`current`·`sorted-for-update`·`unsorted-for-update`). 기본값은 `current`다. 즉시 이체와 OTP 완료 두 경로가 따른다.
- k6 교착 부하, 로컬·운영 실행 스크립트, 요약 스크립트, runbook.
- 운영 프론트 가입·로그인 CORS 수정(PR #19). 실험 고객을 만들려다 발견했다.

## 결과

- 교착은 ①(정렬 없음)에서만 났다. 로컬은 ① 6회에서 167~222건, 운영은 ① 2회에서 252건·309건이다. ②·③은 전부 0건이다.
- ①은 처리량이 초당 3.8~4.1건(운영)으로 무너진다. ②·③은 운영에서 109~141건이다.
- 운영에서 첫 교착 약 48초 뒤에 알림 메일이 왔다(① 동시 50).
- 실험 뒤 FDS 배치는 1,393초 걸렸고 의심 거래 36,590건을 만들었다. 부팅 때는 25초였다.

수치와 한계는 결과 보고서에 있다.

## 막힌 것

- **운영 프론트에서 가입이 안 됐다**: 화면 오류는 `Invalid CORS request`였다. 프론트 프록시가 브라우저의 `Origin`을 그대로 API에 넘기는데, API 허용 목록에 프론트 출처가 없었다. 주석에는 "배포 프론트에는 CORS가 생기지 않는다"고 적혀 있었다. 같은 서술이 설계 문서 05·06·07에도 남아 있어 따로 고쳐야 한다.
- **조사 중에 본 500은 내 실수였다**: 원인을 찾으며 본 500은 셸의 따옴표 실수로 깨진 헤더가 나간 결과였다. 헤더를 바르게 넣어 다시 보내고 나서야 알았다.
- **잔액 0원으로 1차 실행을 마쳤다**: 실행 스크립트가 시작 전에 계좌 잔액을 확인하지 않아, 완료 이체가 0건인 채로 6회가 "완료"로 끝났다. 설정 복귀의 확인용 이체가 409로 실패한 것을 보고 알았다. 결과는 지우지 않고 `prod-zero-balance`에 두고 다시 돌렸다.
- **화면에 두 번째 계좌를 여는 버튼이 없다**: 실험에 계좌 2개가 필요했지만, 계좌가 있으면 홈에서 개설 버튼이 사라진다. 주소로 직접 열었다.
- **없는 날짜의 주민번호로 가입하면 500이 난다**: 프론트가 앞자리를 날짜 검사 없이 생년월일로 만들고, API에 잘못된 본문 처리기가 없다. 사용자가 넣은 값은 확인하지 않았다. 후속 작업으로 남긴다.

## 남긴 것

- 운영은 조건당 1회라 순서 효과를 구분하지 못한다. 로컬과 운영은 서로 비교하지 않는다.
- 실행 스크립트에 시작 전 잔액 확인을 넣는 것, FDS 배치 시간과 메모리는 후속 작업이다.
- 교착 예외의 재시도와 전용 오류 코드는 이 작업 범위 밖이다.
