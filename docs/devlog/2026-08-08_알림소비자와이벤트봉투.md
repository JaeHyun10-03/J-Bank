# 2026-08-08 발행 메시지 eventType 포함 + 이체완료 알림 소비자 (W4 토)

목표: `todo/W4.md` 토요일분 시작. 발신함이 발행하는 단일 토픽(`jbank.events`)을
소비자가 구독할 때 이벤트 종류를 구분할 수 있어야 해서 봉투 형식을 먼저
고치고, 그 위에 알림 소비자를 붙였다.

## `OutboxPublisher` 발행 메시지에 eventType 포함

기존에는 `event.getPayload()`(도메인 데이터 자체)를 그대로 직렬화해
발행했다. 토픽을 하나만 쓰는 구조(`jbank.events`)에서는 소비자가 메시지
본문만 보고 어떤 이벤트인지 알 방법이 없었다 — `OutboxEvent`가 이미
갖고 있는 `eventType`/`aggregateType`/`aggregateId`를 봉투로 감싸
`data` 필드에 기존 payload를 넣는 형태로 바꿨다. `OutboxPublisherTest`에
봉투 필드가 전부 직렬화되는지 검증하는 케이스를 추가했다.

## `NotificationEventConsumer` 구현

`support.notification` 패키지에 `@KafkaListener(topics =
"${jbank.outbox.topic}")`로 `jbank.events`를 구독하는 소비자를 추가했다.
봉투를 파싱해 `eventType`으로 분기하고, `TRANSFER_COMPLETED`만 처리해
알림 내용을 `log.info`로 남긴다 — 실제 발송 채널(푸시/문자) 연동 전까지는
로그 출력이 알림 발송을 대신한다는 게 이번 주 완료 기준의 전제다. 모르는
`eventType`은 `log.debug`로 조용히 넘긴다.

`support`가 도메인을 직접 호출하지 않고 이벤트만 구독하는 폴더구조 4.2절
규칙은 발신함 리스너 때와 동일하게 유지된다 — 소비자는 Kafka 메시지만
보고 어떤 도메인 서비스도 참조하지 않는다.

테스트(`NotificationEventConsumerTest`)는 Kafka 브로커 없이
`consumer.onMessage(String)`을 직접 호출하고, logback `ListAppender`로
로그 출력을 캡처해 검증한다 — `TRANSFER_COMPLETED` 처리와 알 수 없는
타입 무시 두 경로를 확인했다.

## 검증

`./gradlew test --tests "*OutboxPublisherTest*" --tests
"*NotificationEventConsumerTest*"` 통과. Kafka 브로커가 실제로 필요한
통합 검증(발행→소비 전체 흐름)은 하지 않았고, 두 단위 테스트가 각자
경계(발행 메시지 형식 / 소비 후 로그 출력)만 확인했다.

재기동 시 미발행 이벤트가 발행되는지 검증(W4 완료 기준 항목), 백엔드
