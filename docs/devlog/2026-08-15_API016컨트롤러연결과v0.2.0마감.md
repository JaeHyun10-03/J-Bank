## API-016 컨트롤러 연결

`OtpVerificationRequest` DTO(`otpCode` 6자리 숫자, `@Pattern`으로 형식
검증)를 추가하고 `TransferController`에
`POST /transfers/{transactionId}/otp-verifications`를 연결했다.
서비스 레벨 로직은 손대지 않았다 — 경로 변수와 요청 바디를
`OtpVerificationService.verify(transactionId, otpCode, customerId)`로
그대로 전달하고, 성공 응답을 200으로 감싸는 얇은 어댑터 계층만
추가했다. 이체 생성 API(API-008)와 같은 컨트롤러 클래스에 두어
`TransferService`/`OtpVerificationService` 두 의존성을 나란히
주입받는 구조다.

에러 코드(`AUTH_004_OTP_MISMATCH` 400, `AUTH_005_OTP_EXPIRED` 410,
`TXN_005_TRANSACTION_NOT_PENDING` 409)는 어제 `ErrorCode`에 이미
정의돼 있어 `GlobalExceptionHandler`가 그대로 처리한다.

## 테스트

`TransferControllerTest`에 OTP 일치(200/COMPLETED), 불일치(400),
만료(410), 코드 형식 오류(400) 네 시나리오를 `WebMvcTest`로
추가했다. 서비스 레벨 성공/불일치/한도초과/만료/소유자아님/이미완료
시나리오는 어제 `OtpVerificationServiceIntegrationTest`로 이미
검증돼 있어 컨트롤러 테스트는 HTTP 매핑(경로·상태코드·검증)만
확인한다.
