## 이체 OTP 검증 화면

`transfer/otp/page.tsx`가 `ScreenPlaceholder` 스텁 상태였던 걸
실구현으로 교체했다. 화면플로우차트 190~191행 명세를 그대로
따랐다:

- 대기 중인 이체 정보(받는계좌·지급정지 금액)를 화면에 명시해
  둔다 — 202 응답을 받은 시점에 출금계좌 지급정지가 잡히므로,
  OTP 화면에 머무는 동안 다른 화면에서 출금 가능 금액이 줄어
  보이는 게 정상이라는 걸 사용자가 알 수 있어야 한다.
- `otpExpiresAt`(클라이언트가 202 응답 시점 + 3분으로 계산해
  스토어에 넣어둔 값) 기준 카운트다운 타이머.
- `AUTH_004_OTP_MISMATCH` → 인라인 에러, 같은 화면에서 재입력.
- `AUTH_005_OTP_EXPIRED`와 `TXN_005_TRANSACTION_NOT_PENDING`을
  같은 경로로 묶어 처리했다. 후자는 실패 횟수 초과로 거래가
  이미 취소된 뒤 재시도했을 때 나오는 코드인데, 서버가 실패
  횟수초과와 단순 불일치를 같은 `AUTH_004`로 응답하기 때문에
  프론트에서 구분할 수 없다 — 대신 취소된 거래에 재검증을
  시도하면 `TXN_005`가 돌아오므로, 이 코드를 만료와 동일하게
  "지급정지 해제됨, 이체 재시작" 경로로 보냈다.
- 두 경로(만료·이미취소) 모두 계좌 잔액/거래내역 쿼리를
  무효화하고 이체 위저드 스토어를 리셋한 뒤 이체 입력 화면으로
  돌려보낸다.
- 성공 시에는 이체 확인 화면의 즉시완료 케이스와 동일하게
  `TransferCompleteCard`를 재사용했다(이 컴포넌트는 애초에 두
  지점 공용으로 설계돼 있었다).

새 컴포넌트 테스트는 추가하지 않았다 — 레포에 프론트 페이지 단위
테스트 관례 자체가 없고(E2E는 Phase 2 트랙), 입금/출금/이체
화면도 같은 방식으로 커밋됐다.

## 배치 잡 로컬 실행 확인

W5 목~토요일분에서 세 배치 잡의 재실행 안전성은 통합 테스트로
이미 검증해뒀지만, "Compose 환경에서 프로파일+잡 이름 인자로
트리거"하는 실제 실행 경로는 한 번도 타본 적이 없었다. 오늘
직접 확인했다:

1. `infra/compose`에서 `docker compose --profile core up -d`로
   postgres/redis만 띄움(배치 잡엔 kafka 불필요).
2. `./gradlew bootJar`로 빌드한 뒤, 잡마다
   `java -jar jbank-api-*.jar --spring.profiles.active=local,batch
   --spring.batch.job.name=<잡이름> runDate=<일자>`로 개별 실행.
3. `interestMaturityJob`, `ledgerReconciliationJob`,
   `ctrDetectionJob` 셋 다 `COMPLETED` 로그 확인.
4. 같은 `runDate`로 `interestMaturityJob`을 재실행해
   `JobInstanceAlreadyCompleteException`으로 실제 프로세스
   재기동 레벨에서도 차단되는 걸 재확인.

`application.yml`은 `spring.batch.job.enabled=false`가
기본값이고 `application-batch.yml` 프로파일이 이를 `true`로
뒤집는 구조라, 웹 서버는 그대로 뜨되 잡 이름을 지정하지 않으면
아무 배치도 안 도는 것도 이번에 눈으로 확인했다.
