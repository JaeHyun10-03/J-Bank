# 2026-10-29 관측 스택: 로그를 한 곳에 모으고 문제를 메일로 받기

작업: `.claude/tasks/observability-logs-alerts`. 결정은 ADR 0014, 운영 절차는 `docs/runbook/observability.md`.

## 계기

포트폴리오의 교착 해결 항목에 "수정 전" 근거를 보강하려다 질문이 거꾸로 됐다. "운영에서 교착이 나면 어떻게 알지?" 확인해 보니 알 방법이 없었다.

- 지표는 Prometheus·Grafana에 있지만 알림 규칙이 하나도 없었다.
- 로그는 컨테이너마다 `docker logs`에 흩어져 있었다. 9월 다운사이징 때 "한 대면 `docker logs`로 충분"하다며 Loki를 뺐다.
- 교착 카운터(`pg_stat_database_deadlocks`)를 모으는 postgres-exporter는 부하 테스트 구성에만 있었다.
- 로컬 Prometheus는 관리 포트가 없는 api의 8080을 긁어 계속 401이었다. 운영만 고치고(ADR 0013) 로컬은 남겨 둔 것이다.

## 계획 단계에서 바뀐 것들

계획 리뷰를 4회 받았고, 그때마다 구현 전에 큰 구멍이 나왔다.

- **메모리**: t3.small 2GB에 Loki를 얹는 게 맞나. SSM 읽기 전용 명령으로 운영을 재 보니 유휴 가용 944MiB. 새 컨테이너 상한 합계 368MB를 다 쓰면 576MiB가 남는데, 부팅 직후 배치 JVM(512MB)이 뜨면 가용이 100MiB 근처까지 내려갈 수 있다. 예전 부하 테스트에서 127MB까지 떨어져 50분 무응답한 사고와 같은 패턴이다. 사양을 올릴지(t3.medium·t3a.medium, 월 +$5~6) 고민하다 t3.small을 유지하고, "반영 후 유휴 600MiB·배치 중 최저 150MiB" 기준에 미달하면 로그 수집만 끄기로 했다. 끈 상태가 이후 `up -d`에도 유지되도록 compose 프로필(`logs`)로 묶었다.
- **도커 소켓**: 처음엔 alloy에 소켓을 `:ro`로 주면 된다고 적었다. 리뷰에서 "유닉스 소켓 `:ro`는 API 호출을 막지 못한다, 소켓 접근 = 호스트 root"라는 지적을 받았다. 소켓 프록시를 두고 허용 경로를 목록으로 제한했는데, 다음 리뷰에서 또 "일반 프록시의 컨테이너 허용은 archive(컨테이너 안 파일 읽기)까지 연다, 같은 네트워크의 grafana에서도 프록시에 닿는다"가 나왔다. 경로 정규식을 받는 프록시(wollomatic/socket-proxy)로 바꾸고 alloy만 붙는 internal 네트워크를 만들었다. 그래도 inspect 응답에 api 환경변수(비밀값)가 들어 있다는 위험은 남아 수용으로 기록했다.
- **SMTP 비밀번호**: 운영 `.env`에 넣으려 했는데 api가 `env_file: .env`로 파일 전체를 받는다. Gmail 앱 비밀번호가 api 컨테이너 환경변수에 들어간다는 뜻이다. `.env.alertmanager`로 분리했다.
- **병합 순간의 DB 재시작**: postgres에 `log_lock_waits=on`(`command`)을 추가하면, 병합 직후 backend-cd의 `deploy.sh`(`up -d api`)가 의존 서비스인 postgres까지 재생성한다. `--no-deps`가 없기 때문이다. 서버가 꺼진 18시 이후 병합해 다음 날 부팅 때 재생성되게 했다.
- **exporter가 살아 있는데 DB를 못 보는 경우**: postgres-exporter는 DB 접속에 실패해도 `/metrics`에 200을 주고 `pg_up 0`만 낸다. `up`만 보면 교착 알림이 조용히 꺼진다. 다운 알림을 `up`과 `pg_up` 둘 다로 판정하게 넓혔다.

## 구현하며 막힌 것

- **socket-proxy 403**: alloy의 컨테이너 탐색이 `GET /v1.53/networks`로 네트워크 라벨을 계산하려다 막혔다(`Unable to refresh target groups ... Forbidden`). 네트워크 목록에는 비밀값이 없어 허용 목록에 넣었다. 프록시가 허용식 앞뒤에 `^`·`$`를 붙인다는 것도 시작 로그(`[^^(...)$$]`)에서 알았다.
- **Hook이 `docker run --rm ... -verify-config`를 막음**: 하네스의 위험 명령 정규식 `\brm\b.*\s-[a-zA-Z]*[rR]`이 `--rm` 뒤의 `-verify`를 `rm -r`로 봤다. 이름을 붙여 실행한 뒤 정리하는 방식으로 바꿨다.
- **Loki 내장 캐시**: 기본 결과 캐시·청크 캐시가 각 100MB라 192MB 상한을 넘긴다. 16MB로 줄였다.

## 통합 확인에서 틀린 것 (검사 쪽 실수)

1차 통합 확인은 실패 2건과 스크립트 오류로 끝났다. 셋 다 설정이 아니라 검사 쪽 문제였다.

- "alertmanager 재기동 뒤 새 메일 0통"으로 판정했는데, 그 사이 온 메일은 다른 알림의 **해제** 메일이었다. 요구는 "같은 알림의 발생 메일을 다시 안 보냄"이다. 알림이 계속 발생 중인 상태에서 재기동하고 6분 기다리는 독립 검사로 다시 확인했다.
- 프록시 허용 경로를 `/v1.43/...`로 불렀더니 400이 났다. 응답 헤더가 `Server: Docker/29.2.1`이라 프록시가 아니라 데몬이 낸 것이다. Docker 29의 최소 API가 1.44다.
- 정리용 `docker container prune -f`가 시험 중 멈춰 둔 postgres-exporter 컨테이너까지 지웠다. 그래서 exporter 다운이 실제로 한 번 더 일어났고, 그 발생 메일이 "중복"처럼 보였다. 이 명령은 이 로컬 Docker의 다른 멈춘 컨테이너도 지웠을 수 있다. 이후로는 이름을 지정해 지운다.

운영 구성 사전 검증에서는 runbook에 넣을 것 세 가지를 찾았다. `.env`에 `COMPOSE_PROFILES`를 넣으면 api도 재생성된다. Grafana는 Alertmanager 데이터소스의 상태 확인을 지원하지 않는다("Plugin unavailable"). `amtool`의 주석 값에 공백이 있으면 파서 경고가 난다.

## 결과

- 로컬·운영 모두 Grafana 한 곳에서 지표·로그(15일)·발생 중 알림을 본다.
- 알림 4종(교착, 이체 5xx 비율, 수집 대상 다운, 락 대기)이 발생·해제 메일로 온다. 기준값은 promtool 경계 테스트 13건으로 고정했다.
- 로컬에서 psql 교착 → `deadlock detected`·`DETAIL` 로그 조회 → 교착 알림 → 메일까지 이어지는 것을 확인했다. 다음 작업(교착 재현 실험)의 "알림 → 로그로 원인 분석 → 해결" 흐름이 이 위에서 돈다.
- 운영 반영(메일 계정 입력, 메모리 측정, Gmail 수신 확인)은 병합 후 runbook대로 한다.

## 다음에 비슷한 문제를 만나면

- 알림을 추가하기 전에 "그 지표가 실제로 수집되고 있나"부터 본다. 이번엔 교착 카운터도, 로컬 api 지표도 없었다.
- 소켓 `:ro`, `.env` 공유, `up -d <서비스>`의 의존 서비스 재생성처럼 "이름만 보면 안전해 보이는" 설정을 의심한다.
