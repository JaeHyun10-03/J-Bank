# 2026-08-04 이벤트 발행 지점 연결과 위험도 이력 진입점 통합 (W4 화)

목표: `todo/W4.md` 요일별 계획의 화요일분. 계좌 상태변경·이체완료·고객등급변경 세
지점에 이벤트 발행 연결, `CustomerRiskAssessmentHistory` 스냅샷 로직 + 등급 변경
진입점 통합. 7개 커밋으로 진행(기능/리팩토링/테스트를 커밋마다 분리하는 CLAUDE.md
원칙에 따라 각 지점을 feat 커밋과 test 커밋으로 나눔).

## 1~2. 계좌 상태변경 → `AccountStatusChangedEvent`

`AccountService`의 `changeStatus()`와 `close()` 둘 다 계좌 상태를 바꾸는 지점이라
두 곳 모두에서 발행하도록 연결했다. 월요일에 만든 `AuditLogListener`는
`REQUIRES_NEW`로 감사 실패를 삼키는 쪽이라, 상태 전이 자체는 감사 기록 성패와
무관하게 그대로 진행된다.

테스트는 기존 `AccountServiceIntegrationTest`에 `AuditLogListener`를 `@Import`로
추가하고, 정지 전이·해지 테스트 각각에 `ACCOUNT_STATUS_CHANGED` 감사 로그가
남는지 검증하는 assertion을 붙였다.

## 3~4. 이체완료 → `TransferCompletedEvent`

`TransferService.transfer()`에서 `transaction.complete()` 직후 발행한다. 이
리스너는 `REQUIRED`(호출자 트랜잭션 참여)라, 감사 저장이 실패하면 이체 트랜잭션
전체가 롤백된다 — 월요일 설계 그대로.

멱등키 재요청 경로(기존 트랜잭션 반환)와 유니크 제약 충돌 후 복구 경로는 이미
완료된 이체를 다시 반환할 뿐이라 이벤트를 다시 발행하지 않는다. 새로 완료되는
경우에만 발행되도록 `transaction.complete()` 바로 다음 줄에 뒀다.

## 5~7. 위험도 이력 진입점 통합 + `CustomerGradeChangedEvent`

`CustomerService.register()`와 `registerEdd()`에 각각 인라인으로 흩어져 있던
`CustomerRiskAssessmentHistory` 저장 코드를 `recordRiskAssessment()` 사설 메서드
하나로 모았다(순수 리팩토링 커밋, 동작 변화 없음).

그 다음 커밋에서 이 메서드에 `previousKycGrade`/`previousAmlRiskLevel` 파라미터를
추가해, 두 값이 실제로 다를 때만 `CustomerGradeChangedEvent`를 발행하도록 확장했다.
`previousKycGrade`가 `null`이면 최초 등록(비교 대상이 없음)으로 보고 발행하지
않는다.

다만 오늘 기준으로 `registerEdd()`는 등급을 실제로 바꾸지 않는다(재평가 규칙표가
없어 ponytail 처리된 상태 — `CustomerService.java` 상단 주석 참고). 그래서 현재
운영 경로로는 `CustomerGradeChangedEvent`가 실제로 발행되는 경우가 아직 없다.
이벤트/리스너/발행 로직 자체는 다 붙어 있으니, 나중에 위험도 재평가 로직이
`recordRiskAssessment()`를 거쳐 실제로 등급을 바꾸기 시작하면 그대로 동작한다.

이 "발행되지만 아직 아무도 안 쓰는" 분기를 통합 테스트로는 확인할 방법이 없어서
(공개 API로는 등급이 실제로 안 바뀌므로), `recordRiskAssessment()`를
package-private으로 낮추고 Mockito 단위 테스트(`CustomerServiceTest`)로 세 분기
(최초 등록/등급 유지/등급 변경)를 직접 검증했다.
