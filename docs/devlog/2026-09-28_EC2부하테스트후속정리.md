# 2026-09-28 EC2 부하 테스트 후속 정리

직전 작업(EC2 부하 테스트 기준선) 결과 리뷰의 개선 지적을 정리했다. 측정은 다시 하지 않고 받아 둔 원자료로 문서를 바로잡고,
다음 측정에서 쓸 절차를 고쳤다. 명세: `.claude/tasks/ec2-load-test-followup/task.md`.

## 한 일

- **정합성 스냅샷 순서**: 측정 후 "정합성 → 실패 키 대조 → api 정지"를 "api 정지 → 정합성 → 실패 키 대조"로 바꿨다. api가 떠 있으면
  그 사이 대기열 이체가 커밋돼 스냅샷과 대조가 서로 다른 상태를 본다. 이후 측정은 "실패 키 중 반영" 수가 기준선보다 조금 작을 수
  있어 README에 비교 조건 차이로 적었다.
- **정합성 표 행 이름**: "실패 응답인데 실제 반영"이 k6를 멈춘 순간 끊긴 요청의 키까지 합산해 오해를 샀다. "실패 키 중 DB 반영(끊긴
  요청 포함)"으로 바꾸고 실패 응답 중 반영 하한을 함께 적는다.
- **드롭 수**: 요약에 k6가 센 확정 드롭 수와 Prometheus 단계별 추정치를 구분해 넣었다. 추정치는 `increase()` 외삽이라 S3에서는
  확정값보다 크게 나왔고(20,985 대 19,620), 표본이 없으면 null이라 0으로 바꾸지 않고 "수집 없음"으로 적었다.
- **S2 r1·r3, S5 메모리**: 섞여 있던 "실패 응답 반영 0·1건"을 실패 응답 0건과 중단 순간 끊긴 키의 반영으로 나누고, S5 메모리는 배치
  구간 최저와 회차 전체 최저를 구분했다.
- **1차 측정 문서**: `first-pass/` 두 문서 맨 위에 결함 기록임과 기준선 위치를 적었다(본문 수치는 그대로).
- **다음 드라이런 확인 값**: 정지된 api 로그를 실제로 읽었는지 보는 `api_log_lines`를 앱 로그 형식(`log.level`) 줄 수로 센다. `wc -l`은
  compose 에러 한 줄로도 0보다 커져 확인이 되지 않았다(결과 리뷰 1회차 지적).

## 이력 정리

`perf/ec2-load-test` 브랜치에서 내용과 메시지가 맞지 않던 커밋(1차 결과 이동인데 수정 커밋 메시지가 붙음)의 메시지를 고쳤다. 트리
비교로 내용이 같음을 확인했고, 정리 전후 해시 대응표는 작업 기록(progress.md)에 남겼다. 원격 반영은 강제 push가 필요해 직접 실행하기로 했다.

## 검증

계획 리뷰 2회(2회차 통과), 결과 리뷰 2회(1회차 통과 권고 후 개선 반영, 2회차 새 지적 없음), verify 통과. 문서 값은 원자료 대조 스크립트로
12항목 모두 일치를 확인했다.
