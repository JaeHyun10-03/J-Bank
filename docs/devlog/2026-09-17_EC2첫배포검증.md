# 2026-09-17 EC2 첫 배포 검증

## 배경

PR #3으로 EKS를 EC2 단일 인스턴스 + Compose로 낮춘 뒤, 실제로 배포해 끝까지 연결되는지
확인했다. 알려진한계 문서 11번("실행된 적 없는 CD 스텝이 문서상으로만 존재")의 재발을
막으려면 첫 배포를 기록으로 남겨야 했다. 이번엔 Terraform은 터미널, 확인은 AWS 콘솔로
한 단계씩 진행했다 — AWS 콘솔 구조를 익히는 것도 목적이었다.

## 발견 1 — GitHub OIDC `sub` 클레임 형식

`Configure AWS credentials` 단계에서:

```
Error: Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

신뢰 정책(`sub = repo:JaeHyun10-03/J-Bank:ref:refs/heads/main`)과 OIDC provider 설정은
전부 맞아 보였고, 역할 생성 30분 뒤 실행이라 전파 지연도 아니었다. backend-cd가 이
저장소에서 **성공한 이력이 없다**는 점(전부 skipped)이 단서였다 — OIDC 연결 자체가 처음
검증되는 것이었다.

토큰 클레임을 찍는 임시 단계를 넣어 확인했다(토큰은 출력하지 않고 payload만 디코드):

```json
"sub": "repo:JaeHyun10-03@174772263/J-Bank@1314857440:ref:refs/heads/main"
```

GitHub이 소유자·저장소 **숫자 ID를 `@`로 붙인 형식**을 보내고 있었다. 이름만 쓴 조건은
`StringEquals`든 `StringLike repo:owner/repo:*`든 매칭이 안 된다. ID는
`https://api.github.com/repos/<owner>/<repo>`의 `owner.id`, `id`와 일치했다.

수정: `ec2` 모듈과 `bootstrap` 양쪽 신뢰 정책을 ID 포함 형식으로. bootstrap의
plan/apply 역할도 같은 패턴이라 infra-cd 역시 같은 이유로 깨져 있던 상태였다. ID가
붙어 있으면 저장소 이름이 바뀌거나 재생성돼도 다른 저장소가 역할을 못 쓰므로 오히려
더 좁은 조건이다. 와일드카드가 필요 없어져 `StringLike` → `StringEquals`.

교훈: OIDC 인증 실패는 정책을 아무리 들여다봐도 답이 안 나온다. **토큰이 실제로 뭘
들고 오는지** 먼저 찍는다.

## 발견 2 — SSM Run Command는 root

인증 통과 후 `Deploy via SSM`에서:

```
fatal: detected dubious ownership in repository at '/opt/jbank'
```

SSM은 root로 명령을 실행하는데 `/opt/jbank`는 user_data가 `ec2-user` 소유로 clone했다.
git 2.35.2+는 소유자가 다른 저장소를 거부한다. `safe.directory`를 추가하는 대신 명령
자체를 `runuser -u ec2-user -- bash -c "..."`로 내렸다 — 저장소도 `.env`도 ec2-user
소유이고 docker 그룹도 그쪽에 있어서 배포 전체가 한 사용자로 일관된다.

## 발견 3 — Vercel env는 재배포해야 반영

`BACKEND_API_URL` 추가 직후 프록시가 500(빈 응답). 함수가 여전히 기본값
`http://localhost:8080`으로 fetch해 연결 거부. Deployments → Redeploy 후 정상.

## 그 외

- GHCR 첫 푸시 시 패키지가 private으로 생긴다. Package settings → Change visibility →
  Public 전환. 저장소가 public이고 이미지에 비밀값이 없으므로(전부 `.env` 주입) 문제 없음.
- Caddy 첫 기동 로그의 `creating new account ... no such file or directory`는 info
  레벨 — ACME 계정 파일이 아직 없다는 뜻이고 정상.
- SSM 세션은 20분 유휴면 끊긴다. 콘솔에서 다시 연결.

## 알려진한계 11번에 대한 답

이번 CD는 실제로 실행됐고, 실패 2회를 거쳐 성공까지의 과정이 Actions 이력과 이 문서에
남아 있다. 남은 위험은 "다음에 워크플로를 고치고 안 돌려보는 것" — backend-cd는 main
push마다 돌아 자연히 검증되지만, infra-cd는 `TERRAFORM_CI_READY`가 아직 꺼져 있어
검증되지 않았다. 켤 때 같은 방식으로 첫 실행을 기록할 것.

## 남은 것

1. **DB 백업** — postgres 데이터가 EBS 한 장. `pg_dump` → S3 일 1회. 최우선.
2. 시드 데이터 — 새 DB라 계정 없음. 시연용이면 `seed` 프로파일을 EC2에서 한 번 실행하는
   절차 필요.
3. `infra-cd` 첫 실행 검증 (`TERRAFORM_CI_READY=true`, Secrets `AWS_TERRAFORM_*_ROLE_ARN`,
   `TF_STATE_BUCKET`).
4. `demo` 워크스페이스 삭제 (`terraform workspace delete demo`), backend `dynamodb_table` →
   `use_lockfile` 전환.
