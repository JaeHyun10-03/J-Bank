# 2026-08-14 OTP 검증과 지급정지 반영·해제·롤백 (W5 금, 완료 기준)

목표: `todo/W5.md` 금요일분. OTP를 Redis에 3분 만료로 저장·검증하고
실패 횟수를 카운트해 한도 초과 시 거래를 취소한다. 인증 대기 진입 시
지급정지를 반영하고, 검증 성공/실패/만료에 따라 해제·확정·롤백한다.
만료된 대기 거래는 스케줄러가 정리한다.

## 지급정지 반영/해제

`Account`에 `hold`/`release` 메서드를 추가했다. `debit`/`credit`과
같은 자리에 두되 `currentBalanceCache`는 건드리지 않고
`holdAmount`만 증감한다 — 원장은 그대로 두고 출금 가능 금액만 줄이는
FR-AUTH-003 요구 그대로다.

## OtpService

`LoginAttemptService`가 이미 쓰고 있던 Redisson 패턴(RBucket +
RAtomicLong)을 그대로 재사용했다. `issue`는 6자리 코드를 3분 TTL로
저장하고 실패 카운터를 초기화한다. `verify`는 저장된 코드가 없으면
`EXPIRED`, 일치하면 `MATCH`(코드 삭제), 불일치면 실패 카운터를
올리고 한도 도달 여부에 따라 `MISMATCH`/`LIMIT_EXCEEDED`를 반환한다.
실제 SMS 발송은 CTR 배치와 같은 원칙으로 로그 출력으로 대체했다.
실패 한도(기본 5회)는 요구사항명세서에 수치가 없어 로그인 실패
한도와 같은 값을 기본값으로 잡았다.

## TransferService: 지급정지 반영 + OTP 발급

어제 만들어둔 `markPendingOtp()` 분기에 `from.hold(amount)`와
`otpService.issue(...)` 호출을 붙였다. 같은 멱등성 키로 재요청해도
지급정지가 중복 반영되지 않는지도 함께 검증했다(멱등 응답 경로는
새 트랜잭션을 만들지 않고 기존 결과를 그대로 반환하므로 자동으로
안전하다).

이 변경으로 `TransferService` 생성자에 `OtpService` 의존성이
추가됐는데, 이를 `@Import`하는 `@DataJpaTest` 슬라이스 세 곳
(`TransferServiceIntegrationTest`, `TransactionHistoryServiceIntegrationTest`,
`AbstractConcurrencyTest`)에 Testcontainers Redis 기반
`RedissonClient` 빈을 함께 추가해야 했다 — 슬라이스 테스트에는
Redisson 자동설정이 안 붙어서 직접 등록해야 컴파일·기동이 된다.

## 대기 거래 취소 공용 서비스

OTP 검증 실패한도초과·만료 처리와 만료 대기 거래 정리 스케줄러가
같은 취소 로직(거래를 CANCELLED로, 지급정지 해제)이 필요해서
`PendingOtpCancellationService`로 뺐다. 거래·계좌를 `findByIdForUpdate`로
잠가 두 호출자가 같은 거래를 동시에 취소하는 경쟁을 막고, 이미
`PENDING_OTP`가 아니면 조용히 넘어가는 멱등 동작으로 만들었다.

## OTP 검증 처리

`OtpVerificationService`가 API-016의 오케스트레이션을 맡는다. 성공
시 `TransferService.completeAfterOtp`로, 실패한도초과·만료 시
`PendingOtpCancellationService.cancel`로 위임한다. 두 위임 대상 모두
독립 트랜잭션으로 커밋되므로 이 서비스는 트랜잭션을 직접 열지 않고,
상태 변경이 커밋된 뒤에 예외를 던진다 — 그래야 응답 실패가 방금
커밋한 취소를 되돌리지 않는다. `completeAfterOtp`가 즉시 완료
경로와 같은 원장 기록 로직(디버트/크레딧, 원장 2건, 완료 전이,
이벤트 발행)을 쓰도록 `TransferService.transfer`를 먼저
`executeTransfer`로 리팩터링해뒀다.

**한도초과 시 응답 코드**: API설계 문서 표에 `LIMIT_EXCEEDED` 전용
코드가 따로 없어서, 한도를 넘긴 그 요청도 `AUTH_004_OTP_MISMATCH`로
응답하고 부수효과로만 거래를 취소하도록 했다. 이후 재시도는 상태가
더 이상 `PENDING_OTP`가 아니므로 `TXN_005_TRANSACTION_NOT_PENDING`으로
자연스럽게 갈린다 — 화면플로우차트 문서의 분기와 일치한다.

## 만료 대기 거래 정리 스케줄러

Redis의 OTP는 자체 TTL로 사라지지만 거래 자체는 그대로 남기 때문에
별도 정리가 필요하다. `PendingOtpExpirationScheduler`가
`jbank.transfer.otp.cleanup.poll-interval-ms`(기본 1분) 주기로
`created_at`이 만료시간(기본 3분)보다 오래된 `PENDING_OTP` 거래를
찾아 `PendingOtpCancellationService`에 위임한다. 조회 인덱스는 ERD
3절에 미리 정의해둔 부분 인덱스
`(status, created_at) WHERE status = 'PENDING_OTP'`를 그대로 썼다
(V12 마이그레이션).

## 커밋 중간에 바로잡은 것

`OtpVerificationService`를 만들면서 `executeTransfer` 리팩터링을
같은 커밋에 넣었다가, "리팩토링과 기능 구현은 같은 커밋에 넣지
않는다"는 원칙에 걸려 바로 `git reset --soft`로 되돌리고 리팩터
커밋과 기능 커밋으로 다시 나눴다. 되돌리는 과정에서 인덱스에 파일이
남아있는 걸 놓쳐 한 번 더 잘못 커밋했다가 `git restore --staged`로
바로잡았다 — `git add <파일>` 후에는 `git diff --cached --stat`로
실제 스테이징 내용을 확인하는 습관을 들여야겠다.

## 오늘 범위에서 일부러 뺀 것

API-016 컨트롤러 엔드포인트는 손대지 않았다. `OtpVerificationService.verify`는
서비스 레벨에서 완성되어 있고 통합 테스트로 성공/불일치/한도초과/만료/
소유자아님/이미완료 여섯 시나리오를 전부 검증했지만, HTTP로 노출하는
작업은 `todo/W5.md` 토요일분("API-016 2차 인증 검증 구현")으로 남겨뒀다.
