# 2026-08-12 원장 정합성 대사·고액현금거래 판별 배치 (W5 수, 완료 기준)

목표: `todo/W5.md` 수요일분. 원장 정합성 대사 잡과 `CtrReportQueue`
마이그레이션 + 고액현금거래(CTR) 판별 잡을 구현한다.

## 원장 정합성 대사(`batch.reconciliation`)

집계 쿼리로 판정만 하는 잡이라 청크 대신 `Tasklet` 하나로 구성했다.
`LedgerEntryRepository`에 계좌별 CREDIT-DEBIT 합산 쿼리와 전체
차변/대변 합 쿼리를 추가하고, 계좌 캐시 잔액과 비교해 불일치를
`log.warn`으로만 남긴다. 자동 보정을 하지 않는 이유는 구현계획에
적힌 그대로 — 정합성 불일치를 자동으로 고치면 원인을 은폐하게
된다.

테스트에서 "정상 케이스"를 만들다가 이 도메인의 구조적 한계를
하나 확인했다: `accounts` 테이블의 `chk_accounts_hold_amount_range`
체크 제약(`hold_amount <= current_balance_cache`)이 사실상 잔액이
항상 0 이상이어야 함을 강제한다. 그런데 입금/출금은 원장에 한쪽만
기록하는 단건 엔트리라서, 전체 차변 합과 대변 합이 정확히 일치하는
상태에서 모든 계좌 잔액이 양수인 시나리오는 수학적으로 불가능하다
(전액 0일 때만 성립). 그래서 "불일치 없음" 테스트는 원장 엔트리가
아예 없는 잔액 0 계좌로만 구성했다 — 억지로 맞춘 시나리오보다
정직한 케이스다.

## CtrReportQueue + 고액현금거래 판별(`batch.ctr`)

ERD 2.7절 그대로 마이그레이션(V11)과 엔티티를 추가했다. 판별
기준이 "동일인 명의" 합산인데 테이블은 `account_id`가 NOT NULL이라,
고객 단위로 기준 초과 여부를 판정한 뒤 그 고객의 계좌별 당일
현금합계를 각각 한 행씩 적재하는 방식으로 풀었다. 재실행 안전은
`(customer_id, account_id, transaction_date)` 유니크 인덱스로 DB
레벨에서 막았다 — 이자 계산 잡처럼 JobInstance 파라미터에만
의존하지 않는다.

임계 금액(`jbank.batch.ctr.threshold-amount`, 기본 1천만 원)은
이자 계산 잡의 반올림 규칙과 같은 패턴으로 설정값으로 뺐다.

## 부수적으로 고친 것

원장 정합성 대사 잡을 추가하면서 애플리케이션 컨텍스트에 `Job`
빈이 두 개가 됐고, 기존 `InterestMaturityJobIntegrationTest`가
`JobLauncherTestUtils`의 잡 자동 주입 실패로 깨졌다("The Job must
not be null"). `@Qualifier`로 잡을 명시 주입해 `@BeforeEach`에서
지정하도록 고쳤다(별도 fix 커밋). 이후 추가한 두 배치 잡 테스트도
같은 패턴을 따른다.

## 검증

로컬 Docker로 전체 스위트 실행, 178개 테스트 전부 통과. 커밋은
기능 구현/테스트/마이그레이션을 분리해 6개로 나눴다(reconciliation
구현 → 잡 다중등록 fix → reconciliation 테스트 → CtrReportQueue
마이그레이션 → CTR 판별 구현 → CTR 테스트).
