## 1. 문서 개요

이 문서는 프론트엔드 구현에 들어가기 전 기술스택을 확정하는 문서다. 화면플로우차트.md에서 정의한 화면 구조와 API설계.md에서 정의한 요청/응답 계약을 그대로 구현으로 옮기는 것을 목표로 하며, 백엔드 인프라아키텍처.md와도 배포 전략 수준에서 정합성을 맞춘다.

선정 기준은 세 가지다. 첫째, API설계.md의 공통 규칙(인증 쿠키, Idempotency-Key, 위조 방지 토큰, 표준 에러 포맷)을 프론트엔드 레이어에서 반복 구현하지 않고 한 곳에서 처리할 수 있는 구조인가. 둘째, 타입 안전성을 확보해 화면과 API 계약 사이의 불일치를 컴파일 시점에 잡을 수 있는가. 셋째, 금융 서비스 특성상 인증 토큰 노출이나 스크립트 주입 같은 클라이언트 사이드 보안 사고를 구조적으로 줄일 수 있는가.

## 2. 핵심 프레임워크

React 18과 Next.js 14의 App Router, TypeScript 조합을 기본으로 한다.

Next.js를 선택한 이유는 파일 기반 라우팅이 화면플로우차트.md의 화면 구조와 자연스럽게 대응되기 때문이다. 예를 들어 계좌상세 화면과 그 하위의 입금, 출금, 이체 화면은 `app/accounts/[accountId]/deposit`, `app/accounts/[accountId]/withdraw`, `app/accounts/[accountId]/transfer` 같은 디렉터리 구조로 그대로 옮길 수 있다. 라우트 구조와 설계 문서의 화면 트리가 어긋나지 않게 유지하기 쉽다는 점이 실무에서도, 포트폴리오 설명에서도 유리하다.

TypeScript는 필수로 둔다. API설계.md의 요청/응답 스키마를 타입으로 정의해두면, 화면 구현 중에 필드명이 틀리거나 타입이 어긋나는 실수를 빌드 시점에 잡을 수 있다. 6절에서 다루는 명세 기반 타입 자동 생성과 함께 쓰면 효과가 커진다.

## 3. 상태 관리

서버에서 내려오는 데이터와 클라이언트에서만 존재하는 상태를 구분해서 관리한다.

계좌 목록, 잔액, 거래내역, 상품 목록처럼 서버가 소유한 데이터는 TanStack Query로 관리한다. 요청 결과를 캐싱하고, 이체나 입출금처럼 데이터를 변경하는 요청 이후에는 관련 쿼리를 무효화해 최신 잔액을 다시 가져오도록 구성한다. 이렇게 하면 컴포넌트마다 로딩/에러 상태를 직접 관리할 필요가 없고, API설계.md의 공통 응답 포맷과도 자연스럽게 맞물린다.

2차 인증 대기 중인 이체가 있으면 잔액은 그대로인데 출금 가능 금액만 줄어든다. 이 상태에서 잔액 쿼리를 무효화하지 않으면 화면이 낡은 출금 가능 금액을 보여주므로, 인증 대기 응답을 받은 시점과 인증 완료 시점 양쪽에서 계좌 관련 쿼리를 무효화한다.

로그인 여부, 사용자 표시 정보, 진행 중인 이체의 임시 상태처럼 서버가 소유하지 않는 클라이언트 전용 상태는 Zustand로 관리한다. Redux Toolkit도 후보였지만, 이 프로젝트 규모에서는 보일러플레이트 대비 얻는 이점이 적어 Zustand로 정했다. 다만 실무에서 Redux를 쓰는 조직이 많다는 점은 인지하고 있어야 한다.

## 4. 폼과 검증

React Hook Form과 Zod 조합을 사용한다. Zod로 각 화면의 입력 스키마를 정의하면, API설계.md에 정의된 필드별 제약(금액 형식, 계좌번호 형식, 필수값 여부)을 그대로 프론트엔드 검증 규칙으로 옮길 수 있다.

서버가 반환하는 도메인 에러코드(`TXN_001` 같은)는 Zod 검증을 통과한 뒤에도 발생할 수 있다. 예를 들어 출금 가능 금액 초과는 클라이언트가 사전에 알 수 없는 값이므로 서버 응답을 받은 뒤에만 판단 가능하다. 이런 에러는 폼 필드 단위 에러로 변환해 사용자에게 보여주는 매핑 레이어를 따로 둔다. API설계.md의 에러코드 표를 기준으로 코드별 처리 방식을 상수로 관리하면, 새 에러코드가 추가될 때마다 해당 파일 하나만 수정하면 된다.

## 5. 스타일링과 컴포넌트

Tailwind CSS와 shadcn/ui 조합을 사용한다. shadcn/ui는 컴포넌트 코드를 프로젝트에 직접 복사해오는 방식이라 커스터마이징이 자유롭고, 접근성 기본기(키보드 포커스, ARIA 속성)가 이미 갖춰져 있어 금융 서비스에 요구되는 접근성 수준을 맞추기 수월하다.

금액, 계좌번호, 날짜처럼 반복되는 표시 형식은 공통 포맷팅 유틸리티로 분리한다. 금액은 API설계.md 2.6절에 따라 서버가 문자열로 내려주므로, 화면에서는 이 문자열을 천단위 구분 쉼표가 포함된 표시용 문자열로 변환하는 순수 함수만 두고 부동소수점 연산은 어디에서도 하지 않는다.

금액 표시에는 한 가지 규칙을 더 둔다. 계좌 관련 화면은 잔액과 출금 가능 금액을 구분해 보여준다. 두 값은 2차 인증 대기 중인 이체가 있을 때만 달라지는데, 그 상황에서 잔액만 표시하면 사용자가 출금 거절 사유를 이해할 수 없다. 두 값이 같을 때는 출금 가능 금액을 따로 노출하지 않고, 다를 때만 지급정지된 금액과 함께 안내한다. 이 판단 로직도 포맷팅 유틸리티와 같은 위치에 둔다.

## 6. API 연동 레이어

Axios 인스턴스를 하나 두고, 요청과 응답 인터셉터에서 API설계.md의 공통 규칙을 전부 처리한다.

요청 인터셉터가 하는 일은 두 가지다. 첫째, 입금/출금/이체처럼 Idempotency-Key가 필요한 요청에는 헤더가 비어 있을 때만 UUID를 생성해 채운다. 둘째, 상태를 바꾸는 요청에는 `XSRF-TOKEN` 쿠키에서 값을 읽어 `X-CSRF-TOKEN` 헤더에 복사한다.

인증 토큰을 헤더에 싣는 처리는 하지 않는다. 인증 쿠키는 브라우저가 자동으로 실어 보내고, 그 값은 스크립트가 읽을 수 없다. 인스턴스 설정에서 자격 증명 전송을 켜두는 것으로 충분하다.

응답 인터셉터는 401 응답을 가로채 API-014 토큰 재발급을 시도하고, 성공하면 원래 요청을 한 번만 재시도한다. 재발급까지 실패하면 로그인 화면으로 리다이렉트한다. 재발급 요청도 위조 방지 토큰을 요구하므로, 재발급 성공 응답에서 교체된 새 토큰을 다음 요청부터 쓰도록 쿠키에서 다시 읽는다. 이 로직을 인터셉터에 모아두면 화면 컴포넌트는 인증 만료를 신경 쓸 필요가 없어진다.

동시에 여러 요청이 401을 받는 경우를 처리해야 한다. 각 요청이 독립적으로 재발급을 시도하면 갱신 토큰 로테이션 때문에 두 번째 요청 이후가 이미 사용된 토큰을 제출하게 되고, 서버가 이를 탈취로 판단해 토큰 계열 전체를 폐기한다. 정상 사용자가 강제 로그아웃되는 사고다. 재발급 요청을 하나로 합치고 나머지 요청은 그 결과를 기다리도록 큐에 넣는 처리를 반드시 넣는다.

API 타입은 수작업으로 옮기지 않고 자동 생성한다. 백엔드가 Springdoc으로 명세를 노출하고 그것을 저장소에 스냅샷으로 커밋하므로(API설계.md 10절), `openapi-typescript`로 요청/응답 타입을 생성해 프론트엔드 코드에서 그대로 임포트한다. 생성 결과도 커밋하고 검증 파이프라인이 재생성 결과와의 동일성을 확인해, 백엔드 계약이 바뀌면 프론트엔드 빌드가 깨지도록 만든다. 이렇게 하면 API설계.md, 백엔드 코드, 프론트엔드 타입 세 곳이 항상 같은 계약을 공유하게 된다.

## 7. 인증 토큰 처리 전략

인증 토큰과 갱신 토큰 모두 httpOnly, Secure, SameSite=Lax 속성의 쿠키로 관리한다. 두 쿠키는 자바스크립트가 아니라 백엔드가 로그인과 토큰 재발급 응답 시점에 `Set-Cookie` 헤더로 직접 내려준다. 이 방식은 API설계.md 2.2절에 확정 반영되어 있다.

v1.2까지는 API설계 문서가 토큰을 응답 본문에 JSON으로 내려주도록 되어 있어 이 문서와 어긋난 상태였고, 그 사실을 여기에 미해결로 남겨두었다. API설계 v1.1에서 세 쿠키 발급 방식으로 개정되어 불일치가 해소되었으므로 이 절도 확정 서술로 바꾼다.

발급되는 쿠키는 세 종류다.

| 쿠키 | 수명 | 스크립트 접근 | 용도 |
|---|---|---|---|
| `access_token` | 15분 | 차단 | 요청 인증 |
| `refresh_token` | 14일 | 차단 | 인증 쿠키 재발급 |
| `XSRF-TOKEN` | 14일 | 허용 | 위조 방지 토큰, 헤더로 복사 |

초기 버전에서는 인증 토큰을 메모리에만 두는 방식을 검토했으나, 두 가지 이유로 폐기했다. 첫째, 스크립트 주입이 성공하면 페이지와 같은 실행 컨텍스트에서 코드가 돌기 때문에 메모리에 있는 값도 그대로 읽힌다. httpOnly 쿠키는 브라우저가 `document.cookie` 접근 자체를 차단하므로, 이 기준에서는 메모리 보관보다 오히려 httpOnly 쿠키가 더 안전하다. 둘째, 인증 토큰이 메모리에만 있으면 새로고침 시점에 서버가 렌더링을 시작할 때 그 값에 접근할 방법이 없어, 서버 사이드 렌더링이나 미들웨어 기반 접근 제어와 근본적으로 맞지 않는다.

쿠키 기반으로 전환하면서 새로 관리해야 하는 위험은 요청 위조다. 쿠키는 브라우저가 요청마다 자동으로 실어 보내므로, 다른 사이트가 사용자 브라우저를 통해 상태를 변경하는 요청을 몰래 보낼 수 있다. `SameSite=Lax` 설정으로 대부분의 교차 사이트 요청을 막고, 상태를 바꾸는 요청에는 `XSRF-TOKEN` 쿠키 값을 `X-CSRF-TOKEN` 헤더로 함께 제출해 서버가 두 값의 일치를 검증하는 이중 방어를 둔다.

이 방식이 유효한 이유는 공격자가 쿠키를 요청에 실리게 만들 수는 있어도 그 값을 읽을 수는 없다는 점에 있다. 다른 사이트의 스크립트는 브라우저의 출처 정책 때문에 우리 도메인의 쿠키를 읽지 못하므로 헤더에 올바른 값을 채울 수 없다. 프론트엔드가 할 일은 쿠키에서 값을 읽어 헤더로 복사하는 것뿐이고, 그 처리는 6절의 요청 인터셉터 한 곳에 둔다.

## 8. 라우팅과 화면 구조 매핑

화면플로우차트.md의 화면을 App Router 디렉터리로 옮기면 다음과 같다.

| 화면 | 라우트 |
|---|---|
| 로그인 | `/login` |
| 회원가입 - 정보입력 | `/signup` |
| 강화된 고객확인 입력 | `/signup/edd` |
| 계좌개설 | `/accounts/new` |
| 홈 - 계좌목록 | `/` |
| 계좌상세 | `/accounts/[accountId]` |
| 거래내역 조회 | `/accounts/[accountId]/transactions` |
| 입금 | `/accounts/[accountId]/deposit` |
| 출금 | `/accounts/[accountId]/withdraw` |
| 이체 - 입력/확인 | `/accounts/[accountId]/transfer` |
| OTP 검증 | `/transfers/[transactionId]/otp` |
| 상품목록 | `/products` |
| 상품상세 | `/products/[productCode]` |
| 상품가입 신청 | `/products/[productCode]/subscribe` |
| 내 가입상품 | `/contracts` |

여기에 화면이 아닌 경로 하나가 더 있다. 10절의 프록시용 라우트 핸들러가 `/api/proxy/[...path]`에 위치한다.

로그인 여부에 따른 접근 제어는 Next.js 미들웨어에서 처리한다. 인증 쿠키가 브라우저에 있으므로 미들웨어가 매 요청마다 쿠키 존재 여부와 만료 여부를 직접 확인할 수 있고, 만료된 경우 미들웨어 단계에서 재발급을 시도한 뒤 요청을 이어가거나 로그인 화면으로 리다이렉트한다.

## 9. 테스트 전략

컴포넌트 단위 테스트는 Jest와 React Testing Library로 작성한다. 폼 검증 로직과 금액 포맷팅 유틸리티처럼 로직이 있는 부분을 우선순위로 둔다. 잔액과 출금 가능 금액의 표시 분기 로직도 여기에 포함한다.

E2E 테스트는 Playwright로 작성하고, 화면플로우차트.md에 그린 7개 흐름을 그대로 테스트 시나리오로 옮긴다. 특히 이체 플로우는 임계금액 이하/초과 두 경로, OTP 불일치/만료 두 실패 케이스까지 포함해 시나리오를 짠다. 이 매핑 덕분에 설계 문서가 그대로 테스트 커버리지 체크리스트 역할도 하게 된다.

## 10. 배포 전략

7절에서 인증을 미들웨어 기반 쿠키 검증으로 확정하면서 Node.js 런타임이 필요해졌지만, 이 런타임을 백엔드와 같은 AWS 인프라 안에 둘 필요는 없다. 프론트엔드는 Vercel에, 백엔드 API 서버와 DB, 캐시, 메시지큐는 그대로 AWS에 두는 분리 배포로 정한다. Vercel은 Next.js를 만든 회사가 직접 운영하는 플랫폼이라 미들웨어, 서버 컴포넌트 같은 기능이 별도 설정 없이 그대로 동작하고, EKS에 프론트엔드 워크로드를 얹고 오토스케일링과 배포 파이프라인을 새로 구성하는 수고를 덜 수 있다.

프론트엔드와 백엔드가 서로 다른 도메인에 놓이는 구조이므로, 쿠키가 브라우저 기준으로 크로스 사이트 취급을 받지 않도록 설계에 신경 써야 한다. 방법은 두 가지다. 하나는 프론트엔드 도메인 안에 API 프록시용 라우트 핸들러를 두어, 브라우저는 항상 프론트엔드 도메인으로만 요청하고 그 요청을 서버 쪽에서 AWS API로 그대로 전달하는 방식이다. 이렇게 하면 브라우저 입장에서는 모든 요청이 같은 출처이므로 쿠키도 same-site로 동작하고 CORS 설정 자체가 필요 없다. 다른 하나는 프론트엔드와 백엔드를 한 상위 도메인의 서로 다른 서브도메인으로 두고, 쿠키의 Domain 속성을 상위 도메인으로 지정해 두 서브도메인이 쿠키를 공유하게 하는 방식이다. 두 방식 다 실무에서 쓰이지만, 프록시 방식이 CORS와 SameSite 설정을 아예 신경 쓸 필요가 없어 더 단순하므로 이쪽을 기본으로 삼는다.

프록시가 지켜야 할 규칙이 하나 있다. 백엔드가 내려준 `Set-Cookie` 헤더를 그대로 흘려보내면 안 된다. 헤더에 백엔드 도메인이 들어 있으면 브라우저가 다른 사이트의 쿠키로 판단해 저장하지 않으므로, 프록시가 `Domain` 속성을 제거하고 `Path`를 `/`로 정규화해서 다시 내려줘야 한다. 이 처리를 빼먹으면 로그인 응답은 200인데 다음 요청이 인증 실패로 돌아오는 증상이 나타나고, 쿠키가 저장되지 않은 것이 원인이라는 것을 알아채기 어렵다. 반대 방향으로는 브라우저가 보낸 쿠키를 백엔드로 그대로 전달한다.

저장소는 백엔드와 하나로 두므로 Vercel 프로젝트의 루트 디렉터리를 `apps/frontend`로 지정한다. 프론트엔드 경로에 변경이 없는 커밋에서는 빌드를 건너뛰도록 무시 조건도 함께 설정한다.

다만 이 선택은 인프라아키텍처.md 13절에 정리한 것처럼, 실제 은행이라면 프론트엔드도 국내 리전의 승인된 인프라에 둬야 한다는 원칙에서 벗어난 지점이다. 프론트엔드는 원장이나 개인정보를 저장하지 않는 프레젠테이션 계층이라 그 원칙의 실익이 낮다고 보고 내린 결정이며, 원장 데이터와 개인정보를 다루는 모든 컴포넌트는 여전히 AWS 안에 있다는 경계를 명확히 유지한다.

프록시가 요청을 중계한다는 점 때문에 개인정보가 Vercel을 경유하기는 한다. 다만 경유는 저장 없이 전달만 하는 것이고, 이 경계를 유지하기 위해 프록시 라우트 핸들러에서는 요청과 응답 본문을 로그로 남기지 않는다.

## 11. 접근성

금융 서비스는 폭넓은 연령대와 신체 조건의 사용자가 이용하므로, 최소한 WCAG 2.1 AA 수준을 목표로 한다. shadcn/ui의 기본 접근성 기능에 더해, 금액이나 계좌번호처럼 오입력 시 금전적 손실로 이어지는 입력 필드는 스크린리더 사용자를 위한 명확한 레이블과 오류 안내를 별도로 검증한다.
