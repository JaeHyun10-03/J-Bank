# ADR 0012: 이체 입금을 수신 계좌별로 모아 비동기 반영

## 상태

승인됨. 2026-09-30.

## 배경

운영 사양(t3.small) EC2 부하 테스트에서 한 계좌로 이체가 몰리면 초당 80~100건에서 무너졌다(`perf/results/ec2-hot-account/`).
CPU는 44~66%로 여유였고, 원인은 이체가 받는 계좌 행을 `PESSIMISTIC_WRITE`로 잠그는 구조였다. 모든 이체가 그 한 행에서 줄을 서는 동안
커넥션을 붙잡아 풀(10개)이 고갈되고, 핫 계좌와 무관한 잔액 조회 p95까지 8ms에서 1,397ms로 늘었다.

## 결정

이체는 보내는 계좌만 바꾸고, 받는 쪽은 "입금 대기"로 남긴다. 반영 워커가 받는 계좌별로 대기분을 모아 한 번에 반영한다.
은행의 가상계좌 집금(입금은 따로 쌓고 모계좌에 모아 반영)이나 은행 간 차액결제(건마다가 아니라 모아서 정산)와 같은 구조다.

| 단계 | 처리 |
| --- | --- |
| 이체 | 송금 계좌 `FOR NO KEY UPDATE`, 수신 계좌 `FOR KEY SHARE`(존재·상태 확인만). 송금 차감·차변 원장·입금 대기(`pending_credits`) 1건·`COMPLETED`를 한 트랜잭션에 쓴다 |
| 반영 | 워커(200ms 주기)가 미반영 대기가 있는 계좌마다 새 트랜잭션에서 계좌를 `FOR NO KEY UPDATE`로 잠그고, 대기를 `FOR UPDATE SKIP LOCKED`로 최대 500건 가져와 잔액을 늘리고 거래마다 대변 원장 1건(누적 스냅샷)을 쓴다 |
| 해지·상태 변경 | 계좌를 처음부터 `FOR UPDATE`로 읽는다. 반영 대기나 이 계좌로 들어올 OTP 인증 대기 이체가 있으면 해지를 `ACC_012`로 거절한다 |
| 조회 | 반영 전 입금은 받는 사람의 잔액·출금 가능 금액·거래내역에 보이지 않는다. 반영 뒤 원래 거래 시각 위치에 나타난다 |
| 대사 | 계좌별 원장 합 = 잔액 캐시, 전체 차변 = 대변 + 미반영 입금. REPEATABLE READ 한 트랜잭션에서 계산하고 1분 넘은 미반영은 경고 |

락 모드가 핵심이다. PostgreSQL에서 `KEY SHARE`는 `NO KEY UPDATE`와 충돌하지 않고 `FOR UPDATE`와만 충돌한다. 그래서 핫 계좌로 가는
이체는 워커 반영이나 다른 이체의 잔액 갱신과 줄 서지 않고, 해지와는 순서가 정해져 해지된 계좌에 입금이 남지 않는다. JPA
`PESSIMISTIC_WRITE`(입금·출금·이자 경로)는 이 버전 Hibernate가 PostgreSQL에서 `FOR NO KEY UPDATE`로 만든다(`KEY SHARE`를 쥔 행에
대기 32ms로 확인, 2026-09-30).

## 검토한 대안

- **원장은 즉시 둘 다 기록하고 잔액만 비동기**: 차변 = 대변은 항상 유지되지만, 대변 원장의 반영 후 잔액 스냅샷을 이체 시점에 알 수 없어
  원장 규칙을 깨야 한다. 은행 계정계도 잔액을 기준 데이터로 거래와 함께 갱신하는 게 일반적이다.
- **핫 계좌를 하위 버킷으로 분산**: 즉시 반영을 유지하지만 경합을 1/N로 줄일 뿐이고 잔액이 버킷 합이라 조회·출금이 복잡해진다.

## 결과와 한계

- 측정 결과(`perf/results/ec2-async-credit/summary.md`, 기준선과 같은 s2f 조건 6회): 같은 부하에서 이체 p95가 90건/초 238 → 35ms,
  100건/초 395 → 33ms, 핫 계좌와 무관한 잔액 조회 p95가 100건/초 307 → 15ms로 줄었고 110건/초 전까지 커넥션 대기가 사라졌다.
  무너짐 판정 중앙값 95 → 115, 최대 처리 TPS 중앙값 103.8 → 115.1(최대 205). 무너질 때 무관한 조회로 번지는 것은 6/6으로 그대로다.
  병목은 행 락에서 CPU로 옮겨 갔고, 판정값은 일시 정지로 흔들린다(t3 CPU steal과 상관만 관측).
- 반영 지연 목표는 처음에 "무너지기 전 모든 단계 p95 1초 이내"였고, r5가 160 단계 2,046ms·180 단계 1,271ms로 넘었다. 측정 뒤(2026-10-01)
  판정 범위를 기준선이 무너진 최대 요청률 바로 위인 초당 150건 이하로 좁혔고, 이 범위에서는 6회 모두 p95 220~404ms다.
  과부하로 무너진 단계에서는 반영이 수십 초까지 밀린다(r4 130 단계 54초).
- 송금자는 즉시 `COMPLETED`를 받는다. 입금 대기는 송금과 같은 트랜잭션이라 유실되지 않는다.
- 받는 사람에게는 반영 지연(목표 1초 이내)만큼 늦게 보인다. 보이는 잔액이 0이어도 반영 대기·OTP 대기 입금 때문에 해지가 `ACC_012`로
  잠깐 거절될 수 있다.
- 반영 시 수신 계좌 상태는 다시 보지 않는다. 이체 시점에 정상이었다면 그 뒤 정지·휴면이 돼도 입금은 반영한다.
- 영구 실패 계좌(예: 제약 위반)는 돈을 버릴 수 없으므로 워커가 계속 재시도한다. 오류 로그는 1분 1회로 억제하고 대사 경고로 드러낸다.
  무한 재처리 없음(BE-07)과는 "처리를 포기하지 않되 로그·부하를 제한한다"로 절충했다.
- 워커는 운영 api에서만 켠다(`jbank.transfer.credit-worker.enabled`, 코드 기본값 false, batch 프로파일 false). 배치 JVM이 대사와 동시에
  잔액을 바꾸지 않게 하기 위해서다.
- 반영 워커의 알려진 한계(이번 범위에서 고치지 않음): 해지 계좌 방어 경로(오면 안 되는 경로)는 로그 억제 없이 주기마다 오류를 남긴다.
  계좌 행 락에 대기 시간 제한이 없어 한 계좌가 오래 잠기면 워커 전체가 멈추고, 그동안 미반영 수·나이 지표도 갱신되지 않는다.
  미반영 계좌를 고르는 순서가 없어 계속 100개를 넘으면 일부 계좌가 늦어질 수 있다. 반영 지연 Timer 히스토그램은 30초가 상한이라
  그 이상은 max로만 보인다.
- 롤백: 이전 이미지에는 워커가 없다. 롤백하려면 트래픽을 멈추고 미반영 입금이 0인지 확인한 뒤 배포하거나, 전진 복구만 한다.
- 이번 변경으로, 해지·상태 변경이 락 없이 읽은 옛 잔액으로 전체 컬럼을 덮어써 동시에 반영된 입금을 없앨 수 있던 기존 문제도 고쳤다.
