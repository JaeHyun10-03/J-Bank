# J-Bank 코어시스템 요구사항 명세서

문서 버전: v1.7
작성일: 2026-07-21
최종 수정: 2026-07-27

## 1. 문서 개요

### 1.1 목적
본 문서는 J-Bank 코어시스템의 기능적·비기능적 요구사항을 정의한다. 계좌 개설부터 입출금, 계좌이체까지 이어지는 핵심 금융 도메인 로직을 명확히 규정하여, 개발 범위와 우선순위에 대한 판단 기준으로 삼는다.

### 1.2 범위
실제 대외 금융망과 연동하지 않는 폐쇄형 시스템으로, 개인 고객과 계좌 관리(고객확인제도 포함), 복식부기 원장을 기반으로 한 입출금 및 이체, 예적금 상품, 인증과 보안, 감사로그 및 알림, 규제 준수 관련 기능을 포함한다. 법인/단체 고객은 범위에서 제외한다. Phase 3에서는 마이크로서비스 아키텍처 전환 및 이상거래 탐지 기능까지 확대한다.

### 1.3 용어 정의
- 원장: 모든 금전 거래를 차변과 대변의 쌍으로 기록하는 회계 장부. 계좌 잔액은 원장 엔트리의 합으로 계산한다.
- 복식부기: 하나의 거래가 차변과 대변 두 개의 원장 엔트리를 동시에 발생시켜 금액의 총합이 항상 0이 되도록 하는 회계 원칙.
- 멱등성: 동일한 요청이 여러 번 전달되어도 결과가 한 번만 반영되도록 보장하는 성질.
- CIF: 고객 한 명당 하나씩 만들어지는 통합 고객정보 파일. 계좌는 CIF에 1대다로 연결된다.
- CDD: 고객확인제도. 계좌 신규개설, 일정 기준금액 이상 일회성 금융거래 시 고객의 신원을 확인하는 절차.
- EDD: 강화된 고객확인. 고위험 고객을 대상으로 거래목적과 자금원천까지 추가로 확인하는 절차.
- CTR: 고액현금거래보고제도. 동일인 명의로 1거래일 동안 1천만원 이상 현금이 입출금된 경우 금융정보분석원에 보고하는 제도.
- 지급정지 금액: 2차 인증 대기 중인 이체 금액처럼, 잔액에는 남아 있으나 다른 거래에 사용할 수 없도록 묶어둔 금액.
- 출금 가능 금액: 잔액에서 지급정지 금액을 뺀 값. 출금과 이체의 검증 기준이 되는 금액이다.
- 발신함: 이벤트를 메시지 브로커로 직접 발행하지 않고, 원본 거래와 같은 트랜잭션에서 데이터베이스에 먼저 적재한 뒤 별도 발행기가 읽어 보내도록 하는 중간 저장 테이블.
- MoSCoW: 요구사항 우선순위 분류 기법. Must는 필수, Should는 권장, Could는 선택, Won't는 제외.

## 2. 시스템 개요

### 2.1 시스템 목표
트랜잭션 정합성, 동시성 제어, 멱등성 처리, 이벤트 기반 아키텍처, 배포 운영 자동화, 실제 금융 규제 준수를 하나의 코어뱅킹 도메인 안에서 구현하는 것을 목표로 한다.

### 2.2 대상 사용자
| 구분 | 설명 |
|---|---|
| 고객 | 계좌 개설, 입출금, 이체, 상품 가입 등을 수행하는 개인 최종 사용자 |
| 운영자 | 계좌 상태 관리, 이상거래 모니터링, 배치 실행 결과를 확인하는 내부 운영자 |
| 외부 시스템(향후) | Phase 3 확장 시 오픈뱅킹, 알림 채널 등과 연동되는 외부 시스템 |

### 2.3 단계별 개발 범위
| Phase | 핵심 목표 | 포함 범위 |
|---|---|---|
| Phase 1 | 코어 도메인 확립 | 고객/계좌 관리, 고객확인(CDD), 입출금·이체 API, 복식부기 원장, 동시성 제어, 멱등성, JWT 인증 |
| Phase 2 | 이벤트 기반 확장 | 강화된 고객확인(EDD), 거래내역 고도화, 감사로그, 발신함 기반 Kafka 이벤트 알림, 예적금 상품 및 이자 배치, 2차 인증 |
| Phase 3 | MSA 및 운영 고도화 | 서비스 분리, Saga 오케스트레이션, 이상거래 탐지, 고액현금거래 보고대상 판별, 부하테스트/모니터링, IaC |

### 3.1 계좌 관리

**FR-ACC-001 고객 등록 및 고객확인(CDD)**
- 설명: 신규 개인 고객의 개인정보를 등록하고 고유 고객ID를 발급하며, 특정금융거래정보법상 고객확인제도(CDD)를 함께 수행한다. 계좌 신규개설은 법령상 CDD 의무 발생 사유이므로 고객 등록과 최초 계좌 개설은 하나의 흐름으로 처리한다.
- 입력: 고객명, 실명번호(마스킹 대상), 생년월일, 연락처, 주소, 직업정보, 실명확인방법(대면/비대면)
- 처리 절차: 실지명의 형식 유효성 검증 → 동일 실명번호 기존 CIF 존재 여부 조회, 있으면 기존 CIF 재사용 → 실명확인 서비스 연동으로 성명/실명번호/주소 일치 여부 확인 → 실제소유자 확인(개인 고객이므로 본인을 실제소유자로 간주) → 국적/직업/거래목적/예상거래규모를 반영한 위험기반 평가로 AML 위험도(저/중/고)와 KYC등급 산정 → 고위험이면 FR-ACC-006(EDD)으로 분기 → 고객 마스터 저장 → 고객ID 채번 후 반환
- 출력: 고객ID, KYC등급, AML위험도, 등록 완료 메시지 / Must, Phase 1

**FR-ACC-002 계좌 개설**
- 설명: 등록된 고객이 신규 입출금 계좌를 개설한다. 계좌 신규개설은 CDD 의무 발생 사유이므로, FR-ACC-001의 고객확인 절차를 통과한 고객만 계좌를 개설할 수 있다.
- 처리 절차: 고객 상태 및 CDD 완료 여부 확인(미완료 시 거절), 계좌번호 채번, 계좌 마스터 생성, 초기 입금액이 있으면 최초 원장 엔트리 생성 / Must, Phase 1

**FR-ACC-003 계좌 상태 관리** — 계좌 상태를 상태 머신 규칙에 따라 변경하고 상태별 거래 제한을 적용. / Must, Phase 1

**FR-ACC-004 계좌 해지** — 잔액 0원과 지급정지 금액 0원을 확인한 후 계좌 상태를 해지로 변경하고 이후 거래 요청을 차단한다. 잔액이 0원이어도 지급정지 금액이 남아 있으면 2차 인증 대기 중인 거래가 존재한다는 뜻이므로 해지를 거절한다. / Must, Phase 1

**FR-ACC-005 계좌 조회(단건/목록)** — 소유자 검증 후 계좌 목록과 최신 잔액, 출금 가능 금액을 병합해 조회. / Must, Phase 1

**FR-ACC-006 강화된 고객확인(EDD)**
- 설명: FR-ACC-001에서 AML 위험도가 고위험으로 분류된 고객을 대상으로, 기본 고객확인 항목에 더해 거래목적과 자금원천을 추가로 확인한다. 정치적 주요인물, 비거주자, 위험국가 관련 고객 등이 적용 대상이다.
- 처리 절차: 고위험 분류 사유 확인 → 거래목적 및 자금원천 입력 요구 → 미입력 또는 소명 불충분 시 계좌 개설 보류 또는 거래 제한 → 확인 결과를 고객 마스터에 반영
- 출력: EDD 완료 여부, 갱신된 AML 위험도 / Should, Phase 2

### 3.2 거래 및 원장 관리 — 핵심 모듈

**FR-TXN-001 입금 처리** — 계좌 상태 검증, 대변 원장 엔트리 생성, 거래 이력 저장. / Must, Phase 1

**FR-TXN-002 출금 처리**
- 설명: 계좌에서 금액을 출금하고 차변 원장 엔트리를 생성한다.
- 처리 절차: Idempotency-Key 중복 확인 → 비관적 락으로 계좌 로우 획득 → 계좌 상태 검증 → 출금 가능 금액 검증 → 차변 원장 엔트리 생성 → 잔액 캐시 갱신 → 거래 이력 저장. 락 획득부터 거래 이력 저장까지 단일 DB 트랜잭션으로 커밋한다.
- 출금 가능 금액의 정의: 검증 기준은 잔액이 아니라 출금 가능 금액이며, 다음과 같이 계산한다.

  ```
  출금 가능 금액 = 잔액 - 지급정지 금액
  ```

  지급정지 금액은 FR-AUTH-003의 2차 인증 대기 중인 이체 금액의 합이다. 대기 중인 금액을 잔액에서 빼지 않으면 같은 잔액으로 여러 건의 대기 거래를 만들 수 있어 잔액을 초과한 출금이 발생하고, 반대로 잔액을 실제로 차감하면 원장에 기록되지 않은 금액이 잔액에서 사라져 원장 합산과 어긋난다. 두 값을 분리해 관리하는 것이 이 문제의 해법이다.

  출금 가능 금액은 별도로 저장하지 않고 항상 파생 계산한다. 저장하는 값을 늘리면 서로 어긋날 수 있는 조합이 늘어난다.
- 출금 가능 금액을 초과하는 요청은 거절하고, 거절 사유를 잔액 부족과 구분되지 않는 하나의 에러로 반환한다. / Must, Phase 1

**FR-TXN-003 계좌이체 처리, 핵심 기능**
- 처리 절차: Idempotency-Key 중복 확인 → 두 계좌번호를 오름차순 정렬 후 순서대로 락 획득해 교착상태 방지 → 양쪽 계좌 상태 검증 → 출금계좌의 출금 가능 금액 검증 → 임계금액 초과 여부 판별 → 임계금액 이하면 출금계좌 차변과 입금계좌 대변 엔트리를 단일 DB 트랜잭션으로 커밋해 복식부기 보장, 초과하면 FR-AUTH-003으로 분기 → 거래 이력 저장 → Phase 2부터 같은 트랜잭션에서 발신함에 이체완료 이벤트를 적재 / Must, Phase 1에서 동기 처리 후 Phase 2~3에서 이벤트와 Saga로 확장

**FR-TXN-004 잔액 조회** — 원장 엔트리 합산을 정합성의 근거로 삼고, 조회 응답은 계좌의 잔액 캐시에서 읽는다. 응답에는 잔액과 지급정지 금액, 출금 가능 금액을 함께 포함한다. / Must, Phase 1

**FR-TXN-005 거래내역 조회** — 기간/유형 조건에 따른 거래내역 페이징 조회. / Must, Phase 1

**FR-TXN-006 원장 정합성 검증 배치** — 원장 엔트리 합계와 잔액 스냅샷 일치 여부를 배치로 검증한다. 불일치를 발견하면 자동으로 보정하지 않고 리포트만 남긴다. 자동 보정은 원인을 은폐하는 행위이기 때문이다. / Should, Phase 2

**FR-PRD-003 만기 처리** / Could, Phase 2~3

### 3.4 인증 및 보안

**FR-AUTH-001 로그인 및 토큰 발급** — bcrypt 해시 검증 후 인증 토큰과 갱신 토큰을 발급한다. 두 토큰은 모두 스크립트가 읽을 수 없는 쿠키로 내려주고, 클라이언트가 토큰 값을 직접 다루지 않게 한다. 쿠키 기반 인증에서 발생하는 요청 위조 위험은 별도 위조 방지 토큰 검증으로 방어한다. / Must, Phase 1

**FR-AUTH-002 권한 검증(계좌 소유자 확인)** / Must, Phase 1

**FR-AUTH-003 고액 이체 추가 인증(2차 인증)**
- 설명: 임계금액을 초과하는 이체는 즉시 완료하지 않고 인증 대기 상태로 두었다가, OTP 검증을 통과한 뒤에 실행한다.
- 처리 절차: 임계금액 초과 판별 → 이체 금액을 출금계좌의 지급정지 금액으로 설정 → 거래를 인증 대기 상태로 저장 → OTP 발급 후 3분 만료로 관리 → 검증 성공 시 지급정지 해제와 함께 원장 엔트리 기록, 거래를 완료 상태로 전이 → 검증 실패 횟수가 한도를 넘거나 유효시간이 지나면 지급정지 해제 후 거래를 취소 상태로 전이
- 지급정지 처리의 근거: 대기 중인 금액을 묶어두지 않으면 같은 잔액으로 여러 건의 대기 거래를 만들 수 있다. 원장에는 확정된 금전 이동만 기록하므로, 대기 상태에서는 원장을 건드리지 않고 계좌의 지급정지 금액만 조정한다. 취소된 거래가 원장에 흔적을 남기지 않으므로 정합성 검증이 실패하지 않는다.
- 만료된 대기 거래를 정리하는 스케줄러를 함께 운영한다. / Should, Phase 2

### 3.5 지원 기능(감사로그, 알림, 이상거래탐지)

**FR-SUP-001 감사 로그 기록** — 모든 금전 거래와 계좌 상태 변경을 append-only로 기록한다. 서비스 코드에 로그 호출을 흩뿌리지 않고 도메인 이벤트를 발행해 별도 리스너가 저장하는 구조로 구현한다. / Should, Phase 2

**FR-SUP-002 이체 완료 알림**
- 설명: 이체 완료 사실을 비동기로 알린다.
- 처리 절차: 이체 트랜잭션 안에서 발신함에 이벤트를 적재 → 별도 발행기가 미발행 레코드를 폴링해 Kafka로 발행 후 상태 갱신 → 알림 서비스가 구독해 발송
- 발신함을 두는 근거: 데이터베이스 커밋과 메시지 발행 사이에는 원자성이 없다. 커밋 후 발행하면 커밋 직후 장애 시 알림이 누락되고, 커밋 전 발행하면 롤백된 이체에 대한 알림이 나간다. 금융 거래에서 둘 다 허용되지 않으므로, 이벤트를 원본 거래와 같은 트랜잭션에서 데이터베이스에 먼저 적재한다.
- 이 구조는 최소 한 번 전달을 보장하며, 중복 전달은 소비자 측 멱등 처리로 흡수한다.
- 실제 발송은 로그 출력으로 대체하고, 반복 실패하는 메시지는 재시도 후 데드 레터 토픽으로 보낸다. / Should, Phase 2

**FR-SUP-003 이상거래 탐지** — 룰 기반 FDS 간이 버전. / Could, Phase 3

**FR-SUP-004 고액현금거래 보고대상 판별(CTR 목업)**
- 설명: 동일인 명의로 1거래일 동안 1천만원 이상의 현금이 입출금된 경우를 보고대상으로 판별한다. 실제로는 금융정보분석원(KoFIU) 전산망에 자동 보고해야 하나, 이 보고망은 감독당국 승인과 기관 간 계약을 거친 금융기관만 접속할 수 있어, 그런 승인 절차를 거치지 않은 개발 환경에서는 연동이 불가능하다. 보고대상 판별과 내부 큐 적재까지만 구현하고, 실제 전송은 로그 출력으로 대체한다.
- 처리 절차: 동일인 명의 계좌의 1거래일 현금 입출금 합산 → 1천만원 이상 여부 판별 → 보고대상이면 큐 적재 후 로그 출력 / Could, Phase 3

## 7. 제약사항 및 가정
- 실제 대외 금융망 연동 없이 폐쇄형 시스템으로 구현한다.
- 실명번호 등 민감정보는 실제 개인정보가 아닌 테스트 더미 데이터를 사용한다.
- 통화는 원화 단일 통화 기준으로 설계하며, 다통화 지원은 범위에서 제외한다.
- 부하테스트 목표치는 초기 개발 및 검증 환경 기준(동시 사용자 100~500명)으로 가정한다.
- Phase 3는 남은 개발 기간에 따라 선택적으로 진행한다.
- 고객 대상은 개인 고객으로 한정하고, 법인/단체 고객은 지원 범위에서 제외한다. 이에 따라 특정금융거래정보법상 법인 실제소유자 확인 절차(25% 이상 지분자 확인 등 3단계 판별)는 적용 대상이 아니며, 실제소유자는 고객 본인으로 간주하는 방식으로 단순화한다.

### 7.1 규제 준수 관련 목업 처리 사유
현실 서비스와 동일한 흐름으로 구현하되, 감독당국의 인정이나 승인을 받은 사업자만 접속 또는 운영할 수 있는 세 구간은 아래와 같은 이유로 목업이나 대체 수단으로 처리한다. 처리 절차와 데이터 구조는 실제 규정에 맞게 설계하고, 접근이 제한된 구간만 대체한다.

| 항목 | 내용 |
|---|---|
| 실명확인 연동 불가 사유 | 실제 은행은 실명확인 시 행정안전부의 공적장부 진위확인 시스템과 연계해 성명, 주민등록번호, 주소의 일치 여부를 실시간으로 조회한다. 이 시스템은 금융회사가 감독당국 승인과 행정안전부와의 기관 간 계약을 거쳐야 접속할 수 있어, 그런 승인 절차를 거치지 않은 환경에서는 접근이 불가능하다. |
| 실명확인 대안 | 실명확인 서비스를 인터페이스로 분리하고, 개발 환경에서는 입력된 실명번호의 형식 검증과 더미 데이터베이스 대조만 수행하는 목업 구현체로 대체한다. 실제 서비스 전환 시 이 인터페이스의 구현체만 교체하면 되도록 설계한다. |
| CTR 보고 연동 불가 사유 | 1거래일 1천만원 이상 현금 입출금 발생 시 금융정보분석원(KoFIU) 전산망으로 자동 보고해야 하나, 이 보고망 역시 감독당국 승인을 받은 금융기관만 접속할 수 있다. |
| CTR 보고 대안 | FR-SUP-004에서 보고대상 판별과 내부 큐 적재까지만 구현하고, 실제 외부 전송은 로그 출력으로 대체한다. 판별 기준금액(1거래일 1천만원)은 실제 규정을 그대로 반영한다. |
| 공동인증서/전자서명 기반 인증 연동 불가 사유 | 공동인증서, 금융인증서, 카카오·네이버·PASS 등 민간인증서는 모두 전자서명법상 과학기술정보통신부와 위임기관인 한국인터넷진흥원의 전자서명인증사업자 인정을 받은 사업자만 발급할 수 있다. 이 인정은 보안설비, 재정능력, 운영기준 준수 여부를 심사하는 기업 단위 절차이며, 발급기관 자체가 되는 것은 물론 기존 인정사업자와 신뢰당사자 계약을 맺어 인증서 검증 기능만 이용하는 것도 개인 개발자 수준에서는 사실상 불가능하다. |
| 공동인증서/전자서명 대안 | 실제 은행도 인증서를 로그인이나 이체 시 제공하는 여러 인증수단 중 하나로 취급하고, OTP나 생체인증 같은 대체 수단을 동등하게 인정한다는 점에 착안해, 이 프로젝트에서는 FR-AUTH-003의 OTP 기반 2차 인증을 인증서의 실무적 대체 수단으로 채택한다. 자체 서명 인증서로 거래 데이터에 서명하고 서버가 검증하는 모의 전자서명 모듈도 검토했으나, 인증서 발급·검증 인프라 연동이 빠지면 남는 것이 서명값 생성과 검증 로직뿐이라 구현 비용 대비 실익이 낮다고 보아 보류했다. 이 판단의 상세 근거는 구현계획 13절에 있다. |
