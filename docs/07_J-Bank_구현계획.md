## 1. 문서 개요와 전제

지금까지 작성한 설계 문서는 무엇을 만들 것인지에 대한 합의를 마친 상태다. 이 문서는 그 합의를 언제, 어떤 순서로, 어떤 완료 기준으로 코드에 옮길 것인지를 정의한다.

계획을 세울 때 전제한 조건은 다음 다섯 가지다.

첫째, 전체 범위는 Phase 1부터 Phase 3까지 7주로 잡는다. v1.0에서 산정한 총 작업량은 약 315시간이었고 범위 자체는 줄이지 않는다. Phase 3의 인프라 자동화와 관측 가능성 구성이 데브옵스 역량을 보여주는 핵심 구간이라 축소 대상이 아니다.

둘째, 주당 투입 시간은 40~50시간을 기준으로 한다. 315시간을 주당 45시간으로 나누면 정확히 7주가 나온다. v1.0의 주차 구성을 정확히 2대 1로 접어 넣은 것이며, 주제의 순서와 의존 관계는 그대로 유지했다. 다만 두 주 분량을 한 주에 넣는다는 것은 밀렸을 때 흡수할 여유가 사라진다는 뜻이기도 하다. 이 문제는 12절 리스크 항목에서 별도로 다룬다.

셋째, Phase 1이 끝나는 3주차 시점에 그 자체로 완결된 시연이 가능해야 한다. 회원가입부터 계좌개설, 입금, 이체, 잔액과 거래내역 조회까지 이어지는 흐름이 Docker Compose 한 번으로 동작하는 상태를 3주차의 절대 목표로 둔다. 뒤의 어떤 주차가 밀리더라도 이 목표는 지킨다.

넷째, 개발 단계에서는 클라우드 상시 과금을 만들지 않는다. 인프라아키텍처 문서의 비용 항목에서 정리한 대로 NAT 게이트웨이, MSK, Multi-AZ RDS는 시간 단위로 과금되므로, 평상시에는 로컬 Docker Compose와 단일 EC2로 개발하고 EKS와 Multi-AZ 구성은 6주차 이후 검증과 시연 시점에만 올린다.

다섯째, 성능은 처음부터 측정하되 최적화는 뒤로 미룬다. 미루는 것과 일부러 느리게 만드는 것은 다르며, 그 경계를 어디에 두는지를 7절에서 명시적으로 정의한다. 부하 테스트 베이스라인은 v1.0의 11주차가 아니라 2주차에 확보한다.

## 3. W0 준비 작업

본 주차에 들어가기 전 반나절 정도로 끝낼 수 있는 준비 항목이다. 개발 환경 구성 자체는 별도 작업으로 진행하며, 이 문서는 그 결과물이 만족해야 할 조건만 정의한다.

### 3.1 저장소 구성

저장소는 하나로 둔다. 백엔드와 프론트엔드, 인프라 코드, 설계 문서, 계약 스냅샷이 같은 저장소에 들어가고, 구성은 폴더구조 문서 1절의 트리를 따른다.

v2.0까지는 백엔드와 프론트엔드를 분리한 두 개의 저장소로 두기로 했다. 배포 대상이 AWS와 Vercel로 갈라져 있고 릴리스 주기도 달라서 하나의 저장소에 묶으면 파이프라인에 조건 분기만 늘어난다는 판단이었다. v2.1에서 이 결정을 뒤집는다.

뒤집는 근거는 세 가지다.

첫째, 조건 분기 부담이 실제로는 작다. 워크플로에 경로 필터를 걸면 백엔드 경로가 바뀔 때만 백엔드 검증이 돌고 프론트엔드 경로가 바뀔 때만 프론트엔드 검증이 돈다. 배포 대상이 다르다는 것도 문제가 되지 않는다. Vercel은 루트 디렉터리를 지정하면 하위 경로만 배포하고, 백엔드 이미지 빌드는 별도 워크플로로 분리하면 된다.

둘째, 계약 드리프트 검사가 단순해진다. 이 프로젝트는 백엔드 코드에서 생성한 API 명세를 프론트엔드 타입의 입력으로 쓴다. 저장소가 둘이면 명세를 저장소 사이로 옮기는 단계가 필요하고, 어느 쪽 명세가 최신인지 확인하는 부담이 생긴다. 하나면 같은 커밋 안에서 백엔드 변경과 프론트엔드 타입 변경이 함께 드러난다.

셋째, 문서와 코드가 같은 이력을 공유한다. 설계 문서 여덟 종과 아키텍처 결정 기록이 코드와 같은 저장소에 있으면 어떤 변경이 어떤 결정에 따른 것인지가 커밋 단위로 남는다. 7주 일정에서 문서와 코드가 어긋나는 것이 가장 위험한 실패 방식이라, 이 이점이 파이프라인 편의보다 크다고 판단했다.

한 가지 대가가 있다. Vercel이 빌드할 때 백엔드 코드까지 포함한 저장소 전체를 내려받는다. 빌드 시간이 다소 늘지만 무시할 수준이고, 무시 조건을 걸어 프론트엔드 경로에 변경이 없을 때는 빌드를 건너뛰도록 설정한다.

### 3.2 브랜치와 커밋

브랜치 전략은 트렁크 기반으로 간다. `main`을 항상 배포 가능한 상태로 유지하고, 작업은 `feat/`, `fix/` 접두어의 짧은 수명 브랜치에서 하고 Pull Request로 병합한다. 혼자 하는 프로젝트에서 git-flow를 도입하면 릴리스 브랜치 관리 비용만 생긴다.

커밋 메시지는 Conventional Commits 규칙을 따르고, 이를 근거로 릴리스 노트를 자동 생성한다. 저장소가 하나이므로 범위 표기를 활용해 어느 영역의 변경인지 구분한다.

### 3.3 결정 기록

아키텍처 결정은 `docs/adr/` 디렉터리에 번호를 붙여 남긴다. 비관적 락을 택한 이유, 발신함 패턴을 도입한 이유, 도메인 패키지 사이의 의존 방향을 그렇게 정한 이유, 그리고 7절에서 다루는 성능 개선 판단들이 이 디렉터리에 쌓이도록 한다. 일정을 압축한 만큼 기억에 의존할 여지가 줄어들기 때문에 결정 기록의 가치는 오히려 커진다.

## 4. Phase 1 상세 계획

### W1 스캐폴딩·공통 기반과 고객·계좌 도메인

기술 스택은 Java 21, Spring Boot 3.3, Gradle Kotlin DSL로 확정한다. v1.0에서는 Java 17로 잡았으나 Java 21로 올릴 것을 권한다. 둘 다 장기 지원 버전이고 Spring Boot 3.3이 정식 지원하므로 도입 위험이 없으면서, 가상 스레드를 설정 한 줄로 켜고 끌 수 있다는 점이 6주차 성능 최적화 구간에서 측정 가능한 개선 지렛대가 된다. 데이터베이스 접근이 블로킹인 이 시스템에서 가상 스레드가 실제로 효과가 있는지 없는지를 수치로 확인하고 그 결과를 결정 기록으로 남기는 것이, 최신 기능을 썼다고 나열하는 것보다 설득력이 높다.

모듈은 처음부터 쪼개지 않고 단일 모듈 안에서 패키지를 도메인 기준으로 나눈다. `customer`, `account`, `ledger`, `transfer`, `product`, `auth`, `support` 각각이 자기 controller, service, domain, repository를 가지는 구조이며, 여기에 프레임워크 계층인 `global`과 도메인 무관 기반층인 `common`, 배치 잡을 담는 `batch`를 더한다. 전체 배치는 폴더구조 문서 1절에 있다.

패키지 사이의 의존 방향은 폴더구조 문서 4절의 표를 따르고, ArchUnit 테스트로 검증 시점에 강제한다. 허용 방향을 미리 확정해두는 이유는 W2에서 이체를 구현할 때 `transfer`가 `account`와 `ledger`를 동시에 필요로 한다는 점이 즉시 드러나기 때문이다. 이 의존을 예외로 처리하지 않고 규칙에 명시해두면 나머지 방향을 엄격하게 막을 수 있다. 특히 `account`와 `ledger`가 서로를 참조하지 않도록 하는 규칙이 W7 서비스 분리의 전제가 된다.

이 구조를 처음부터 Gradle 멀티모듈로 쪼개지 않는 이유는 결정 기록으로 남긴다. 요지는 모듈 경계를 확정할 근거가 W2 이후에 생긴다는 것이고, 패키지 이동이 모듈 이동보다 되돌리는 비용이 낮다는 것이다. 판단 기준 자체는 7절의 그것과 같다.

로컬 인프라는 Docker Compose로 PostgreSQL 16과 Redis 7을 띄운다. Compose 파일은 하나로 두고 프로파일을 나눈다. `core` 프로파일은 데이터베이스와 캐시만, `messaging` 프로파일은 Kafka, `observability` 프로파일은 Prometheus와 Grafana, Loki를 담는다. 뒤에서 서비스가 추가될 때마다 파일을 고치는 대신 처음부터 자리를 만들어두는 편이 압축된 일정에서 유리하다. 파일을 여러 개로 쪼개지 않는 이유는 서비스 정의가 중복되면 어느 쪽이 진실인지 흐려지기 때문이다.

스키마는 처음부터 Flyway로 관리하고 JPA의 `ddl-auto`는 `validate`로 고정한다. 운영 환경에서 스키마 자동 생성을 쓰지 않는 것이 당연한 만큼, 로컬에서도 같은 규칙을 적용해야 마이그레이션 스크립트가 실제 진실이 된다. 마이그레이션 파일은 `resources/db/migration` 한 곳에만 두고 버전 계열을 하나로 유지한다.

공통 기반으로 이번 주에 만들 것은 다섯 가지다. API설계 문서 2.4절의 봉투 구조를 그대로 담는 `ApiResponse<T>` 제네릭 응답 클래스, 2.7절의 공통 에러코드를 담는 `ErrorCode` 열거형, 모든 예외를 이 포맷으로 변환하는 `@RestControllerAdvice` 전역 예외 처리기, 금액을 항상 문자열로 직렬화하는 Jackson 커스텀 시리얼라이저, 그리고 요청 추적 식별자를 생성해 진단 컨텍스트에 심는 서블릿 필터다.

금액 직렬화와 요청 추적 식별자를 첫 주에 넣는 데는 이유가 있다. 금액 표현 규칙은 API 응답 계약의 일부라서 뒤에 바꾸면 이미 붙은 클라이언트를 전부 손봐야 하고, 요청 추적 식별자는 6주차에 관측 가능성을 붙일 때 넣으면 그 이전에 쌓인 로그가 전부 추적 불가능한 상태로 남는다. 둘 다 나중에 도입 비용이 급격히 오르는 항목이라 뒤로 미루지 않는다.

Springdoc OpenAPI를 붙여 `/v3/api-docs`와 Swagger UI를 노출시킨다. GitHub Actions 워크플로도 이번 주에 만든다. Pull Request마다 경로 필터에 따라 컴파일, 단위 테스트, ArchUnit 검증, Spotless 포맷 검사를 돌리고, `main` 병합 시에는 Docker 이미지를 빌드해 레지스트리에 올린다. 명세 스냅샷이 코드와 어긋나는지 확인하는 단계도 함께 넣는다. 파이프라인을 코드보다 먼저 세워두면 이후 모든 작업이 자동으로 검증받는다.

여기까지가 이번 주 전반부이고, 후반부에 고객과 계좌 도메인을 얹는다.

Customer와 Account 엔티티를 ERD 문서 2.1절, 2.2절 스키마 그대로 만들고 Flyway 마이그레이션을 작성한다. 계좌 테이블에는 지급정지 금액 컬럼을 처음부터 포함시킨다. 이 컬럼이 실제로 쓰이는 시점은 W5의 고액이체 2차 인증이지만, 잔액을 다루는 컬럼을 나중에 추가하면 이미 쌓인 계좌 데이터에 대한 보정 마이그레이션이 필요해진다. 컬럼 정의와 출금 가능 금액 계산 규칙은 ERD 문서 2.2절과 요구사항명세서 FR-TXN-002에 반영되어 있다.

개인정보 암호화가 이번 주의 첫 번째 기술 포인트다. 실명번호, 연락처, 주소는 JPA `AttributeConverter`로 AES-256-GCM 암복호화를 투명하게 처리한다. 여기에 더해 실명번호는 HMAC-SHA256 결정론적 해시를 별도 컬럼에 저장해 중복 고객 확인에 쓴다. AES-GCM은 같은 평문이라도 매번 다른 암호문이 나오기 때문에 암호문 컬럼으로는 중복 조회가 불가능한데, 이 점이 해시 컬럼을 따로 둔 이유다. 키는 로컬에서는 환경변수로, 배포 환경에서는 AWS Secrets Manager로 주입한다.

계좌번호 채번은 지점코드 세 자리, 일련번호, 체크디지트로 구성하고 모듈러스 10 방식으로 검증한다. 일련번호는 데이터베이스 시퀀스에서 뽑아 동시 채번 시 충돌을 원천 차단한다.

CDD 등급 산정은 규칙 기반 서비스로 분리한다. 직업, 거래목적, 실명확인 방식을 입력으로 받아 위험도를 산출하고, 결과가 높음이면 응답에 강화된 고객확인이 필요하다는 플래그를 함께 내린다.

이번 주에 완성할 엔드포인트는 API-001 고객 등록, API-002 계좌 개설, API-003 계좌 상세 조회, API-004 계좌 상태 변경, API-005 계좌 해지, API-013 강화된 고객확인 등록, API-017 고객별 계좌 목록이다.

### W2 원장·거래 코어와 동시성·멱등성 검증

이 주차가 프로젝트 전체에서 가장 중요하고, 동시에 가장 위험하다. 여기서 만드는 것이 다른 모든 기능의 토대이며 기술 면접에서 가장 깊게 파고들 부분인데, v1.0에서 난이도가 가장 높다고 표시했던 두 주를 한 주에 접어 넣었기 때문이다. 이번 주가 밀리면 뒤를 압축하지 말고 W7의 서비스 분리를 축소한다.

LedgerEntry와 Transaction 엔티티를 만들고, 원장 테이블에는 애플리케이션 레벨에서 수정과 삭제를 막는 장치를 건다. 리포지토리에서 해당 메서드를 노출하지 않고, JPA 엔티티 리스너에서 `@PreUpdate`와 `@PreRemove` 시 예외를 던지는 이중 방어다.

거래 상태는 ERD 문서 2.4절의 상태 기계를 그대로 코드로 옮긴다. 이번 주에는 인증 대기 상태로 진입하는 경로가 아직 없지만, 상태 열거형과 허용 전이 규칙은 처음부터 전체를 정의한다. 종료 상태에서 어떤 전이도 허용하지 않는다는 규칙이 나중에 추가되면 그 이전에 쌓인 거래의 상태 이력을 신뢰할 수 없게 된다.

이체 처리 절차는 요구사항명세서 FR-TXN-003에 정의된 순서를 그대로 코드로 옮긴다. 멱등성 키 중복 확인, 두 계좌를 계좌 식별자 오름차순으로 정렬한 뒤 그 순서대로 비관적 쓰기 락 획득, 양쪽 계좌 상태와 출금 가능 금액 검증, 차변과 대변 원장 두 건을 단일 트랜잭션에서 기록, 거래 이력 저장 순이다.

락 획득 순서를 정렬하는 것이 교착상태 방지의 핵심이다. A 계좌에서 B 계좌로 이체하는 요청과 B에서 A로 이체하는 요청이 동시에 들어올 때, 각자 출금 계좌부터 락을 잡으면 서로가 상대의 락을 기다리며 영구히 멈춘다. 계좌 식별자 순서로 정렬해두면 두 요청 모두 같은 계좌를 먼저 잡으려 하므로 한쪽이 대기하다 정상적으로 처리된다.

잔액은 원장 합산을 진실의 근거로 삼되, 조회 성능을 위해 계좌 테이블의 캐시 컬럼을 트랜잭션 안에서 함께 갱신한다. 원장 엔트리마다 반영 직후 잔액 스냅샷도 남긴다. 이 세 값이 서로 어긋나면 W5의 대사 배치가 잡아내는 구조다.

검증 기준이 잔액이 아니라 출금 가능 금액이라는 점을 이번 주부터 지킨다. 지급정지 금액은 아직 항상 0이지만, 검증식을 나중에 바꾸면 그 사이에 작성한 테스트가 전부 잔액 기준으로 남아 W5에서 어느 것을 고쳐야 하는지 분간하기 어려워진다.

멱등성은 두 겹으로 구현한다. 서비스 진입 시 거래 테이블에서 멱등성 키를 조회해 이미 처리된 요청이면 원래 결과를 그대로 반환하고, 그 확인을 통과한 요청이 동시에 두 개 들어오는 경우에는 데이터베이스의 유니크 제약이 두 번째 삽입을 막는다. 유니크 제약 위반 예외를 잡아 원래 결과를 조회해 반환하는 처리까지 넣어야 클라이언트 입장에서 완전한 멱등이 된다.

완성할 엔드포인트는 API-006 입금, API-007 출금, API-008 이체, API-009 잔액 조회, API-010 거래내역 조회다.

이번 주 후반은 앞에서 만든 로직이 실제로 동작하는지 증명하는 데 쓴다. 코드를 짜는 시간보다 검증 시나리오를 설계하는 시간이 더 든다.

테스트 환경은 Testcontainers로 실제 PostgreSQL과 Redis를 띄운다. 인메모리 H2로는 비관적 락 동작이 실제와 달라 검증의 의미가 없다.

검증 시나리오는 다섯 가지다. 첫째, 잔액 10만 원 계좌에 1만 원 출금 요청 100건을 동시에 던져 정확히 10건만 성공하고 나머지는 잔액 부족으로 실패하는지 확인한다. 둘째, A에서 B로, B에서 A로 향하는 이체 요청을 각각 50건씩 동시에 던져 교착상태 없이 전부 처리되고 두 계좌 잔액 합이 보존되는지 확인한다. 셋째, 동일한 멱등성 키로 요청 10건을 동시에 던져 거래가 정확히 한 건만 생성되고 열 개의 응답이 모두 같은 거래 식별자를 반환하는지 확인한다. 넷째, 랜덤 계좌 쌍에 대해 이체 1000건을 실행한 뒤 모든 계좌의 원장 합산과 캐시 잔액이 일치하고 전체 차변 합과 대변 합이 같은지 확인한다. 다섯째, 이체 도중 강제로 예외를 발생시켜 원장 두 건이 모두 롤백되고 한쪽만 남는 상태가 생기지 않는지 확인한다.

이번 주에 분산 락은 도입하지 않는다. 애플리케이션 인스턴스가 하나인 동안에는 데이터베이스의 행 수준 락이 모든 동시성을 직렬화하므로 Redisson 분산 락은 중복 방어일 뿐이다. 인스턴스를 여러 개로 늘리는 W7 시점에도 데이터베이스 락은 여전히 유효하므로, 분산 락이 실제로 필요해지는 지점은 데이터베이스 트랜잭션 밖에서 조율해야 하는 배치 잡의 단일 실행 보장이다. 이 판단 근거를 아키텍처 결정 기록에 남긴다.

마지막으로 이번 주의 신설 항목이 부하 테스트 베이스라인 확보다. k6 스크립트를 작성해 이체 엔드포인트에 대한 최초 측정치를 남긴다. 상세한 이유와 운영 방식은 7절에서 다룬다.

### W3 인증·보안과 상품 도메인, Phase 1 마감

Spring Security 6 필터체인을 구성하고 비밀번호는 bcrypt로 해시한다.

토큰 발급은 API설계 문서 2.2절의 쿠키 기반 방식을 그대로 구현한다. 인증 토큰과 갱신 토큰을 모두 HttpOnly, Secure, SameSite=Lax 속성의 쿠키로 내려주고, 응답 본문에는 만료 시각과 사용자 표시 정보만 담는다. v2.0 시점에는 API설계 문서가 토큰을 본문으로 내려주도록 되어 있어 프론트엔드 전략과 어긋난 상태였는데, 이 불일치는 v1.1 개정으로 해소되었다.

갱신 토큰은 재발급마다 새 값으로 교체하는 로테이션을 적용하고, 발급된 토큰의 식별자를 Redis에 화이트리스트로 관리한다. 이미 사용된 토큰이 다시 들어오면 탈취를 의심할 근거가 되므로, 해당 사용자의 토큰 계열 전체를 폐기하고 재로그인을 요구한다.

쿠키 기반으로 전환하면서 생기는 위험이 요청 위조다. 브라우저가 쿠키를 자동으로 실어 보내기 때문에 다른 사이트에서 사용자 브라우저를 통해 이체 요청을 보낼 수 있다. SameSite=Lax로 대부분의 교차 사이트 요청을 차단하고, 상태를 바꾸는 요청에는 무작위 값을 쿠키와 요청 헤더 양쪽으로 받아 일치 여부를 검증하는 방식을 추가한다. 적용 대상과 예외, 에러코드는 API설계 문서 2.8절에 정의되어 있다.

로그인 연속 실패는 Redis 카운터로 관리하고 5회 초과 시 계정을 일정 시간 잠근다.

CORS는 프론트엔드 도메인만 허용하고 자격 증명 전송을 켠다. 다만 이 시점의 CORS 설정은 로컬 개발용이며, 배포 환경에서는 프론트엔드 트랙에서 만드는 프록시 구조 덕분에 브라우저 기준으로 동일 출처가 되어 CORS 자체가 발생하지 않는다.

이번 주 후반에 Product와 ProductContract 엔티티를 만들고 API-012 상품 가입, API-018 상품 목록, API-019 고객별 계약 조회를 구현한다. 최소 가입금액 미달과 판매 중지 상품에 대한 도메인 에러코드를 정의한다.

API설계 문서의 모든 엔드포인트에 Springdoc 어노테이션을 붙여 요청과 응답 예시, 에러코드까지 문서에 드러나게 한다. 여기서 생성되는 명세가 프론트엔드 타입 생성의 입력이 되므로 정확도가 중요하다. 생성된 명세를 `contracts/openapi/openapi.yaml`로 덤프해 커밋하고, 검증 파이프라인이 코드와 스냅샷의 동일성을 확인하도록 연결한다.

시연용 시드 데이터를 준비한다. 고객 몇 명, 계좌 몇 개, 상품 네 종을 Flyway 마이그레이션과 분리된 별도 프로파일에서 주입한다.

마지막으로 전체 흐름을 하나의 통합 테스트로 묶는다. 고객 등록, 계좌 개설, 로그인, 입금, 이체, 잔액 조회, 거래내역 조회, 상품 가입까지 한 번에 통과하는 시나리오다. 이 테스트가 초록불이면 Phase 1이 끝난 것이다. 저장소에 v0.1.0 태그를 붙이고, README에 Docker Compose 실행 한 줄로 전체가 뜨는 절차를 정리한다.

## 5. Phase 2 상세 계획

### W4 감사 로그·위험도 이력과 이벤트 기반 알림

AuditLog 엔티티를 만들고, 계좌 상태 변경과 이체 완료, 고객 등급 변경처럼 추적이 필요한 사건을 기록한다. 기록 방식은 서비스 코드에 로그 호출을 흩뿌리는 대신 Spring 도메인 이벤트를 발행하고 별도 리스너가 받아 저장하는 구조로 간다. 감사 기록이 실패해도 본래 거래가 실패하지 않아야 하는 경우와, 반드시 함께 커밋되어야 하는 경우를 구분해 리스너의 트랜잭션 전파 속성을 각각 다르게 설정한다.

이 구조는 폴더구조 문서 4.2절의 의존 방향 규칙과 맞물린다. `support`는 어떤 도메인도 직접 호출하지 않고 `common.event`에 정의된 이벤트만 구독한다. 감사 기록을 붙이거나 떼는 것이 도메인 코드에 영향을 주지 않게 하려는 의도다.

CustomerRiskAssessmentHistory에 등급 변경 시점의 스냅샷을 남기는 로직을 붙인다. 현재 등급만으로는 감독 검사 시 특정 시점의 판단 근거를 제시할 수 없다는 것이 이 테이블을 만든 이유이므로, 등급을 바꾸는 모든 경로가 예외 없이 이력을 남기도록 서비스 계층 한 곳으로 진입점을 모은다.

거래내역 조회를 고도화한다. 기간과 거래유형 필터를 추가한다. 이 시점에서 조회 성능은 아직 손대지 않는다. 데이터 10만 건을 넣고 인덱스 없는 상태의 응답 시간과 실행 계획을 기록만 해두고, 실제 인덱스 설계와 반영은 W6의 최적화 구간에서 측정 근거와 함께 진행한다.

API-020 감사 로그 조회를 구현한다.

이번 주 후반에는 로컬 Compose의 메시징 프로파일을 켜고 이체 완료 이벤트를 발행한다.

여기서 다룰 핵심 문제는 데이터베이스 커밋과 메시지 발행 사이의 원자성이다. 트랜잭션 커밋 후에 발행하도록 리스너를 걸어도, 커밋 직후 애플리케이션이 죽으면 메시지는 영영 발행되지 않는다. 반대로 커밋 전에 발행하면 트랜잭션이 롤백됐는데 이벤트만 나가는 상황이 생긴다. 금융 거래에서 둘 다 허용되지 않으므로 발신함 패턴을 적용한다. 이체 트랜잭션 안에서 이벤트를 별도 테이블에 함께 저장하고, 폴링하는 발행기가 미발행 레코드를 읽어 Kafka로 보낸 뒤 상태를 갱신하는 구조다. 이렇게 하면 최소 한 번 전달은 보장되고, 중복 전달은 소비자 측 멱등 처리로 흡수한다.

발신함 테이블의 스키마는 ERD 문서 2.9절에 정의되어 있다. 상태와 재시도 횟수, 마지막 오류 메시지를 함께 두고, 미발행 상태만 담는 부분 인덱스를 건다. 이 인덱스는 7절 기준으로도 초기부터 넣어야 하는 항목인데, 발신함은 발행된 레코드가 계속 쌓여 테이블이 커지는 구조라 인덱스 없이 두면 폴링 비용이 시간에 비례해 나빠지기 때문이다.

소비자는 알림 발송을 담당하되 실제 발송 대신 로그 출력으로 대체한다. 소비 실패가 반복되는 메시지는 재시도 후 데드 레터 토픽으로 보낸다.

### W5 배치 처리와 고액이체 2차 인증

Spring Batch로 세 개의 잡을 만든다. 잡은 별도 실행 모듈로 분리하지 않고 같은 애플리케이션의 `batch` 패키지에 두되, 실행만 프로파일과 잡 이름 인자로 분리한다. 배포 환경에서는 API와 같은 이미지를 쓰는 쿠버네티스 CronJob으로 올려 자원을 분리한다. 이미지를 하나로 유지하는 이유는 폴더구조 문서 5절에 정리했다.

첫째는 이자 계산과 만기 처리다. 만기일이 도래한 계약을 조회해 이자를 계산하고 원장에 입금 엔트리를 기록한 뒤 계약 상태를 만기로 바꾼다. 이자 계산은 소수점 처리 규칙을 명시적으로 정하고, 원 단위 절사 여부를 코드가 아니라 설정으로 뺀다.

둘째는 원장 정합성 대사다. 모든 계좌에 대해 원장 합산 값과 캐시 잔액을 비교하고, 전체 차변 합과 대변 합이 일치하는지 검증한다. 불일치가 발견되면 자동으로 고치지 않고 리포트만 남긴다. 금융 시스템에서 정합성 불일치를 자동 보정하는 것은 원인을 은폐하는 행위이기 때문이다.

셋째는 고액현금거래 판별이다. 일자별 고객별 현금 거래 합계를 집계해 기준 금액을 넘는 대상을 CtrReportQueue에 적재한다. 실제 보고 전송 구간은 요구사항명세서 7.1절에 정리한 대로 로그 출력으로 대체한다.

잡은 전부 재실행 안전하게 만든다. 같은 기준일로 두 번 돌려도 결과가 달라지지 않도록 잡 파라미터에 기준일을 넣고 중복 실행을 막는다. 청크 크기는 일단 기본값으로 두고 W6에서 처리 시간을 측정하며 조정한다.

이번 주 후반은 고액이체 2차 인증이다. 임계 금액을 초과하는 이체는 즉시 완료되지 않고 인증 대기 상태로 남는다. W2에서 정의해둔 상태 기계에 따라 허용된 전이 외에는 예외를 던지도록 만든다.

일회용 비밀번호는 Redis에 3분 만료로 저장하고, 검증 실패 횟수도 함께 카운트해 일정 횟수 초과 시 거래를 취소시킨다. 만료된 대기 거래를 정리하는 스케줄러도 함께 만든다. 이 스케줄러의 조회 대상은 인증 대기 상태의 거래이므로, ERD 문서 3절에 정의한 부분 인덱스를 사용한다.

여기서 W1에 만들어둔 지급정지 금액 컬럼을 실제로 사용한다. 인증 대기에 들어간 이체 금액을 지급정지로 잡고, 인증 성공 시 지급정지를 해제하면서 원장에 차변 엔트리를 기록한다. 실패나 만료 시에는 원장을 건드리지 않고 지급정지만 되돌린다. 대기 상태에서 원장을 건드리지 않는 것이 이 설계의 핵심이며, 그 덕분에 취소된 거래가 정합성 대사를 깨뜨리지 않는다.

API-016 2차 인증 검증을 구현하고 v0.2.0 태그를 붙인다.

## 6. Phase 3 상세 계획

### W6 관측 가능성·성능 최적화와 인프라 코드화

Micrometer로 지표를 노출하고 Prometheus가 수집하도록 구성한다. Grafana 대시보드에는 이체 처리 시간 백분위, 초당 처리 건수, 에러율, 데이터베이스 커넥션 풀 사용률, 락 대기 시간을 올린다. 마지막 두 항목이 동시성 설계를 설명할 때 근거가 되는 지표다.

로그는 JSON 구조화 출력으로 바꾼다. 요청 추적 식별자는 W1에서 이미 심어뒀으므로 여기서는 출력 포맷만 바꾸면 되고, 그 결과 W1부터 쌓인 로그가 전부 추적 가능한 상태로 남는다. 수집은 Loki로 한다. OpenSearch도 후보지만 운영 비용과 구성 복잡도가 이 규모에 과하다.

이번 주 전반부의 절반은 성능 최적화에 쓴다. W2부터 매주 기록해온 부하 테스트 결과가 여기서 입력이 된다. 진행 방식과 개선 후보 목록은 7절에 정리한다.

후반부는 인프라 코드화다. Terraform으로 인프라아키텍처 문서의 Phase 1 구성을 모듈화한다. 네트워크 계층은 퍼블릭, 애플리케이션, 데이터, 관리 네 단계 서브넷으로 나누고, 그 위에 RDS, ElastiCache, ALB, WAF, ECR, EKS 모듈을 얹는다.

상태 파일은 S3에 저장하고 DynamoDB로 잠금을 건다. 혼자 하는 프로젝트라도 로컬 상태 파일은 유실 위험이 크고, 원격 상태 구성은 실무에서 기본이다.

파이프라인에는 `terraform plan`까지만 자동으로 돌리고 `apply`는 수동 승인 단계를 둔다. 인프라 변경이 자동으로 반영되는 파이프라인은 편리한 만큼 위험하다.

비용 통제를 위해 상시 구동 구성과 시연 구성을 Terraform 워크스페이스로 분리한다. 평상시에는 단일 인스턴스와 Compose로 충분하고, 시연 기간에만 전체 구성을 올렸다가 내린다.

### W7 쿠버네티스 배포와 GitOps, 서비스 분리

EKS에 애플리케이션을 올린다. 매니페스트는 Helm 차트로 작성하고 환경별 값 파일을 분리한다. 차트 하나에 API 디플로이먼트와 배치 CronJob을 함께 담고, 두 워크로드가 같은 이미지 태그를 참조하도록 값 파일을 구성한다.

준비 상태와 생존 확인 프로브를 구분해서 설정한다. 준비 프로브에는 데이터베이스 연결까지 확인하는 엔드포인트를 붙이고, 생존 프로브는 애플리케이션 프로세스 자체만 본다. 두 프로브를 같은 엔드포인트로 두면 데이터베이스가 잠깐 느려질 때 컨테이너가 통째로 재시작되는 사고가 난다.

무중단 배포는 롤링 업데이트에 종료 유예 시간과 파드 중단 예산을 함께 설정해 확인한다. 배포 중에 부하 스크립트를 돌려 실패 요청이 0건인지 측정하면 무중단이라는 주장에 근거가 생긴다.

수평 파드 오토스케일러를 CPU와 초당 요청 수 기준으로 걸고, ArgoCD로 저장소 상태와 클러스터 상태를 동기화하는 GitOps 구조를 만든다. 배포 이력이 Git 커밋 이력과 같아지는 것이 이 구성의 이점이다.

민감 정보는 Secrets Manager에 두고 External Secrets Operator로 클러스터에 주입한다.

인스턴스가 여러 개로 늘어나는 이 시점에 배치 잡의 단일 실행 보장 문제가 실제로 발생한다. W2에서 미뤄둔 분산 락을 여기서 도입하고, 왜 이 시점인지를 결정 기록에 남긴다.

이번 주 후반은 서비스 분리다. 전면적인 마이크로서비스 전환은 이 규모에서 오히려 설계 판단력을 의심받을 수 있다. 대신 분리가 정당화되는 경계 하나만 실제로 떼어낸다. 후보는 상품과 계약 도메인이다. 거래 코어와 트랜잭션 경계를 공유할 필요가 없고 배포 주기도 다르기 때문이다.

W1부터 지켜온 패키지 의존 방향이 여기서 회수된다. `product` 패키지를 별도 모듈로 승격한 뒤 독립 배포 단위로 떼어내는 순서로 진행하고, ArchUnit이 막아온 역방향 의존이 실제로 없었는지를 분리 과정에서 확인한다. 경계를 지킨 것이 실제로 값을 했는지 여기서 검증되는 셈이라, 결과를 결정 기록에 남긴다.

분리하면 상품 가입 흐름이 두 서비스에 걸치게 되므로 오케스트레이션 방식의 사가를 적용한다. 계약 생성, 초기 납입금 출금, 계약 확정 세 단계를 조율하고 각 단계마다 보상 트랜잭션을 정의한다. 출금은 완료됐는데 계약 확정이 실패하는 경우 출금을 되돌리는 보상 거래가 원장에 기록되는지까지 확인한다.

간이 이상거래 탐지 규칙을 넣는다. 단일 거래 임계 금액 초과, 짧은 시간 내 반복 이체, 심야 시간대 고액 이체 같은 단순 규칙으로 시작하고 API-022로 결과를 조회한다.

마지막으로 문서를 정리한다. 아키텍처 결정 기록을 훑어 빠진 판단이 없는지 확인하고, README에 시스템 구성도와 실행 방법, 주요 설계 판단 요약, 그리고 7주치 성능 추이 그래프를 정리한다. v1.0.0 태그를 붙인다.

## 7. 성능 측정과 최적화 전략

### 7.1 기본 방침

기능을 먼저 완성하고 성능은 측정한 뒤에 손댄다. 근거 없는 선제 최적화는 코드만 복잡하게 만들고, 개선했다는 주장의 근거도 남지 않는다.

다만 여기에는 반드시 구분해야 할 것이 있다. 최적화를 미루는 것과 일부러 비효율적으로 만드는 것은 다르다. 앞의 것은 정상적인 순서고, 뒤의 것은 나중에 되돌릴 수 없는 부채를 스스로 만드는 행위다.

둘을 가르는 기준은 되돌리는 비용이다. 판단 기준은 한 문장으로 정리된다. 나중에 바꿀 때 이미 쌓인 데이터나 이미 붙은 클라이언트를 건드려야 하는가.

건드릴 필요가 없으면 미뤄도 된다. 인덱스는 나중에 추가해도 기존 데이터가 그대로 쓰이고, 조회 쿼리 방식은 바꿔도 API 응답이 같으며, 커넥션 풀 크기는 설정 한 줄이다. 반대로 락 획득 순서를 나중에 바꾸려면 그때까지 쌓인 교착상태 사고를 감당해야 하고, 금액 컬럼 타입을 바꾸려면 데이터 마이그레이션이 필요하며, API 응답 구조를 바꾸려면 이미 붙은 프론트엔드를 전부 손봐야 한다.

이 기준은 성능 외의 판단에도 그대로 적용된다. W1에서 모듈을 쪼개지 않기로 한 것과 지급정지 금액 컬럼을 미리 만들어두는 것이 같은 기준에서 나온 서로 다른 결론이다. 앞의 것은 되돌리는 비용이 낮아 미뤘고, 뒤의 것은 이미 쌓인 데이터를 건드려야 해서 앞당겼다.

### 7.2 처음부터 지키는 항목

다음 항목은 성능 최적화가 아니라 설계 정합성의 문제라서 첫 주부터 지킨다. 나중에 바꾸는 비용이 지금 지키는 비용보다 훨씬 크다.

락 획득 순서 정렬과 트랜잭션 경계 설정, 원장의 추가 전용 구조, 멱등성 키 유니크 제약, 금액의 NUMERIC과 BigDecimal 타입 고정, 이벤트 발행의 발신함 구조, API 응답 봉투 구조와 금액 문자열 표현이 여기 속한다. 여기에 요청 추적 식별자를 진단 컨텍스트에 심는 것과 발신함 테이블의 부분 인덱스를 더한다. 앞의 것은 나중에 넣으면 그 이전 로그가 전부 무의미해지고, 뒤의 것은 테이블이 커질수록 폴링 비용이 나빠지는 구조라 초기 데이터가 적을 때 넣어두는 편이 낫다.

지급정지 금액 컬럼과 거래 상태 기계의 전체 정의도 여기에 포함한다. 둘 다 나중에 추가하면 이미 쌓인 계좌 데이터와 거래 이력을 보정해야 한다.

### 7.3 측정 후에 손대는 항목

다음 항목은 되돌리는 비용이 낮으므로 처음에는 가장 단순한 형태로 짜고, 측정해서 문제가 확인된 것만 고친다.

조회용 복합 인덱스, JPA 지연 로딩으로 인한 반복 쿼리를 페치 조인이나 엔티티 그래프 또는 프로젝션으로 바꾸는 작업, 커넥션 풀 크기, Redis 캐시 적용 범위, 거래내역 페이지네이션을 오프셋에서 키셋 방식으로 바꾸는 것, 발신함 폴링 주기와 배치 크기, Spring Batch 청크 크기, 원장 테이블 월별 파티셔닝, 가상 스레드 적용 여부, 로그 레벨 조정이 여기 속한다.

이 목록은 그 자체로 W6의 작업 후보 목록이 된다.

### 7.4 일부러 느리게 만들지 않는 이유

개선 폭을 키우려고 의도적으로 비효율적인 코드를 넣는 접근은 권하지 않는다. 이유는 세 가지다.

첫째, 그럴 필요가 없다. 정직하게 짠 첫 구현에는 이미 개선 여지가 충분히 남는다. 인덱스를 아직 안 걸었고, JPA 연관관계는 기본 설정대로 두었고, 커넥션 풀도 기본값이며, 페이지네이션은 오프셋 방식이고, 캐시는 없다. 이것들은 억지로 만든 것이 아니라 실제로 처음에 그렇게 짜는 것이 맞는 것들이다. 10만 건 데이터에서 인덱스 없는 조회와 있는 조회의 차이만으로도 보여줄 수 있는 개선 폭은 충분히 크다.

둘째, 면접에서 방어하기 어렵다. 개선 전후 수치를 설명할 때 "처음에 왜 이렇게 짰나"라는 질문은 반드시 따라온다. "측정 전이라 가장 단순한 형태로 두었다"는 답과 "개선 폭을 크게 보이려고 일부러 비효율적으로 짰다"는 답은 받는 인상이 완전히 다르다. 뒤의 답은 수치 전체의 신뢰도를 떨어뜨린다.

셋째, 되돌릴 수 없는 것을 잘못 건드릴 위험이 있다. 느리게 만들 대상을 고르다 보면 7.2절 항목에 손이 갈 수 있는데, 그 순간 성능 문제가 아니라 정합성 문제가 된다.

요약하면 방향은 맞다. 측정 없이 최적화하지 않는다는 원칙과 개선 전 수치를 반드시 남긴다는 원칙은 그대로 가져간다. 다만 "성능을 고려하지 않는다"가 아니라 "구조는 지키고 튜닝만 미룬다"로 표현을 바꾼다.

### 7.5 베이스라인 전진 배치

v1.0에서는 부하 테스트를 11주차에 처음 돌리는 것으로 잡았다. 이 배치에는 문제가 있다. 개선 전 수치를 그 시점에 처음 뽑으면 이미 열 주간의 변경이 섞여 있어서, 어떤 코드가 어떤 영향을 줬는지 분해할 수 없다.

그래서 k6 베이스라인을 W2로 옮긴다. 원장과 이체가 동작하기 시작한 직후, 인덱스도 캐시도 없는 상태에서 이체 엔드포인트에 대한 최초 측정치를 남긴다. 요구사항명세서 NFR-PERF-001의 이체 200밀리초 이내, 초당 100건 처리가 기준선이다.

이후 매주 같은 스크립트를 같은 조건으로 돌리고 결과를 저장소의 `perf/results` 아래에 커밋한다. 데이터 건수, 인스턴스 수, 컨테이너 자원 제한, 그리고 측정 시점에 떠 있던 Compose 프로파일을 매번 동일하게 고정하고 기록에 함께 남겨야 비교가 성립한다. 마지막 항목은 관측 스택이 떠 있는지 여부만으로도 수치가 흔들리기 때문에 필요하다.

이렇게 하면 두 가지를 동시에 얻는다. 하나는 진짜 개선 전 수치이고, 다른 하나는 어느 주차의 어떤 변경이 성능을 떨어뜨렸는지 즉시 잡아내는 회귀 감지다.

W6의 최적화는 반복 루프로 진행한다. 측정하고, 가장 큰 병목 하나만 고치고, 다시 측정하고, 결정 기록에 남기고, 다시 반복한다. 한 번에 여러 개를 고치면 무엇이 효과를 냈는지 알 수 없다. 기록에는 병목이 무엇이었는지, 어떻게 찾아냈는지, 무엇을 바꿨는지, 얼마나 나아졌는지에 더해 무엇을 대가로 내줬는지까지 적는다. 캐시를 넣으면 정합성 관리 부담이 늘고, 인덱스를 늘리면 쓰기가 느려진다. 이 트레이드오프를 함께 적는 것이 개선 수치만 나열하는 것보다 훨씬 설득력 있다.

최종 산출물은 7주간의 성능 추이 그래프다. 매주 같은 조건으로 찍은 점들이 이어지고, W6 구간에서 꺾이는 그래프 한 장이 개선 전후 수치 두 개보다 강하다.

## 8. 프론트엔드 트랙

W3부터 백엔드와 병행한다.

W3에는 Next.js 14 App Router 프로젝트를 스캐폴딩하고 Tailwind와 shadcn/ui를 설정한다. 화면플로우차트 문서의 화면을 프론트엔드기술스택 문서 8절의 라우트 표대로 디렉터리로 옮겨 빈 페이지만 먼저 만들어둔다. 배치는 폴더구조 문서 1절의 `apps/frontend` 트리를 따른다. 이어서 API 연동 레이어를 만든다. Axios 인스턴스 하나에 요청과 응답 인터셉터를 붙여 멱등성 키 자동 생성과 401 응답 시 재발급 후 한 번 재시도하는 로직을 넣는다. 위조 방지 토큰을 쿠키에서 읽어 헤더에 복사하는 처리도 같은 인터셉터에 둔다. 백엔드가 노출하는 명세에서 `openapi-typescript`로 타입을 생성하는 스크립트를 만들고 검증 단계에 넣어, 백엔드 계약이 바뀌면 프론트엔드 빌드가 깨지도록 만든다.

여기서 중요한 것이 프록시 구조다. 프론트엔드는 Vercel에, 백엔드는 AWS에 있어 도메인이 다르기 때문에 쿠키가 교차 사이트로 취급된다. SameSite=Lax 쿠키는 이 경우 전송되지 않는다. SameSite=None으로 낮추면 방어가 약해지므로, 대신 Next.js 라우트 핸들러로 `/api/proxy/[...path]` 경로를 만들어 브라우저는 항상 프론트엔드 도메인으로만 요청하고 서버 측에서 백엔드로 중계하도록 한다. 브라우저 기준으로 동일 출처가 되므로 쿠키 속성을 낮추지 않아도 되고 CORS 설정도 필요 없어진다.

이 프록시는 응답의 쿠키 헤더를 그대로 흘려보내는 것이 아니라 도메인 속성을 제거하고 경로를 정규화해야 한다. 백엔드 도메인이 그대로 남으면 브라우저가 다른 사이트의 쿠키로 판단해 저장하지 않는다. 이 처리를 빼먹으면 로그인이 성공했는데 다음 요청이 인증 실패로 돌아오는 증상이 나타나고, 원인을 찾기 어렵다.

W4에는 인증과 계좌 화면을 만든다. 로그인, 회원가입, 강화된 고객확인 입력, 홈 계좌 목록, 계좌 상세, 거래내역 조회다. 접근 제어는 미들웨어에서 쿠키 존재와 만료를 확인해 처리한다.

W5에는 거래 화면을 만든다. 입금, 출금, 이체 입력과 확인, 2차 인증 화면이다. 폼 검증은 React Hook Form과 Zod로 하고, 서버 도메인 에러코드를 폼 필드 에러로 변환하는 매핑 테이블을 상수 파일 하나로 관리한다. 잔액과 출금 가능 금액을 구분해 표시해야 한다는 점을 잊지 않는다. 두 값이 다를 수 있는데 잔액만 보여주면 사용자가 출금 거절 사유를 이해할 수 없다.

W6에는 상품 화면과 Playwright E2E 테스트를 만든다. 화면플로우차트 문서의 일곱 개 흐름을 그대로 시나리오로 옮기고, 이체는 임계 금액 이하와 초과 두 경로, 2차 인증 불일치와 만료 두 실패 경로까지 포함한다. Vercel 배포도 이 주에 붙이고 미리보기 배포가 Pull Request마다 생성되도록 연결한다. 저장소가 하나이므로 루트 디렉터리를 `apps/frontend`로 지정하고, 프론트엔드 경로에 변경이 없는 커밋은 빌드를 건너뛰도록 무시 조건을 설정한다.

한 가지 짚어둘 것은 이 병행이 진짜 병행이 아니라는 점이다. 혼자 하는 프로젝트에서 백엔드와 프론트엔드, 데브옵스를 같은 주에 배치했다는 것은 주당 40~50시간을 셋으로 쪼갠다는 뜻이다. 우선순위는 백엔드가 가장 높고 프론트엔드가 가장 낮다. 프론트엔드가 밀리면 화면 수를 줄이되, 화면플로우차트의 일곱 개 흐름 가운데 로그인, 계좌 조회, 이체 세 개는 시연에 필수이므로 반드시 지킨다.

## 9. 데브옵스 트랙 요약

데브옵스 작업은 위 주차 계획에 녹아 있지만, 트랙 관점에서 순서만 다시 정리하면 다음과 같다.

W1에 Docker Compose 로컬 환경과 프로파일 구성, GitHub Actions 기본 파이프라인과 경로 필터, W2에 Testcontainers 기반 통합 테스트 자동화와 k6 베이스라인 확보, W3에 이미지 빌드와 레지스트리 푸시 그리고 명세 스냅샷 드리프트 검사, W4에 Compose 메시징 프로파일 활성화, W6에 Prometheus와 Grafana, Loki 그리고 Terraform 모듈과 원격 상태 관리, W7에 EKS와 Helm, ArgoCD, 오토스케일링, 서비스 단위 배포 분리 순이다.

k6는 W2에서 한 번 만들고 끝나는 것이 아니라 매주 실행하는 항목이라는 점이 v1.0과 다르다. 실행 자체는 파이프라인에서 수동 트리거로 돌리고 결과 파일만 저장소에 커밋한다. Pull Request마다 자동으로 돌리면 파이프라인 시간이 감당되지 않는다.

이 순서의 원칙은 로컬에서 완결된 것만 클라우드로 올린다는 것이다. 로컬 Compose로 전체가 돌지 않는 상태에서 쿠버네티스로 넘어가면 문제가 애플리케이션에 있는지 인프라에 있는지 구분할 수 없게 된다.

## 10. 테스트 전략

계층별로 목표를 다르게 잡는다.

단위 테스트는 도메인 로직에 집중한다. 이자 계산, 계좌번호 채번과 체크디지트 검증, 위험도 산정 규칙, 금액 포맷 변환, 출금 가능 금액 계산처럼 순수한 계산 로직이 대상이다. 외부 의존이 없어 빠르게 돌아가므로 커밋마다 실행한다.

구조 테스트는 ArchUnit으로 폴더구조 문서 4절의 의존 방향 규칙을 검증한다. 이 테스트는 단일 모듈에서 경계를 지키는 유일한 강제 수단이므로 실패 시 병합을 막는다.

통합 테스트는 Testcontainers로 실제 데이터베이스와 캐시를 띄우고 서비스 계층부터 검증한다. 동시성과 멱등성 시나리오가 여기 속하며, 이 프로젝트에서 가장 가치 있는 테스트다.

API 테스트는 MockMvc로 요청과 응답 계약을 검증한다. 공통 응답 포맷과 에러코드가 문서대로 나오는지 확인하는 것이 목적이다.

E2E 테스트는 Playwright로 실제 브라우저 흐름을 검증한다.

커버리지 수치 자체를 목표로 삼지 않는다. 대신 원장, 이체, 인증 세 패키지에 대해서만 분기 커버리지 80퍼센트를 기준선으로 두고 파이프라인에서 강제한다. 나머지 영역까지 일괄로 높은 수치를 요구하면 의미 없는 테스트가 늘어난다.

일정을 압축한 만큼 테스트를 줄이고 싶은 유혹이 생기는데, 줄일 대상은 API 테스트와 E2E 테스트이지 통합 테스트와 구조 테스트가 아니다. 동시성 검증을 건너뛰면 이 프로젝트에서 보여줄 것의 절반이 사라지고, 구조 테스트를 빼면 단일 모듈 선택의 전제가 무너진다.

## 11. 주차별 완료 기준

| 주차 | 완료 기준 |
|---|---|
| W1 | Pull Request가 CI를 통과하고 ArchUnit 규칙이 초록불이며, 고객 등록 시 실명번호가 암호문으로 저장되고 동일 실명번호 재등록이 409로 거부된다 |
| W2 | 이체 한 건에 대해 원장 두 건이 기록되고 차변 합과 대변 합이 일치하며, 동시성 검증 시나리오 다섯 가지가 전부 통과하고 k6 베이스라인 수치가 저장소에 커밋되어 있다 |
| W3 | 로그인 응답에 세 쿠키가 실리고 위조 요청이 403으로 차단되며, 통합 시나리오 테스트가 통과하고 Compose 실행 한 번으로 전체가 뜨며 명세 스냅샷이 코드와 일치한다 |
| W4 | 계좌 상태 변경 시 감사 로그와 위험도 이력이 예외 없이 남고, 애플리케이션을 강제 종료해도 미발행 이벤트가 재기동 후 발행된다 |
| W5 | 대사 배치가 인위적으로 만든 불일치를 리포트로 잡아내고, 임계 금액 초과 이체가 인증 없이는 완료되지 않으며 만료 시 지급정지가 해제되어 출금 가능 금액이 원래대로 돌아온다 |
| W6 | 부하 테스트 개선 전후 수치가 대시보드 캡처와 함께 기록되고, 인프라를 전부 파괴한 뒤 Terraform으로 재생성해 동일하게 동작한다 |
| W7 | 배포 중 부하 스크립트 실패 요청이 0건이고, 사가 보상 트랜잭션이 원장에 기록되는 것을 확인한다 |

## 12. 리스크와 대응

가장 큰 리스크는 W2다. v1.0에서 이미 난이도가 가장 높다고 표시했던 두 주를 한 주로 접었기 때문이다. 난이도가 높은 작업은 투입 시간을 두 배로 늘려도 소요 시간이 절반으로 줄지 않는다. 원장과 동시성은 코드를 치는 시간보다 문제를 이해하고 검증 시나리오를 설계하는 시간이 지배적이라 시간 투입에 선형으로 반응하지 않는다. 이 주가 밀리면 뒤를 압축하지 말고 W7의 서비스 분리를 축소한다. 코어 도메인의 완성도가 마이크로서비스 구성보다 우선순위가 높다.

W1에서 모듈을 쪼개지 않기로 한 결정이 이 리스크에 대한 대응이기도 하다. 가장 어려운 작업을 하는 주에 모듈 경계 협상을 함께 하지 않게 된다.

두 번째는 트랙 병행이다. 8절에서 짚은 대로 백엔드와 프론트엔드, 데브옵스를 같은 주에 배치했다는 것은 주당 시간을 셋으로 나눈다는 뜻이지 세 배로 일한다는 뜻이 아니다. 문맥 전환 비용도 무시할 수 없다. 하루 단위로 트랙을 붙여 오전 백엔드, 오후 프론트엔드처럼 쪼개는 대신, 이틀 백엔드 뒤 하루 프론트엔드처럼 덩어리로 묶는 편이 낫다.

세 번째는 지속 가능성이다. 주당 40~50시간은 7주 내내 유지하기 쉽지 않은 강도다. 어느 주에 컨디션이 무너지면 그 주만 밀리는 것이 아니라 뒤가 연쇄로 밀린다. 주차 사이의 결합을 낮춰둔 v1.0의 설계 원칙은 그대로 유지하되, 각 주의 마지막 날은 그 주 완료 기준을 맞추는 데만 쓰고 다음 주 작업을 당겨오지 않는다.

네 번째는 클라우드 비용이다. 6주차 이후 인프라를 올린 채 방치하면 비용이 빠르게 누적된다. 워크스페이스를 분리하고, 작업이 끝날 때마다 파괴하는 것을 습관으로 만든다. 예산 알림도 미리 걸어둔다.

다섯 번째는 로컬 리소스다. PostgreSQL, Redis, Kafka, Prometheus, Grafana, Loki를 전부 동시에 띄우면 개발 머신이 버겁다. W1에서 Compose 프로파일을 나눠 필요한 것만 올리도록 구성한다. 전부 올리는 단축 명령은 만들지 않는다. 편의를 위해 만들어두면 습관적으로 쓰게 되고, 그러면 k6 측정 조건이 주차마다 달라진다.

여섯 번째는 범위 확장이다. 만들다 보면 기능을 더 붙이고 싶어지는데, 요구사항명세서에 없는 기능은 추가하지 않는다. 추가하고 싶은 것이 생기면 문서에 먼저 반영하고 우선순위를 재조정한 뒤에 착수한다. 7주 일정에서는 이 원칙이 v1.0 때보다 훨씬 엄격하게 지켜져야 한다.

## 13. 보류 항목

모의 전자서명 모듈은 **보류로 결정했다.** 이번 7주 범위에 넣지 않으며, 요구사항명세서에도 기능 요구사항으로 추가하지 않는다.

보류 근거는 두 가지다. 실제 금융권의 전자서명은 인증서 발급과 검증을 담당하는 외부 인프라 연동이 본질인데, 이를 자체 구현으로 모사하면 남는 것은 서명값 생성과 검증 로직뿐이라 기술적으로 보여줄 것이 적다. 그리고 구현과 검증에 최소 한 주가 드는데, 전체 일정이 7주라 한 주는 전체의 7분의 1이다.

전자서명의 실무적 대체 수단은 FR-AUTH-003의 OTP 2차 인증이며, 이 판단의 근거는 요구사항명세서 7.1절에 이미 정리되어 있다. 따라서 보류로 인해 비는 기능은 없다.

나중에 이 항목을 다시 꺼낸다면 전체 인증서 체계를 모사하는 방향보다, 이체 요청 본문에 대한 서버 측 무결성 검증을 넣는 쪽을 권한다. 클라이언트가 요청 시각과 본문 해시를 포함한 값에 서명하고 서버가 이를 검증하는 구조인데, 재전송 공격 방어와 요청 위변조 탐지라는 실질적인 효과가 있고 구현 비용은 하루 수준이다. 부인 방지라는 전자서명의 목적 가운데 시스템으로 증명 가능한 부분만 취하는 접근이다.

이 보류로 착수를 막는 미결 사항은 남아 있지 않다.

## 14. 다른 문서 반영 현황

구현 계획을 세우면서 확인한 기존 문서와의 불일치는 2026-07-26에 모두 해소했다. 착수 전에 문서를 먼저 고치고 시작한다는 원칙에 따라 코드 작성 전에 처리했다.

| 항목 | 반영 문서 | 상태 |
|---|---|---|
| 토큰을 쿠키로 발급하는 방식과 상태 변경 요청의 위조 방지 규칙 | API설계 v1.1의 2.2절, 2.8절, API-011/014/015 | 완료 |
| 지급정지 금액 컬럼과 출금 가능 금액 정의 | ERD v1.2의 2.2절, 요구사항명세서 v1.6의 1.3절과 FR-TXN-002 | 완료 |
| 이벤트 발신함 테이블 | ERD v1.2의 2.9절, 요구사항명세서 v1.6의 5절과 FR-SUP-002 | 완료 |
| 저장소를 단일 저장소로 전환 | 이 문서 3.1절, 폴더구조 v2.0 | 완료 |

보정 과정에서 문서 사이의 불일치 두 건이 추가로 발견되어 함께 처리했다.

첫째, 거래 상태값이다. API설계 문서는 `PENDING_OTP`를 응답 계약으로 노출하고 있었는데 ERD의 상태 목록에는 그 값이 없었다. 인증 대기와 취소를 표현할 수 없는 상태였다. ERD v1.2에 다섯 가지 상태와 허용 전이를 상태 기계로 정의하고, 이 문서 W2에 상태 열거형을 처음부터 전체 정의하도록 명시했다.

둘째, 계좌 해지 조건이다. 잔액 0원만 확인하도록 되어 있어서 인증 대기 중인 지급정지 금액이 남은 계좌가 해지될 수 있었다. 요구사항명세서 FR-ACC-004에 지급정지 금액 0원 조건을 추가하고 API설계에 에러코드를 신설했다.

두 건 모두 지급정지 개념을 반영하는 과정에서 드러난 것이다. 한 개념을 문서에 넣을 때 그 개념이 닿는 모든 절을 함께 훑어야 한다는 것을 보여주는 사례라, 앞으로 요구사항이 추가될 때도 같은 방식으로 점검한다.
