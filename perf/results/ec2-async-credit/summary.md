# 입금 비동기 반영 후 핫 계좌 측정 (s2f, 2026-09-30)

이체의 수신 측 반영을 입금 대기 + 수신 계좌별 묶음 반영으로 바꾼 뒤([ADR 0012](../../../docs/adr/0012-async-credit.md)), 개선 전 기준선
([`ec2-hot-account/summary.md`](../ec2-hot-account/summary.md))과 같은 s2f 조건으로 잰 결과다. 명세: `.claude/tasks/async-credit/task.md`.

## 조건

- 기준선과 같음: 대상 t3.small(unlimited), 부하 발생기 c7i.large, 1천만 건 시드, 초당 40건부터 1분마다 +10(상한 400), 병행 잔액 조회 초당 20건,
  회차 시작 절차, 무너짐 기준(p95 > 200ms·오류율 > 1%·재시작), 판정 코드.
- 다른 점
  - api 이미지: main에 없는 브랜치 코드라 대상 인스턴스에서 체크아웃한 커밋으로 빌드(`perf-<sha>`, Dockerfile 동일).
  - 측정 경계 전에 미반영 입금이 0이 될 때까지 기다리고, 정합성 식에 api 정지 시점의 미반영 입금을 포함.
  - r5는 정합성 SQL이 1천만 건 원장을 이체마다 훑어 멈춘 것을 고친 뒤(af89f3c) 후처리만 다시 실행. 부하·지표 수집은 이미 끝난 상태였다.
- 드라이런(상한 60) 정상: 정합성 전부 일치, 반영 지연 p95 226ms.

## 기준선과 비교

| 지표 | 개선 전(유효 6회) | 개선 후(6회) |
| --- | --- | --- |
| 무너진 요청률 중앙값(범위) | 95 (80~140) | 115 (80~200) |
| 최대 지속 중앙값 | 85 | 105 |
| 최대 처리 TPS 중앙값(범위) | 103.8 (87.7~140.6) | 115.1 (90~205.1) |
| 무너진 다음 단계가 회복한 회차 | 0/6 | 3/6 |

같은 부하 단계에서 보면 차이가 더 분명하다(회차별 값의 중앙값).

| 요청률 | 이체 p95 전 → 후 | 무관한 잔액 조회 p95 전 → 후 | 커넥션 대기 최대 전 → 후 | 대상 CPU 전 → 후 |
| --- | --- | --- | --- | --- |
| 80 | 71 → 24ms | 14 → 12ms | 24.5 → 0 | 43 → 46% |
| 90 | 238 → 35ms | 181 → 17ms | 20.5 → 0 | 48 → 49% |
| 100 | 395 → 28ms | 307 → 13ms | 67.5 → 0 | 51 → 53% |
| 110 | 295 → 78ms | 181 → 32ms | 87 → 30 | 58 → 59% |

- 개선 전에는 핫 계좌 행 락 대기가 커넥션 풀을 고갈시켜 무너진 뒤에도 다음 단계가 계속 나빴다(295~2,056ms). 개선 후에는 같은 부하에서
  커넥션 대기가 사라졌고, 받는 계좌 락 대기는 r1 90 단계에서도 최대 0.13초였다.
- 판정상 "무너짐"은 대부분 한 단계만 튀고 다음 단계에서 회복한 일시 정지다(r1·r3·r6). 튄 단계의 대상 CPU steal이 높았다(r2 110 단계 0.177,
  r3 80 단계 0.180, r1 90 단계 0.119). t3 인스턴스에서 다른 사용자와 CPU를 나눠 쓰는 시간이 부하와 겹칠 때 생기는 것으로 보이며, 상관만 관측했다.
- 지속적으로 무너진 r4(120 단계)는 CPU 71% → 100%로 포화됐다. 병목이 행 락에서 CPU로 옮겨 갔다. r4·r6이 무너진 120 단계는 k6 가상 사용자가
  BCrypt 재로그인을 시작하는 9분 시점과 겹친다. 개선 전에는 대부분 그 전에 무너져 드러나지 않던 측정 도구 부하다(재로그인을 뺀 p95 보조 값은
  판정을 바꾸지 않았다. r6 120 단계 2,787 → 2,658ms).

## 반영 지연(REQ-07, 목표 1초 이내)

- 6회 중 5회는 판정값 220~340ms로 목표 안이다. 초당 150건 이하 단계는 모든 회차에서 p95 404ms 이하.
- r5만 2,046ms로 목표를 넘었다. CPU 70~82%인 160~210 단계에서 반영 워커도 CPU·커넥션을 기다려 p95가 1.1~2.0초가 됐다.
  워커는 200ms 주기에 계좌당 최대 500건을 한 트랜잭션으로 반영하므로, CPU가 포화에 가까울수록 반영이 늦어진다.

## 정합성

- 모든 회차에서 새 불일치 계좌 0, 원장 행 = 2 × 이체 − 미반영, 차변 = 대변 + 미반영, 핫 계좌 증가분 + 미반영 = DB 완료 금액, 전체 증가분도 일치.
- 완료 이체마다 입금 대기 1건, 대변 원장은 반영된 건 1·미반영 건 0(중복·유실 0). api 정지 시점 미반영은 r4 986건, r5 246건이고 식에 포함했다.
- 타임아웃(실패)을 받았지만 실제로 완료된 이체가 r4에서 3,997건 나왔다. 기준선과 같은 현상이며 별도 과제(타임아웃 이체 중복 위험)다.

## 한계와 다음

- 무너짐 판정값은 CPU steal 일시 정지에 크게 흔들린다. 개선 효과를 말할 때는 같은 부하 단계의 지연·전파 비교를 우선 근거로 쓴다.
- 120 단계 이후는 재로그인 부하가 섞인다. 더 높은 구간을 공정하게 비교하려면 재로그인 시점을 늦추거나 테스트 토큰 TTL을 늘려야 한다.
- 다음 병목은 CPU다. 이체 한 건의 CPU 비용(감사 로그·트랜잭션 수)과 반영 워커 주기·묶음 크기가 다음 개선 대상이다.
