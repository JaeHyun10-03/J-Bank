# 입금 비동기 반영 후 핫 계좌 측정 (s2f, 2026-09-30)

이체의 수신 측 반영을 입금 대기 + 수신 계좌별 묶음 반영으로 바꾼 뒤([ADR 0012](../../../docs/adr/0012-async-credit.md)), 개선 전 기준선
([`ec2-hot-account/summary.md`](../ec2-hot-account/summary.md))과 같은 s2f 조건으로 잰 결과다. 명세: `.claude/tasks/async-credit/task.md`.

## 조건

- 기준선과 같음: 대상 t3.small(unlimited), 부하 발생기 c7i.large, 1천만 건 시드, 초당 40건부터 1분마다 +10(상한 400), 병행 잔액 조회 초당 20건,
  회차 시작 절차, 무너짐 기준(p95 > 200ms·오류율 > 1%·재시작), 판정 코드.
- 다른 점
  - api 이미지: main에 없는 브랜치 코드라 대상 인스턴스에서 체크아웃한 커밋으로 빌드(`perf-<sha>`, Dockerfile 동일).
  - 측정 경계 전에 미반영 입금이 0이 될 때까지 기다리고, 정합성 식에 api 정지 시점의 미반영 입금을 포함.
  - r5는 정합성 SQL이 1천만 건 원장을 이체마다 훑어 멈춘 것을 고친 뒤(af89f3c) 후처리만 다시 실행. 부하·지표 수집은 이미 끝난 상태였다.
  - 측정 이미지는 `perf-f535020`(`env/target/environment-target.md`). 운영 코드의 마지막 변경은 그 전 커밋 2d26adb이고, 측정 뒤에는 테스트·측정 도구·대시보드·문서만 바꿨다.
- 드라이런(상한 60) 정상: 정합성 전부 일치, 반영 지연 p95 226ms.

## 기준선과 비교

| 지표 | 개선 전(유효 6회) | 개선 후(6회) |
| --- | --- | --- |
| 무너진 요청률 중앙값(범위) | 95 (80~140) | 115 (80~200) |
| 최대 지속 중앙값 | 85 | 105 |
| 최대 처리 TPS 중앙값(범위) | 103.8 (87.7~140.6) | 115.1 (90~205.1) |
| 무너진 다음 단계가 회복한 회차(p95 ≤ 200ms) | 0/6 | 3/6 (r1·r2·r3) |
| 무너질 때 무관한 조회로 전파 | 6/6 | 6/6 (변화 없음) |

같은 부하 단계에서 보면 차이가 더 분명하다. 그 단계를 실제로 돈 회차(기준선 유효 r2~r7, 개선 후 r1~r6)의 `analysis.json` 단계 값 중앙값이고,
양쪽을 같은 계산으로 다시 냈다(1회차 요약은 개선 후 r6을 빠뜨려 고침).

| 요청률 | 회차 수 전/후 | 이체 p95 전 → 후 | 무관한 잔액 조회 p95 전 → 후 | 커넥션 대기 최대 전 → 후 | 대상 CPU 평균 전 → 후 |
| --- | --- | --- | --- | --- | --- |
| 80 | 6 / 6 | 71 → 25ms | 14 → 12ms | 24.5 → 0 | 43 → 46% |
| 90 | 6 / 6 | 238 → 35ms | 181 → 17ms | 20.5 → 0 | 48 → 49% |
| 100 | 4 / 5 | 395 → 33ms | 307 → 15ms | 67.5 → 0 | 51 → 53% |
| 110 | 4 / 4 | 302 → 66ms | 201 → 29ms | 47 → 15 | 59 → 59% |

- 기준선 r2의 110 단계는 무너진 뒤 감시가 k6를 멈추기 전 7초(742건) 꼬리 구간이다. 요청이 있는 단계를 모두 넣는 같은 규칙이라 포함했고,
  나머지 칸은 50초를 다 채운 단계다.

- 개선 전에는 핫 계좌 행 락 대기가 커넥션 풀을 고갈시켜 무너진 뒤에도 다음 단계가 계속 나빴다. 개선 후에는 110 단계 전까지 커넥션 대기
  중앙값이 0이 됐고, 받는 계좌 락 대기는 r1 90 단계에서도 최대 0.13초였다.
- 무너질 때 무관한 조회로 번지는 것(전파)은 6/6으로 기준선과 같다. 무너진 단계에서는 여전히 풀이 밀려 다른 요청도 느려진다. 달라진 것은
  무너지는 지점과 그 뒤 회복이다. 다음 단계에서 회복한 회차는 r1·r2·r3(3/6)이고 r4·r5·r6은 다음 단계도 200ms를 넘었다.
- 일시 정지와 CPU steal: 튄 단계의 대상 CPU steal 단계 내 최대값(Prometheus 5초 간격)이 높았다(r2 110 단계 0.177, r3 80 단계 0.180,
  r1 90 단계 0.119). 단계 평균(`target_steal_avg`)은 0.04~0.08이다. 반례도 있다. 부하가 낮은 r1 40·50 단계는 steal 최대 0.155·0.175에도
  정상이었다. 다른 사용자와 CPU를 나눠 쓰는 시간이 높은 부하와 겹칠 때 생기는 것으로 보이지만 상관만 관측했고 원인은 확정하지 못했다.
- 지속적으로 무너진 r4(120 단계)는 CPU 71% → 100%로 포화됐다. 병목이 행 락에서 CPU로 옮겨 갔다. r4·r6이 무너진 120 단계는 k6 가상 사용자가
  BCrypt 재로그인을 시작하는 9분 시점과 겹친다. 개선 전에는 대부분 그 전에 무너져 드러나지 않던 측정 도구 부하다(재로그인을 뺀 p95 보조 값은
  판정을 바꾸지 않았다. r6 120 단계 2,787 → 2,658ms).

## 반영 지연(REQ-07, 목표 1초 이내)

- 원래 기준(계획 Q-05)은 "무너지기 전 모든 단계에서 p95 1초 이내"였다. 이 기준으로 r5가 160 단계 2,046ms, 180 단계 1,271ms로 넘었다.
- 결과 리뷰 뒤 2026-10-01에 사용자 결정으로 판정 범위를 "초당 150건 이하이면서 무너지기 전인 단계"로 좁혔다(측정 뒤 조정, 재측정 없음).
  150은 기준선이 무너진 최대 요청률 140 바로 위 단계다. 개선 전 구조가 버티지 못한 부하에서의 반영 지연을 보자는 뜻이고, 그 위는 기록만 한다.
- 좁힌 기준으로는 6회 모두 충족한다. 판정값 r1 281, r2 340, r3 220, r4 333, r5 404, r6 266ms.
- 150 초과 단계(r5만 해당, 무너지기 전): 160 2,046ms, 170 434ms, 180 1,271ms, 190 677ms. 160 단계는 대상 CPU 평균 74%, 커넥션 대기 최대 148이었다.
  워커가 API와 같은 풀(10개)을 쓰므로 CPU와 풀 대기 둘 다 원인 후보이고 확정하지 못했다.
- 무너진 단계와 그 뒤에는 반영도 크게 밀린다. r1 90 단계 824ms, r6 120 단계 3,206ms, r4 120 단계 12,357ms, 130 단계 53,618ms.
  과부하에서는 받는 사람에게 입금이 수십 초 늦게 보일 수 있다.
- 반영 지표(미반영 수·가장 오래된 나이·반영 지연 Timer)는 이번 측정 대시보드에 패널이 없어 EC2 원자료에 시계열이 없다. 패널을 추가했고
  로컬에서 적체를 만들어 수집을 확인했다(`.claude/tasks/async-credit/logs/credit-metrics.log`). 적체는 위 단계별 지연 증가로만 관측했다.

## 정합성

- 모든 회차에서 새 불일치 계좌 0, 원장 행 = 2 × 이체 − 미반영, 차변 = 대변 + 미반영, 핫 계좌 증가분 + 미반영 = DB 완료 금액, 전체 증가분도 일치.
- 완료 이체마다 입금 대기 1건, 대변 원장은 반영된 건 1·미반영 건 0(중복·유실 0). api 정지 시점 미반영은 r4 986건, r5 246건이고 식에 포함했다.
- 타임아웃(실패)을 받았지만 실제로 완료된 이체가 r4에서 3,997건 나왔다. 기준선과 같은 현상이며 별도 과제(타임아웃 이체 중복 위험)다.

## 한계와 다음

- 무너짐 판정값은 CPU steal 일시 정지에 크게 흔들린다. 개선 효과를 말할 때는 같은 부하 단계의 지연·전파 비교를 우선 근거로 쓴다.
- 120 단계 이후는 재로그인 부하가 섞인다. 더 높은 구간을 공정하게 비교하려면 재로그인 시점을 늦추거나 테스트 토큰 TTL을 늘려야 한다.
- 다음 병목은 CPU다. 이체 한 건의 CPU 비용(감사 로그·트랜잭션 수)과 반영 워커 주기·묶음 크기·전용 커넥션이 다음 개선 대상이다.
- 핫 행에 KEY SHARE가 여럿 걸린 채 UPDATE가 반복될 때의 MultiXact 비용이 일시 정지에 기여하는지는 조사하지 않았다.
