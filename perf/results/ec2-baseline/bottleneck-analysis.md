# EC2 기준선 병목 분석 (개선 전, 재측정)

회차별 수치는 [summary.md](summary.md), 원자료는 각 `<시나리오>/<회차>/`. 이 문서는 후속 작업(입금 비동기 반영)과 그 밖의
개선 후보를 고르는 근거다. 수치는 대표값(유효 회차 중앙값), 괄호는 회차 범위. 1차 측정(`first-pass/`)은 결함 때문에 대표값에
쓰지 않고, 재현된 사고(가설 E)의 근거로만 인용한다.

## 한 줄 결론

운영과 같은 t3.small 한 대는 **혼합 부하 초당 100건에서 무너진다**(3/3, 최대 지속 가능 초당 50건). 원인은 시나리오마다 다르다.
평소 혼합 부하는 **CPU 포화**(로그인이 가장 무거움), 한 계좌로 이체가 몰리면 **행 락 대기 → 커넥션 풀 고갈 → 관계없는 조회까지
느려짐**(초당 80건), 급증은 **대기열이 쌓여 100초간 회복하지 못함**이다. 어느 경우에도 원장·잔액 정합성은 깨지지 않았지만,
**클라이언트가 타임아웃(실패)을 받은 이체가 사실상 전부 실제로 완료**됐다(멱등키 대조).

참고로 NFR-PERF-001은 "이체 200ms 이내, 초당 100건"으로 이체 단독 기준이다. S1의 초당 100건은 혼합 부하(이체는 그중 20%)라
NFR과 같은 조건이 아니다. 이체만 몰리는 S2에서는 한 계좌에 초당 80건이 모이면 무너졌다.

## 가설별 판정

| 가설 | 판정 | 근거 |
| --- | --- | --- |
| A. 핫 계좌 락 → 커넥션 풀 고갈 → 조회 API 전파 | **확인** | S2 3회 모두. 무너진 단계에서 계좌 락 대기 최대 0.77s(0.72~1.12), PG 락 대기 세션 9(1~9), Hikari 대기 99(45~192). 대상 CPU 46%(45~59%)로 여유 — CPU가 아니라 락이 원인. 핫 계좌와 무관한 잔액 조회 p95가 8ms → 1,397ms(162~6,685ms), 전파 3/3 |
| B. 커넥션 풀 10·Tomcat 200 비율, 급증 후 회복 지연 | **확인** | S3 3회 모두. 목표 초당 500건에 실제 172.4건/s, 오류 88.1%, 10초 타임아웃 약 1.2만 건, 대기열이 넘친 요청 일부는 caddy 502(29~172건). Hikari 대기 192 = Tomcat 200 스레드 중 10개만 DB를 쓰고 나머지가 줄을 섬. 부하 중단 후 탐침 p95 회복까지 100초(75~145) → 3/3 미회복. 이번에는 관리 포트 분리로 스파이크 구간 api 지표가 끊기지 않아 이 값이 직접 관측됐다 |
| C. 로그인 BCrypt CPU | **부분 확인** | S1은 락 대기 없이(계좌 락 0.09s, PG 락 대기 0) CPU 83%(80~84%)에서 무너짐 → CPU 포화. 서버 측 API별 p95(초당 50건 단계)에서 로그인 315ms(263~374)로 이체 39ms·잔액 12ms의 8~26배, 초당 100건에서 약 715ms. 로그인은 요청의 10%뿐인데 가장 무겁다. 로그인 비중을 바꿔 CPU 기여를 분리하는 S4는 범위 밖(Q-04)이라 기여도는 미확정 |
| D. 마감 배치와 온라인 경합 | **확인(무너짐까지는 아님)** | S5 3회. CTR 판별 쿼리가 하루치만 보면서 1천만 건 **Parallel Seq Scan 9.1초**(9,023~9,152ms, 디스크 약 1.2GB 읽음) — `(transaction_type, status, processed_at)` 인덱스 없음. CTR이 신규 적재한 것은 200건(준비 단계의 1억 원 현금 입금), FDS는 하루 이체 약 6,600건 처리. 부하 중 배치 수행 시간 1.31~1.54배, 배치 구간 CPU 75~94%, 온라인 p95 99ms → 배치 구간 최대 220ms(9구간 중 2구간 200ms 초과, 모두 대사 구간). 초당 35건에서 무너지지 않음, 배치 밖 포화 없음 |
| E. 2GB 메모리 한계 | **확인(1차 측정 사고로 재현)** | `first-pass/s1/incident-r1-memory/`: 무너진 뒤 api 컨테이너 약 1GB 상태에서 대사 잡 JVM(512MB)이 더 뜨자 가용 메모리 807MB → 127MB, 메이저 페이지 폴트 초당 169건, 수집 대상 전부 down, SSM 끊김 → 재부팅 전까지 약 50분 무응답. OOM 킬 없이 스래싱으로 멈춤(자동 재시작도 안 됨). 재측정에서는 이를 피하려고 정합성 확인 대사 전에 api를 멈췄다. 재측정 S3 스파이크 중 가용 메모리 60~67MB, S5 배치 구간 204~241MB. 운영은 관측 도구까지 같은 인스턴스에 있어 여유가 더 적다 |

## 금융 관점에서 가장 중요한 발견: 실패 응답인데 실제로 완료된 이체

| 시나리오 | 실패 응답(체크 실패) | 그중 DB에 완료로 반영(멱등키 대조) | 중단 순간 잔차(키 없음) |
| --- | --- | --- | --- |
| S1 (3회) | 1,723 / 579 / 844 | 체크 실패 전부(100%). 상태는 모두 0(10초 타임아웃) | 37 / 163 / 207 |
| S2 r2 (무너져 오류가 난 회차) | 7,257 | 체크 실패 전부(100%), 상태 0 | 635 |
| S2 r1·r3 (지연만 커진 회차) | 0 / 0 | 0 / 1 | 1 / 0 |
| S3 (3회) | 2,794 / 2,856 / 2,807 | 타임아웃 2,672 / 2,827 / 2,633 전부 또는 거의 전부(2,635 중 2,633), 502는 0건 | 0 |
| S5 (3회) | 0 | 0 | 0 |

k6는 10초에 요청을 끊지만 서버는 줄 서 있던 요청을 계속 처리해 커밋한다. 원장·잔액은 맞다(차변=대변, 새 불일치 0, 멱등키 중복 0).
하지만 고객 화면에는 "실패"로 보인 이체가 돈은 빠져나간 상태다. S3에서는 완료된 이체의 약 89%가 고객에게 실패로 보였다.
같은 멱등키로 재시도하면 원래 결과를 돌려받아 안전하지만, 고객이 새로 이체하면 **중복 송금**이 된다. 반대로 caddy가 돌려준 502는
한 건도 반영되지 않았다 — "실패"의 의미가 응답 종류에 따라 다르다. 개선 후보: 서버 측 처리 시간 상한(대기열 제한)으로 늦게 커밋되는
요청 줄이기, 과부하 시 빠른 거절(429/503)로 "애매한 실패" 대신 "명확한 실패" 주기, 멱등키로 결과를 조회하는 API로 클라이언트가
확정 상태를 확인하게 하기.

1차 측정은 이 값을 "새 완료 − 201"로 계산해 k6 중단 순간 처리 중이던 요청까지 섞었다(예: 1차 S2의 723건 대부분). 재측정은 멱등키
대조로 실패 응답 반영과 중단 잔차를 나눴다.

## 측정 한계

- 대상은 운영과 같은 사양이지만 관측 도구가 없어 메모리 여유가 운영보다 크다(가설 E는 운영에서 더 나쁠 수 있다).
- api 지표는 `/actuator/prometheus`가 인증을 요구해 perf 전용 계정으로 로그인하는 프록시로 수집했다. 1차 측정에서는 이 수집이 본 포트
  Tomcat을 거쳐 포화 구간에 끊겼다. 재측정은 관리 엔드포인트를 별도 포트(9095)로 분리하고 프록시 재로그인을 백그라운드로 옮겨 모든 회차
  결측 0이다. 관리 포트 분리는 운영과의 차이다.
- 계좌 락 대기 지표(`db.lock.wait`)는 `@Timed` 최대값 기준이다. PG 락 대기 로그는 `deadlock_timeout`(1초)을 넘긴 대기만 남는다.
- S2의 무너지는 지점은 80~100으로 흔들린다(락 대기열이 쌓였다 풀리는 성질). 대표값은 3회 중앙값.
- 실패 응답 반영의 k6 SIGINT 영향: S1·S2는 무너진 뒤 한 단계 더 가서 k6를 멈추므로 끊긴 요청의 키가 체크 실패 수보다 많이 남는다
  (예: S1 r1 1,887 대 1,723). 표의 "체크 실패 전부 반영"은 이 차이를 뺀 하한이다.
- 1차 측정의 배치 수행 시간은 종료 시각을 로그 후처리 뒤에 재 약간 부풀었을 수 있다(대사 잡). 재측정은 실행 직후에 잰다.
- 로그인 비중·장시간(S4·S6)은 범위 밖이다.

## 후속 작업에 넘길 것

1. **입금(수신 측) 비동기 반영 — 가설 A 대상(확정 근거 있음).** 비교 기준: S2 대표값(무너짐 초당 80건, 최대 지속 60건, 무너진 단계 이체
   p95 1,561ms, 병행 조회 p95 8 → 1,397ms, 전파 3/3, 락 대기 0.77s). 같은 절차(`perf/run-ec2.sh s2 <회차>`)로 재측정한다.
2. CTR 판별 배치 인덱스 — 가설 D. 비교 기준: CTR 쿼리 9,105ms(Parallel Seq Scan), 배치 46s(부하 중)/35s.
3. 과부하 시 빠른 거절·서버 측 처리 시간 상한 — 가설 B와 "실패 응답인데 반영". 비교 기준: S3 회복 100초, 반영 2,672건.
4. 배치를 api와 같은 2GB 인스턴스에서 돌리는 운영 cron의 메모리 위험 — 가설 E.
5. 로그인 CPU 분리 측정(S4) — 가설 C.
