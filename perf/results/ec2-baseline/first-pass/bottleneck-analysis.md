# EC2 기준선 병목 분석 (개선 전)

회차별 수치는 [summary.md](summary.md), 원자료는 각 `<시나리오>/<회차>/`. 이 문서는 후속 작업(입금 비동기 반영)과
그 밖의 개선 후보를 고르는 근거다. 수치는 대표값(중앙값), 괄호는 회차 범위.

## 한 줄 결론

운영과 같은 t3.small 한 대는 **혼합 부하 초당 100건에서 무너진다**(NFR-PERF-001이 요구하는 초당 100건과 같은 지점).
무너지는 원인은 시나리오마다 다르다. 평소 혼합 부하는 **CPU 포화**(로그인 BCrypt가 가장 무거움), 한 계좌로
이체가 몰리면 **행 락 대기 → 커넥션 풀 고갈 → 관계없는 조회까지 느려짐**, 급증은 **대기열이 쌓여 85초간 회복하지
못함**이다. 어느 경우에도 원장·잔액 정합성은 깨지지 않았지만, **클라이언트가 실패(타임아웃)를 받은 이체가 실제로는
완료된 건이 회차마다 수백~수천 건** 생겼다.

## 가설별 판정

| 가설 | 판정 | 근거 |
| --- | --- | --- |
| A. 핫 계좌 락 → 커넥션 풀 고갈 → 조회 API 전파 | **확인** | S2 4회 모두. 무너진 단계에서 계좌 락 대기 최대 0.84s(0.52~1.12), PG 락 대기 세션 8~9, Hikari 활성 10/10에 대기 120(36~188). 대상 CPU는 56%(49~69%)로 여유 — CPU가 아니라 락이 원인. 핫 계좌와 무관한 잔액 조회 p95가 10ms → 744ms(377~2,281ms)로 약 75배(최대 250배) 느려짐 → 장애 전파 4/4 |
| B. 커넥션 풀 10·Tomcat 스레드 200 비율, 급증 후 회복 지연 | **확인** | S3 3회 모두. 목표 초당 500건에 실제 처리 176건/s, 오류 89%, 10초 타임아웃 약 1.2만 건. Hikari 대기 최대 189 = Tomcat 200개 중 10개만 DB를 쓰고 나머지가 줄을 섬. 부하를 멈춘 뒤에도 쌓인 요청을 처리하느라 탐침 p95가 회복하는 데 85초(75~110) → 3/3 미회복. S1 초당 150건 단계도 같은 모양(Tomcat 200 포화, Hikari 대기 약 190) |
| C. 로그인 BCrypt CPU | **부분 확인** | S1은 락 대기 없이(계좌 락 0.04~0.14s, PG 락 대기 0) CPU 84~95%에서 무너짐 → CPU 포화가 원인. 서버 측 API별 p95(s1/r1, 초당 50건 단계)에서 로그인 297ms로 다른 API(11~52ms)의 6~27배, 초당 100건에서 793ms. 로그인은 요청의 10%뿐인데 가장 무겁다. 다만 로그인 비중을 바꿔 CPU 기여를 분리 측정하는 S4는 이번 범위 밖(Q-04)이라 기여도는 미확정 |
| D. 마감 배치와 온라인 경합 | **확인(무너짐까지는 아님)** | S5 3회. CTR 판별 쿼리가 하루치만 보면서도 1천만 건 **Parallel Seq Scan 9.1초**(디스크 152,710블록 ≈ 1.2GB 읽음) — `(transaction_type, status, processed_at)` 인덱스 없음. 부하 중 배치 수행 시간 1.34~1.49배, 배치 구간 CPU 71~96%, 온라인 p95 105ms → 배치 구간 158~223ms(9구간 중 3구간이 200ms 초과). 초당 35건(최대 지속의 70%)에서는 무너지지 않음. 배치는 하루치만 처리하므로 "1천만 건 전체 처리"가 아니라 "인덱스 없는 하루치 조회가 전체를 읽는 비용"이 문제 |
| E. 2GB 메모리 한계 | **확인(사고로 재현)** | 첫 S1 r1 시도(`s1/incident-r1-memory/`): 무너진 뒤 api 컨테이너 약 1GB(힙 512MB + 스레드 200개 스택 등)인 상태에서 대사 잡 JVM(512MB)이 더 뜨자 가용 메모리 807MB → 127MB, 메이저 페이지 폴트 초당 169건, 수집 대상 전부 down, SSM 연결 끊김 → 재부팅 전까지 약 50분 무응답. OOM 킬은 일어나지 않고 스래싱으로 멈춤(더 나쁨: 자동 재시작도 안 됨). S3 스파이크 중 가용 메모리 58~81MB. 운영은 관측 도구(Prometheus·Grafana)까지 같은 인스턴스에 있어 이 측정보다 여유가 더 적다(측정은 관측 도구를 부하 발생기로 옮김 → 낙관적) |

## 금융 관점에서 가장 중요한 발견: 실패 응답인데 실제로 반영된 이체

| 시나리오 | 클라이언트 성공(201) | 실제 완료 | 실패 응답인데 반영 |
| --- | --- | --- | --- |
| S1 (중앙값) | 5,980 | 7,620 | 1,640 (21.5%) |
| S2 (중앙값) | 22,538 | 23,111 | 393 |
| S3 (중앙값) | 269 | 2,960 | 2,685 (약 90%) |
| S5 | 8,434 | 8,434 | 0 |

k6는 10초에 요청을 끊지만 서버는 줄 서 있던 요청을 계속 처리해 커밋한다. 원장·잔액은 맞다(차변=대변, 새 불일치
0, 멱등키 중복 0). 하지만 고객 화면에는 "실패"로 보인 이체가 돈은 빠져나간 상태다. 같은 멱등키로 재시도하면 원래
결과를 돌려받아 안전하지만, 고객이 새로 이체하면 **중복 송금**이 된다. 무너짐 자체보다 이 불일치가 금융 서비스에서 더
큰 위험이다. 개선 후보: 요청 처리 시간 상한(서버 측 타임아웃·대기열 제한)으로 늦게 커밋되는 요청을 줄이기, 과부하 시
빠른 거절(429/503)로 "애매한 실패" 대신 "명확한 실패"를 주기, 결과 조회 API로 클라이언트가 멱등키 상태를 확인하게 하기.

## 측정 한계

- 대상은 운영과 같은 사양이지만 관측 도구가 없어 메모리 여유가 운영보다 크다(가설 E는 운영에서 더 나쁠 수 있다).
- api 지표는 `/actuator/prometheus`가 인증을 요구해 perf 전용 계정으로 로그인하는 프록시로 수집했다(5초마다 1회, 서버
  기준 60~106ms). 부하에 비해 무시할 수준이지만 운영과의 차이다.
- 계좌 락 대기 지표(`db.lock.wait`)는 `@Timed` 최대값 기준이라 짧은 구간 안의 분포는 보지 못한다. PG 락 대기 로그는
  `deadlock_timeout`(1초)을 넘긴 대기만 남는다.
- S2의 무너지는 지점은 회차마다 60~100으로 흔들린다(락 대기열이 쌓였다 풀리는 성질). 대표값은 4회 중앙값.
- 로그인 비중·장시간(S4·S6)은 범위 밖이다.

## 후속 작업에 넘길 것

1. **입금(수신 측) 비동기 반영 — 가설 A 대상(확정 근거 있음).** 비교 기준: S2 대표값(무너짐 초당 90건, 최대 지속 70건,
   무너진 단계 이체 p95 916ms, 병행 조회 p95 10 → 744ms, 전파 4/4). 같은 절차(`perf/run-ec2.sh s2 <회차>`)로 재측정한다.
2. CTR 판별 배치 인덱스 — 가설 D. 비교 기준: CTR 쿼리 9,146ms(Parallel Seq Scan), 배치 43s(부하 중)/32s.
3. 과부하 시 빠른 거절·서버 측 처리 시간 상한 — 가설 B와 "실패 응답인데 반영". 비교 기준: S3 회복 85초, 반영 2,685건.
4. 배치를 api와 같은 2GB 인스턴스에서 돌리는 운영 cron의 메모리 위험 — 가설 E.
5. 로그인 CPU 분리 측정(S4) — 가설 C.
