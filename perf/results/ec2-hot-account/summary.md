# 핫 계좌 정밀 기준선 (s2f, 2026-09-28)

입금 비동기 반영 작업의 개선 전 비교 기준이다. 명세: `.claude/tasks/hot-account-baseline/task.md`.
기존 S2 기준선(`perf/results/ec2-baseline/`)보다 단계를 촘촘하게(초당 10건) 나누고 회차를 늘려 무너지는 지점과 핫 계좌 최대 처리량의 분산을 본다.

## 조건

- 대상 t3.small(credit unlimited), 부하 발생기 c7i.large, 1천만 건 시드. 앱 이미지·스택·회차 시작 절차(복원 → 캐시 비움 → 재기동 → 예열 2분 → 경계 기록)는 기존 기준선과 같다.
- 인스턴스 체크아웃: `perf/hot-account-baseline` 32f9f58(`env/target/environment-target.md`).
- 부하: 발신 고객 200명 → 핫 수신 계좌 1개로 1,000원 이체. 초당 40건에서 시작해 1분마다 +10(상한 400). 무관한 계좌 잔액 조회를 초당 20건으로 60초 먼저 시작해 끝까지 유지.
- 무너짐: 단계 구간(시작 10초 제외)의 이체 p95 > 200ms, 오류율 > 1%, 재시작·OOM 중 하나. 무너진 뒤 한 단계 더 가고 중단.
- 사전 검증: `dryrun/20260928-154742`(상한 60, 40·50·60 단계). 결과물 누락 없음, 결측 없음. 기준선에서 제외.

## 회차별 결과

최대 처리 TPS = 단계를 다 채운 구간(50초)에서 hot-transfer가 201을 받은 건수 ÷ 구간 길이의 최댓값. 감시가 k6를 멈추기 전까지 돈 다음 단계 앞부분(6~7초)은 뺐다.
분석 파일(`analysis.json`)의 `max_success_tps`는 이 규칙을 넣기 전(aff5bff) 코드로 계산돼 r2(106.0 @110)와 r4(119.7 @120)에는 그 짧은 구간 값이 들어 있다. 아래 표는 같은 파일의 단계 값에 규칙을 적용한 값이다.

- ※ 그 단계에 드롭이 있어 실제 제공 부하가 목표보다 낮았다. 이 값은 "목표 부하를 다 받지 못한 상태의 처리율"이다. r4는 드롭 확정 12건이 있지만 단계 추정이 모두 null이라 어느 단계인지 알 수 없어 ※를 붙이지 않았다.
- 201 확정은 k6 요약의 `hot-transfer 201` passes, 추정은 Prometheus `increase()` 합(이체 구간 전체)이다. 차이는 0.0~0.8%.
- 드롭 확정은 k6 요약의 `dropped_iterations.count`, 단계 추정은 Prometheus 값이다. 추정이 null이면 "수집 없음"으로 적고 0으로 바꾸지 않았다.
- 이체 실패 확정값은 k6 체크 실패 수와 실패 키 파일(모두 상태 0: 10초 타임아웃 또는 k6 중단 순간 끊긴 요청)이다.
  분석 파일의 단계별 `failed`는 전 회차 0이다. r3의 실패 키 588건은 k6.log 시각 기준 150 단계 안(끝 3초)에 89건, 단계가 끝난 뒤
  감시의 판정 대기(15초)와 중단 순간에 499건이다. 150 단계의 89건은 실패가 처음 생긴 순간 만들어지는 시계열의 첫 값을 `increase()`가
  세지 못해 빠졌고, 나머지는 요청 수조차 0으로 잡힌 짧은 뒷구간(160)에 있다. 그래서 실패 수는 k6 확정값으로 대신한다.
- 이체 외 실패는 r3에만 있다: 무관한 잔액 조회 `parallel-balance 200` 실패 78건, 재로그인 `relogin 200` 성공 315·실패 1,418건
  (k6 `http_req_failed` 1,953 = 이체 457 + 재로그인 1,418 + 잔액 조회 78). 다른 회차는 이체 외 실패 0건, 재로그인 0~22건이다.
- 부하 발생기 CPU 최대 4~16%(기준 80% 이하), 모든 회차 결측 없음(`gaps.txt` invalid=no).

r1을 넣은 7회 기준이면 무너진 요청률 중앙값 100, 최대 처리 TPS 중앙값 109.7이다(r1 제외는 명세의 무효 사유 목록에 없는 절차 조건 차이로 판단했다).

- r3을 빼면 무너짐 80~100, 최대 처리 TPS 87.7~112.0이다. 6회 중 5회가 80~100에서 무너졌다.
- 회차 구성: r1은 참고 회차다. 로컬 맥이 덮개 닫힘·배터리 상태로 잠들어 예열이 끝나고 약 37분 뒤에 측정을 시작했고, 절차 조건이 달라 대표값에서 뺐다. r6은 r1을 대신한 회차, r7은 변동폭 규칙(r2 90 대 r3 140, 한 단계 초과)으로 추가한 회차다. r7 뒤에도 폭은 한 단계를 넘지만 규칙상 추가는 1회까지라 원인만 기록한다.

## 무너지는 방식

- 무너진 단계의 대상 CPU는 44~66%로 CPU 한계가 아니다. 무너진 단계에서 핫 계좌 행 락 대기가 최대 0.36~1.02초, PostgreSQL 락 대기 세션이 최대 1~9개, Hikari 대기 요청이 49~123개였다. 한 계좌 행에 이체가 줄을 서는 동안 커넥션 10개가 잡혀 있고 나머지 요청은 풀에서 기다린다.
- 전파: 모든 회차(7/7)에서 무너진 단계의 무관한 잔액 조회 p95가 시작 전 6~11ms에서 193~1,115ms로 올랐다. 핫 계좌 하나가 전체 API를 늦춘다.
- 무너진 뒤에도 성공 처리율은 목표 요청률을 거의 따라갔다(r1 100단계 98.9, 110단계 110.0). 오류 없이 지연이 늘어나는 형태다. 이체 오류(타임아웃)는 r3에서만 나왔다(150 단계 끝과 그 뒤 중단 전 구간).
- r3이 튄 원인은 단정하지 못했다. CPU 크레딧은 전 회차 68.6~106.2로 남아 있었고 초과 크레딧 과금(CPUSurplusCreditsCharged)은 0이었다. 무너진 단계의 대상 steal이 r3 1.6%로 다른 회차(3.4~7.6%)보다 낮았다. 같은 사양이라도 호스트 이웃 부하에 따라 락 보유 시간이 달라져 줄 서기가 폭발하는 지점이 옮겨 갈 수 있다(상관만 관측).
- 재로그인 섞임: k6 VU는 토큰 발급 후 9~12분에 재로그인한다(`perf/k6/lib/ec2.js`). s2f에서 9분은 120 단계라, 120 단계를 넘긴 r3만 120~150 단계 통계(시나리오 태그 `hot_transfer`)에 bcrypt 로그인 요청이 섞였다. 재로그인은 부하를 더하는 쪽이라 r3의 높은 무너짐 지점을 설명하지는 않지만, 그 구간의 p95·오류율은 이체만의 값이 아니다.

## 정합성 (전 회차)

- 새 불일치 계좌 0, 전체·새 원장 차변 = 대변, 핫 계좌 잔액 증가분 = DB 완료 이체 금액 합, 경계 이후 멱등키 중복 0, 대사 잡 COMPLETED.
- 핫 계좌 증가분과 k6 201 × 1,000원의 차이는 실패 키 중 반영(r2 11, r3 373, r4 5, r5 1, r7 1건. r3은 실패 응답 중 반영 하한 242)과 중단 잔차(r2 12, r4 7, r5·r6 1건)로 모두 설명된다(`s2f/r<n>/integrity.md`). 기존 기준선과 같이 타임아웃을 받은 이체도 대부분 실제로 완료됐다.

## 기존 S2 기준선과의 관계

| 항목 | 기존 S2 (ec2-baseline/s2) | s2f (이 문서) |
| --- | --- | --- |
| 단계 | 초당 20건 시작, +20 | 초당 40건에서 바로 시작, +10 |
| 회차 | 3회 | 유효 6회(+참고 1회) |
| 무너진 요청률 | 80 / 100 / 80 | 90 / 140 / 100 / 80 / 100 / 80 (중앙값 95) |
| 최대 지속 | 60 / 80 / 60 | 중앙값 85 (70~130) |
| 후처리 | 정합성 → api 정지 | api 정지 → 정합성(ec2-load-test-followup) |

- 단계가 촘촘해져 기존 "80 또는 100"이 대부분 80~100 사이의 한 지점으로 좁혀졌다. 최대 지속이 기존보다 높게 나온 것은 대부분 간격이 10으로 줄어서다(기존 60은 "80에서 무너짐"의 한 단계 아래).
- s2f는 0에서 40으로 바로 오른다. 기존처럼 20부터 점진적으로 오르지 않으므로 초반 부하 이력이 다르다. 40~70 단계에서 무너진 회차는 없었다.
- 비교 한계: 개선 뒤 무너짐 지점이 120을 넘으면 그 회차들은 120 단계 이후 통계에 재로그인이 섞인다(개선 전에는 r3뿐). 비교 작업에서 단계 통계에서 재로그인을 빼는지(`name!="relogin"`) 또는 재로그인 시점을 늦추는지 정한다.
- 입금 비동기 반영 뒤 비교할 때 쓸 값: 무너진 요청률 중앙값 95(80~140), 최대 처리 TPS 중앙값 103.8(87.7~140.6), 전파 7/7. 같은 s2f 조건(`PERF_RESULTS`·`s2f`)으로 다시 잰다.
