# 작업 명세

## 요구사항 구체화

명세 상태: 확정
원문 요청: 후속으로 남긴거 진행시켜.
("후속으로 남긴 것" = 직전 작업 ec2-load-test의 결과 리뷰 3/3 개선 지적 중 문서 정리 4건과 다음 측정 전 수정 1건. 작업 칩으로 띄운 운영 문제 3건은 별도 작업이라 포함하지 않는다.)
요청 해석: 측정을 다시 하지 않고, 이미 받아 둔 원자료로 기준선 문서를 바로잡고, 다음 측정에서 정합성 스냅샷이 api 정지 뒤에 찍히도록 오케스트레이터 순서를 바꾼다.
조사한 사실:
- 개선-1(드롭 수): 두 종류의 값이 있다.
  - 확정 전체 수: 회차별 `loadgen/k6-summary.json`의 `metrics.dropped_iterations.count`(k6가 직접 센 값). S1 1,628/1,549/1,588, S2 r1 항목 없음(=0)·r2 1,403·r3 99, S3 19,620/19,685/19,635, S5 r1~r3 항목 없음(=0).
  - 단계·구간별 추정치: `loadgen/analysis.json`의 `dropped_iterations`는 Prometheus `increase()` 계산이라 소수이고 외삽으로 과대·과소가 생기며, 표본이 없으면 `null`이다. S1 150 단계 1,267/1,049/1,124, S1 100 단계 null/null/null, S2 무너진 단계 r1(80) null·r2(100) 778·r3(80) 70, S3 스파이크 구간 20,985/20,764/20,835(확정 전체 수보다 큼 — 외삽 과대).
  - summary.md·bottleneck-analysis.md에는 드롭 수가 없다.
- 개선-3(S2 r3 문구): s2/r3는 k6 이체 체크 실패 0, 기록된 실패 키 2(SIGINT로 끊긴 요청), 그중 1건 DB 반영, 잔차 0. summary.md S2 문단과 bottleneck-analysis.md 표의 "0 / 1"은 자체 정의(실패 응답 중 반영 하한 = 반영 키 − (키 수 − 체크 실패 수))와 어긋난다. s2/r1은 체크 실패 0, 키 0, 잔차 1.
- 개선-4(S5 메모리): summary.md S5 표의 "가용 메모리 최저" 217/204/241MB는 배치 구간 값이다. 회차 전체 최저(analysis.json overall_system)는 185/204/181MB. 단위 MB는 10^6바이트.
- 개선-1 관련 생성기: run-ec2.py의 정합성 표 행 "실패 응답인데 실제 반영된 이체(멱등키 대조)"는 SIGINT로 끊긴 요청의 키(상태 0)까지 합산해, s2/r3처럼 체크 실패가 0인데 "1"로 나온다. 다음 측정에도 같은 표현이 생긴다.
- 순서 변경의 비교 영향: api를 먼저 멈추면 대기열 요청이 커밋되지 않고 끊겨, 다음 측정의 "실패 키 반영" 수가 이번 기준선보다 조금 작게 나올 수 있다(기준선의 잔차는 모두 0 이상이라 영향은 작을 것으로 본다). 12개 회차 모두 api_error_lines·api_warn_lines가 0이라, 정지된 api 로그 발췌가 실제로 되는지는 기존 증거로 확인되지 않는다.
- 개선-5(first-pass 머리말): `perf/results/ec2-baseline/first-pass/summary.md`·`bottleneck-analysis.md` 맨 위에 결함·대체 표시가 없다.
- 개선-2(스냅샷 순서): `perf/run-ec2.py` cmd_run이 integrity → 실패 키 복사·대조 → stop-api 순이다. api가 떠 있는 동안 대기열 이체가 커밋되면 새 완료·실패 키 반영 수가 스냅샷마다 달라진다. stop-api 뒤에도 logs(docker compose logs)와 psql은 동작한다(컨테이너 로그 보존, postgres는 정지 대상 아님).
- 직전 작업 기록(progress.md·review.md)과 개발일지에는 커밋 해시가 적혀 있다. 이번에 브랜치 이력을 정리하면서 479eefc → b4f097a, a2f21f7 → a870ee0 등 이후 커밋 해시가 바뀌었다(내용 동일). 기록된 해시는 작업 당시 값이다.
질문하지 않은 이유: 다섯 항목 모두 결과 리뷰 3/3이 구체적 수정을 제시했고 원자료에 값이 있어 선택지가 없다. 수치를 새로 만들지 않고 기존 원자료를 옮겨 적는 일이다. 드롭 수 표기 규칙(확정값 우선, 추정치는 추정으로 표시, null은 "수집 없음")은 원자료의 성격에서 정해지는 기술 선택이라 질문하지 않았다. 순서 변경은 다음 측정에만 적용되며, 그 비교 조건 차이는 README에 적는다. 해시 변경은 기록 보존 원칙상 기존 기록을 고치지 않고 이 작업 기록에 대응표만 남긴다.

## 목표

EC2 기준선 문서가 원자료와 자체 정의에 정확히 맞게 하고, 다음 측정에서 정합성 스냅샷이 대기열 커밋의 영향을 받지 않게 한다.

## 범위

- `perf/results/ec2-baseline/summary.md`, `bottleneck-analysis.md`: 드롭 수, S2 r1·r3 실패 응답 반영 문구, S5 메모리 열.
- `perf/results/ec2-baseline/first-pass/summary.md`, `first-pass/bottleneck-analysis.md`: 결함 기록 머리말.
- `perf/run-ec2.py`: 측정 후 순서를 stop-api → integrity → 실패 키 대조 → 대사로 변경.
- `perf/README.md` 회차 흐름 설명이 순서를 적고 있으면 맞춘다.

| --- | --- | --- |
| REQ-01 | summary.md의 S1·S2·S3·S5 표 | 회차별 확정 드롭 수(k6-summary.json `dropped_iterations.count`, 항목이 없으면 0)가 적힌다. S1·S2는 무너진 단계와 한 단계 더 간 단계, S3는 스파이크 구간의 추정치(analysis.json, 정수 반올림)를 "추정"으로 표시해 함께 적고, `null`은 "수집 없음"으로 적는다(0으로 바꾸지 않음). 추정치가 확정 전체 수보다 큰 경우(S3) 외삽 과대임을 적는다. 문서 값이 이 규칙으로 원자료에서 얻은 값과 하나라도 다르면 실패 |
| REQ-02 | S2 r1·r3의 실패 응답 반영 서술(summary.md, bottleneck-analysis.md) | "실패 응답 0건"과 "중단 순간 끊긴 키 수와 그중 반영 수"(r3: 키 2 중 1 반영, r1: 키 0·잔차 1)로 나눠 적혀 자체 정의와 모순이 없다. "실패 응답 반영 0·1건" 같은 섞인 표현이 남으면 실패 |
| REQ-03 | summary.md S5 표 | 배치 구간 최저(217/204/241MB)와 회차 전체 최저(185/204/181MB)가 구분된 열 이름으로 적히고, 대표 행에 각각의 중앙값(배치 구간 217MB, 전체 185MB)과 단위(MB=10^6바이트)가 적힌다. bottleneck-analysis.md 가설 E의 S5 메모리 서술이 같은 구분을 따른다 |
| REQ-04 | first-pass/summary.md, first-pass/bottleneck-analysis.md | 맨 위에 "결함이 있는 1차 기록이며 기준선은 ../summary.md"라는 표시와 결함 요약(지표 공백, S5 동시 재로그인 포화, 실패 응답 반영 수치 혼입, 배치 건수 누락)이 있다. 본문 수치는 바꾸지 않는다 |
| REQ-05 | 다음 측정의 회차 후처리 | run-ec2.py cmd_run이 측정 수집(분석·export) 뒤 api 정지 → 정합성 스냅샷 → 실패 키 복사·대조 → 대사 → 로그 순으로 실행한다. 정지 전에 스냅샷을 찍는 경로가 남으면 실패. 정합성 표의 실패 키 행 이름은 끊긴 요청의 키가 포함됨을 드러낸다(예: "실패 키 중 반영(k6 중단 시 끊긴 요청 포함)"). 기존 integrity.md는 다시 만들지 않는다(원자료 보존). 정지된 api 로그 발췌의 실제 동작은 다음 EC2 드라이런에서 확인한다(이 작업은 정적 확인만) |
| REQ-06 | 문서·코드 일관성 | perf/README.md의 회차 흐름 설명이 REQ-05 순서와 같고, 순서 변경 이후 측정은 "실패 키 반영" 수가 기준선보다 조금 작을 수 있다는 비교 조건 차이와 다음 드라이런 확인 항목(api-full 로그 줄 수 > 0)이 적힌다. 커밋 해시 대응표(이력 정리 전→후)가 이 작업 progress.md에 남는다 |
