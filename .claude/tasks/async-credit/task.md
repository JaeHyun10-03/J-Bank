# 작업 명세

## 요구사항 구체화

명세 상태: 확정
원문 요청: 1순위 진행시켜. 병렬로 2순위도 신행시켜
("1순위" = 핫 계좌 입금(수신 측) 비동기 반영. 2순위 3건은 별도 세션 작업으로 분리해 이 작업 범위가 아니다.)
요청 해석: 한 계좌로 이체가 몰릴 때 수신 계좌 행 락이 병목이 되는 문제를, 수신 측 반영을 비동기로 바꿔 해소하고 기존 s2f 기준선과 같은 조건으로 전후를 측정한다.
조사한 사실:
- `TransferService.transfer`는 두 계좌번호를 정렬해 둘 다 `PESSIMISTIC_WRITE`로 잠그고, `executeTransfer`에서 송금 잔액 차감·수신 잔액 증가·원장 2건(각각 반영 후 잔액 스냅샷)·`COMPLETED`·`TransferCompletedEvent`(감사 로그)를 한 트랜잭션으로 처리한다. OTP 완료(`completeAfterOtp`)도 같은 `executeTransfer`를 쓴다.
- 기준선(perf/results/ec2-hot-account/summary.md, s2f 유효 6회): 무너진 요청률 중앙값 95(80~140), 최대 처리 TPS 중앙값 103.8, 무관한 잔액 조회 전파 7/7, 무너질 때 CPU 44~66%. 원인은 핫 계좌 행 락 대기가 커넥션 풀을 고갈시키는 것.
- 거래내역 조회(`TransactionHistoryService`)는 `transactions` 테이블을 Specification으로 조회한다. 원장이 아니다.
- 원장 대사(`LedgerReconciliationTasklet`)는 계좌별 원장 합 = 잔액 캐시, 전체 차변 = 대변을 검사하고 불일치는 로그만 남긴다.
- 계좌 해지는 잔액 캐시가 0이 아니면 `ACC_008_BALANCE_NOT_ZERO`로 거절한다. 계좌 상태는 ACTIVE·SUSPENDED·DORMANT·CLOSED.
- `@EnableScheduling`과 `@Scheduled` 폴링(`PendingOtpExpirationScheduler`) 선례가 있다. 예전 outbox 테이블(V9)이 미처리 행 부분 인덱스 패턴을 쓴다. 최신 마이그레이션은 V17.
- 입금 API(`DepositService`)·출금·이자 배치는 단일 계좌만 잠그거나 원장을 따로 쓴다.
- 측정 도구의 정합성 검사(perf/ec2/target.sh integrity)는 "핫 계좌 잔액 증가분 = 완료 이체 금액 합"을 본다. 측정 후 api를 먼저 멈추므로 미반영 입금이 남을 수 있다.
- 프론트 E2E(transfer.spec.ts)는 수신 계좌 잔액을 검사하지 않는다. 백엔드 테스트 15개 파일이 잔액 캐시를 직접 검사한다.
- 2순위 작업(타임아웃 이체 중복 위험, CTR 인덱스, 과부하 회복)이 다른 세션에서 진행될 수 있어 `TransferService`·설정 충돌 가능성이 있다.

기술 선택(근거):
- 입금 대기 테이블(`pending_credits`: 거래 ID 유니크, 수신 계좌 FK, 금액, 생성 시각, 반영 시각)을 V18로 추가하고, 미반영 행만 담는 부분 인덱스를 건다(V9 선례).
- 계좌 행 락 모드를 목적별로 명시한다(PostgreSQL 행 락 호환표 기준, JPA `PESSIMISTIC_WRITE`가 만드는 SQL에 기대지 않고 네이티브 쿼리로 고정).
  - 이체 송금 계좌, 워커의 수신 계좌 반영: `FOR NO KEY UPDATE`(잔액 갱신).
  - 이체의 수신 계좌 읽기: `FOR KEY SHARE`(존재·상태 확인). `NO KEY UPDATE`와는 충돌하지 않아 워커 반영·다른 이체와 줄 서지 않고, 해지의 `FOR UPDATE`와만 충돌한다.
  - 해지·상태 변경: 계좌를 처음 읽는 쿼리부터 `FOR UPDATE`로 잠근다(같은 트랜잭션에서 먼저 `findById`로 읽으면 영속성 컨텍스트가 옛 값을 돌려줘 덮어쓰기가 다시 생기므로 첫 로드를 락 쿼리로 바꾼다). 해지는 잠근 뒤 잔액·지급정지(기존)와 함께 이 계좌로 들어올 미반영 입금 대기·PENDING_OTP 이체가 있으면 `ACC_012`로 거절한다(Q-09). PENDING_OTP 이체는 생성 때 받는 계좌를 KEY SHARE로 읽고 ACTIVE를 확인하므로 해지의 FOR UPDATE와 순서가 정해진다. 지금 해지·상태 변경이 락 없이 읽고 전체 컬럼을 UPDATE해 동시 잔액 갱신을 덮어쓸 수 있는 문제도 이 락으로 막는다.
  - 입금·출금·OTP 취소·이자 경로는 기존 JPA `PESSIMISTIC_WRITE`를 그대로 쓴다. Hibernate가 만드는 SQL(`for update`인지 `for no key update`인지)을 구현 때 SQL 로그로 확인해 ADR에 기록한다. `for update`여도 같은 계좌를 쓰는 경우에만 직렬화될 뿐 정합성 문제는 없다.
- 이체 트랜잭션: 송금 계좌 `NO KEY UPDATE`, 수신 계좌 `KEY SHARE` 후 기존 검사(존재·ACTIVE·잔액·권한), 송금 잔액 차감, 차변 원장 1건, 입금 대기 1건, `COMPLETED`, 감사 이벤트를 한 트랜잭션에 쓴다. 두 계좌 락 순서는 기존처럼 계좌번호 정렬을 유지한다.
- 반영 워커(`@Scheduled` 약 200ms): 미반영 대기가 있는 수신 계좌를 고르고, 계좌마다 한 트랜잭션에서 계좌 행을 `NO KEY UPDATE`로 잠근 뒤 미반영 대기를 `FOR UPDATE SKIP LOCKED`로 최대 500건 가져와 잔액을 한 번에 늘리고, 거래마다 대변 원장 1건(스냅샷 누적, `occurred_at` = 반영 시각)을 쓰고 반영 시각을 기록한다. 원장 행 수는 이체당 2건으로 기존과 같다.
- 실패 격리: 한 계좌 묶음이 실패하면 그 트랜잭션만 롤백, 다른 계좌는 계속, 다음 주기에 재시도. 같은 계좌 연속 실패의 오류 로그는 1분에 1회로 억제하고 대사 경고(1분 초과 미반영)로 드러낸다. 인스턴스가 여러 개여도 `SKIP LOCKED`와 계좌 행 락으로 중복 반영이 없다.
- 반영 시 수신 계좌 상태는 다시 검사하지 않는다(Q-08). 해지는 `FOR UPDATE` 후 미반영 입금·OTP 대기 입금이 있으면 거절하므로 CLOSED 계좌에 대기가 생기거나 반영될 수 없다. 방어적으로 CLOSED면 반영하지 않고 오류 로그를 남긴다(대사 경고로 드러남).
- 워커는 계좌마다 새 트랜잭션에서 락 쿼리로 계좌를 처음 읽는다. `applied_at`은 반영 트랜잭션 안의 `clock_timestamp()`(트랜잭션 시작 시각이 아닌 실제 시각), `created_at`은 이체 트랜잭션의 `clock_timestamp()`로 기록해 지연이 낙관적으로 잡히지 않게 한다.
- 영구 실패 계좌는 돈을 버릴 수 없으므로 재시도를 계속하되(계좌별 백오프는 두지 않음) 오류 로그는 1분 1회로 억제하고 대사 경고로 드러낸다. BE-07의 "무한 재처리 없음"과의 관계를 ADR에 적는다.
- 보이는 잔액이 0인데 미반영·OTP 대기 입금 때문에 해지가 `ACC_012`로 거절되는 짧은 창이 생긴다(ADR·API 설계 문서에 기록). 프론트 오류 문구 매핑(`apps/frontend/lib/domain-error-map.ts`)에 `ACC_012`를 추가한다.
- 워커 켜고 끄기: `@ConditionalOnProperty(jbank.transfer.credit-worker.enabled)`의 기본값은 false이고 운영 application.yml에서 true로 켠다. batch 프로파일(application-batch.yml)은 false로 덮는다. 테스트는 src/test/resources에 application.yml을 두지 않고(메인 설정을 가림) 테스트 공통 속성(@TestPropertySource 또는 추상 테스트 기반 클래스의 DynamicPropertySource)으로 false를 준다. REQ-11의 "기본에서 동작"은 운영 설정 그대로 띄운 컨텍스트로 확인한다. 끄는 목적: — 배치 JVM이 대사와 동시에 DB를 바꾸지 않게 하고, 테스트가 스케줄 타이밍에 흔들리지 않게 한다. 테스트는 반영 서비스를 직접 호출한다.
- 지표: 워커가 주기마다 미반영 수·가장 오래된 나이를 계산해 캐시하고 게이지는 캐시 값을 읽는다(스크레이프가 DB 커넥션을 쓰지 않음). 반영 지연 Timer(히스토그램 버킷 포함)도 보조로 둔다.
- 거래내역 조회는 수신 측 이체 중 미반영 입금 대기가 있는 건을 제외한다(Q-03). 반영 후에는 원래 거래 시각(created_at) 위치에 나타난다(ADR에 표시 의미 기록).
- 대사: 한 번의 REPEATABLE READ 트랜잭션에서 계좌별 원장 합 = 잔액 캐시, 전체 차변 = 대변 + 미반영 대기 합을 계산한다(쿼리 사이 반영으로 인한 오탐 방지). 생성 1분 초과 미반영은 경고 로그. 입금·출금·이자처럼 한쪽만 남는 원장이 전역식에 주는 영향은 기존 대사 의미를 유지하고 테스트 데이터에 명시한다.
- 롤백 호환: 구버전 앱에는 워커가 없으므로 롤백은 "트래픽을 멈추고 미반영 0 확인 후" 또는 전진 복구만 허용한다. ADR 0012와 운영 문서에 적는다.
- 측정 도구:
  - 경계 기록(boundary) 전에 미반영 0이 될 때까지 기다리고 미반영 수를 boundary.env에 기록한다(예열 이체의 대변이 경계 뒤에 생기는 오차 제거).
  - 정합성 표(integrity) 식: 새 원장 행 = 2 × 반영된 새 이체 + 미반영 새 이체, 새 원장 차변 합 = 대변 합 + 미반영 합, 핫 계좌 증가분 + 핫 계좌 미반영 합 = 완료 금액 합 = k6 201 × 1,000원, 전체 차변·대변 증가분도 미반영 포함. 직접 검사: 경계 이후 이체마다 대변 원장 수가 반영된 건 1, 미반영 건 0(중복·유실 0).
  - 반영 지연: DB의 created_at·applied_at으로 단계 구간별 p95를 계산한다. Prometheus Timer는 보조. credit-lag.md·json의 판정값(무너지기 전 단계 p95 최대)은 원래 정의(Q-05)의 값으로 원자료에 그대로 둔다. REQ-07 판정값(Q-10, 초당 150건 이하이면서 무너지기 전 단계 p95 최대)은 summary.md에서 credit-lag.json 단계값으로 계산해 원래 정의 값과 나란히 적는다.
  - 무너짐 판정·단계 통계는 기준선과 같은 코드로 계산한다(비교 공정성). 재로그인 섞임(기준선 summary 78행이 넘긴 결정): 판정은 기준선과 같게 두고, 재로그인을 뺀(`name!="relogin"`) 이체 p95를 보조 필드로 함께 남긴다.
  - 상한 400까지 무너지지 않은 회차는 무너진 요청률을 ">400"으로 표기하고, 중앙값은 400을 하한값으로 둔 값과 함께 적는다.
  - 비교 표시 규칙: 중앙값과 범위를 나란히 적고, 차이가 한 단계(10건/초) 이내면 "변화 없음"으로 적는다.
- 측정 결과는 `perf/results/ec2-async-credit/`(PERF_RESULTS), 절차·인스턴스·시드는 기준선과 같다.

## 목표

핫 계좌로 이체가 몰려도 수신 계좌 행 락이 병목이 되지 않게 하고, s2f 기준선 대비 무너지는 지점·최대 처리량·무관한 조회 전파가 어떻게 바뀌는지 같은 조건으로 측정해 남긴다.

## 범위

- DB: 입금 대기 테이블(V18).
- 해지·상태 변경의 계좌 락(동시 잔액 갱신 덮어쓰기 방지 포함), 해지 거절 조건(`ACC_012`)과 프론트 오류 문구·API 설계 문서.
- 이체(즉시·OTP 완료 경로): 수신 계좌 무락, 입금 대기 기록.

## 커밋 계획

생산자(이체 전환)보다 소비자·방어 로직을 먼저 넣어 모든 커밋이 빌드·기존 테스트가 통과하고 동작이 깨지지 않게 한다.

1. `feat(db)`: 입금 대기 테이블 추가(V18)
2. `feat(transfer)`: 입금 대기를 수신 계좌별로 묶어 반영하는 워커와 지표(대기가 없으면 아무것도 하지 않음, batch·테스트에서 끔)
3. `fix(account)`: 해지·상태 변경이 계좌를 처음부터 잠가 읽도록 수정(동시 잔액 갱신 덮어쓰기 방지)
4. `feat(account)`: 처리 중인 입금(미반영·OTP 대기)이 있으면 해지 거절(`ACC_012`, 프론트 문구, API 설계 문서)
5. `feat(transfer)`: 반영 전 입금을 거래내역에서 제외
6. `feat(batch)`: 원장 대사를 한 트랜잭션에서 미반영 입금까지 포함해 계산
7. `feat(transfer)`: 이체가 수신 계좌를 약한 락으로 읽고 입금 대기를 기록(기존 테스트는 반영 서비스 호출 후 검사로 수정)
8. `feat(perf)`: 측정 경계·정합성 식·반영 지연 분석에 미반영 입금 반영
9. `perf(results)`: 입금 비동기 반영 후 s2f 원자료
10. `docs`: ADR 0012, README·perf 요약
11. `docs(devlog)`: 개발일지
12. `chore(harness)`: 작업 기록

결과 리뷰 1회차 후 추가(11 개발일지 앞에 둔다):

- `test(batch)`: 대사 중 반영이 끼어도 오탐 없음
- `test(transfer)`: 반영 워커 연속 실패 로그 억제
- `test(perf)`: 정합성 SQL 검사에 경계 이전 원장 사례 추가
- `feat(perf)`: 측정 대시보드에 입금 반영 지표 패널
- `docs`: 측정 요약·ADR·README 수치 정정, API 설계 문구·application.yml 주석 보완

커밋 규칙과의 관계: 커밋 7은 이체 동작 전환과 그 전환으로 깨지는 기존 테스트의 수정이 한 커밋이다. 둘을 나누면 중간 커밋의 빌드(테스트)가 깨지므로 "커밋마다 빌드 가능"을 우선한다. 커밋 2의 batch 프로파일 설정도 워커 기능의 일부(배치 JVM에서 끄지 않으면 대사와 경합)라 같은 커밋에 둔다.

- 백엔드·데이터: 적용. BE-01(상태·잔액 규칙), BE-02(응답·오류 코드 불변), BE-03(실제 PostgreSQL), BE-04(동시성·멱등·중복 반영 없음), BE-05(V18 마이그레이션, 기존 데이터에서 적용), BE-07(비동기: 중복·재처리·실패 격리·재시작). BE-06(외부 연동 없음)·BE-08(권한 규칙 변경 없음 — 거래내역 제외 조건만) 해당 없음.

- AI: 해당 없음(제품에 LLM 기능 없음).
- 전체 흐름: E2E-06(이체 흐름 회귀) 적용. E2E-01~05 사용자 흐름 변경 없음.
- DevOps: OPS-05(롤백 호환: 미반영 0 확인 후 롤백 또는 전진 복구 — 절차 기록), OPS-06·07(자원·지표 수집 추가, 측정 환경). OPS-01~04·08 배포·빌드 절차 변경 없음(마이그레이션은 기존 Flyway 절차).
- 보안: SEC-05(결과물 비밀값). 나머지 인증·권한·입력 변경 없음.
- 프론트: FE-01·03(해지 오류 문구 `ACC_012` 매핑만). 이체 API 응답 형식은 불변. FE-02·04~07 해당 없음(화면·입력 변경 없음).

## 성능 테스트

- 필요 여부와 이유: 필요. 작업 목적이 핫 계좌 락 경합 해소다.
- 변경 전 결과: `perf/results/ec2-hot-account/summary.md`(2026-09-28 s2f, 유효 6회). 무너짐 중앙값 95(80~140), 최대 처리 TPS 103.8(87.7~140.6), 전파 7/7.
- 측정 대상·조건: 기준선과 같다(t3.small 대상, c7i.large 발생기, 1천만 건 시드, s2f 40부터 +10 상한 400, 병행 잔액 조회 초당 20, 회차 시작 절차). 차이는 api 이미지뿐.
- 반복: 유효 5회, 무효·추가 규칙은 기준선(ec2-load-test·hot-account-baseline)과 같다.
- 지표·판정: 목표 없이 전후 비교(Q-06). 반영 지연 p95 1초 이내는 REQ-07 목표로 판정한다(초당 150건 이하·무너지기 전 단계, Q-10).
- 결과 위치: `perf/results/ec2-async-credit/`.
- 주의: 기준선은 후처리 순서 차이(api 정지 → 정합성)를 이미 반영한 절차라 그대로 쓴다. 미반영 대기가 남는 것은 정합성 식에 포함한다.
- 증거 재사용: 측정 이미지 이후 결과 리뷰 1회차 처리는 테스트·측정 도구·대시보드·문서만 바꾸고 운영 코드(apps/jbank-api/src/main)는 바꾸지 않는다. 측정 이미지는 `perf-f535020`(env/target/environment-target.md)이고 운영 코드 마지막 변경은 그 이전 2d26adb다. 그래서 r1~r6 결과를 그대로 쓴다. 측정 이미지 커밋과 이후 운영 코드 변경 0은 summary에 적는다. 개선 제안 I1(해지 계좌 방어 로그 억제)·I2(워커 lock_timeout)·I3(계좌 선택 순서)·게이지가 워커 정지 때 굳는 점은 운영 코드 변경이라 이번 범위에서 빼고 ADR 한계에 적는다.
