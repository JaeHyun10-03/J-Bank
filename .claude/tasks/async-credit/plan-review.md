  - 방안 2: CLOSED 계좌로 가는 대기를 송금자에게 되돌립니다(보상 처리). 이는 제품 결정이므로 사용자에게 물어야 합니다.

## 6. 개선 제안(완료를 막지 않음)

### I1. 락 모드 확인
- 입금 대기와 거래 행을 넣을 때 수신 계좌에 FK로 `FOR KEY SHARE` 락이 걸립니다. 이 락은 워커의 락이 `FOR NO KEY UPDATE`일 때만 서로 막지 않습니다.
- Hibernate가 실제로 만드는 SQL을 확인합니다. 만약 `for update`라면 워커가 묶음을 처리하는 동안 핫 계좌 이체가 다시 줄을 서게 됩니다.
- REQ-01 테스트는 워커와 같은 `findByIdForUpdate`로 수신 계좌를 잠그고, 완료 시간 상한을 검사하도록 적습니다.

### I2. 실패 격리 테스트와 반복 재시도
- 한 계좌 반영 실패를 어떻게 일으킬지 정해지지 않았습니다. TransferRollbackScenarioTest 주석은 운영 코드에 장애 훅을 두는 것을 부적절하다고 봅니다. 테스트 전용 DB 트리거 같은 방법을 계획에 적습니다.
- 영구 실패가 나면 200ms마다 무한 재시도와 로그가 반복됩니다. BE-07의 "무한 재처리 없음" 기준에 맞게 로그 억제나 격리 방식을 기록합니다.

### I3. 대사 읽기 일관성과 전역식
- 대사는 여러 쿼리를 따로 실행합니다(READ COMMITTED). 운영에서는 API와 동시에 돌기 때문에 쿼리 사이에 반영이 끼면 오탐이 납니다. REPEATABLE READ 트랜잭션이나 단일 쿼리를 권합니다.
- 전역 "차변 = 대변" 식은 입금·출금·이자(한쪽만 기록되는 원장)가 있으면 원래 성립하지 않습니다. REQ-06 테스트 데이터와 기대값을 명시합니다.

### I4. 게이지 구현 방식
- 미반영 수·가장 오래된 나이 게이지를 스크레이프 때마다 DB 조회로 구현하면, 커넥션 풀이 고갈됐을 때 /metrics 응답이 막힙니다. 그러면 수집 결측이 생기고 기준선 규칙상 그 회차가 무효가 됩니다.
- 워커가 주기마다 값을 캐시하는 방식을 권합니다.

### I5. 비교 표시 규칙
- PERF-07은 회귀 허용폭을 미리 정하라고 합니다. 사용자는 목표 없이 비교하기로 했으므로 목표는 두지 않습니다.
- 대신 "개선·변화 없음"을 판단할 표시 규칙(중앙값과 범위, 한 단계 10건/초 변동)을 미리 적어 둡니다.

### I6. 기타
- 반영 후 노출되는 입금은 거래내역에서 created_at 기준 과거 위치에 끼어듭니다. 이 표시 의미를 ADR에 적습니다.
- 적용 영역 목록에 "AI: 해당 없음"이 빠져 있습니다.

## 4. Q-09 반영 검증(이번 회차 중점)

### 해지 경로가 하나뿐임
- `account.close()`는 AccountService.close 154행에서만 호출됩니다.
- changeStatus는 CLOSED로 바꿀 수 없습니다(210행 `to == AccountStatus.CLOSED` 거절).
- 따라서 해지 경로는 하나이고, "CLOSED 계좌에 대기가 생기지 않는다"(task.md 43행)는 주장의 범위가 닫혀 있습니다.

### 해지와 동시 경로의 순서
해지는 READ COMMITTED에서 FOR UPDATE를 잡은 뒤 새 문장으로 조회하므로, 모든 경우가 올바르게 끝납니다.

| 동시 경로 | 먼저 잡은 쪽 | 결과 |
| --- | --- | --- |
| PENDING_OTP 생성 | 이체가 KEY SHARE 선점 | 해지가 기다린 뒤 PENDING_OTP를 보고 ACC_012 |
| PENDING_OTP 생성 | 해지 선점 | 이체가 CLOSED를 보고 TXN_004(TransferService 84~85행) |
| OTP 완료 | 완료가 받는 계좌 KEY SHARE 선점 | 해지가 기다린 뒤 미반영 대기를 보고 ACC_012 |
| OTP 완료 | 해지 선점 | 완료 전이라 PENDING_OTP가 남아 있으므로 ACC_012. 해지 후 완료가 진행되어 정상 반영 |

"PENDING_OTP 중 해지 거절 → OTP 성공 정상 반영"이라는 REQ-05 사례와 일치합니다.

### 교착 없음
- 해지는 계좌 락 하나만 잡습니다. transactions와 pending_credits는 락 없이 읽습니다.
- completeAfterOtp는 거래 행을 먼저 잠그고 계좌 락을 잡습니다.
- 따라서 순환 대기가 없습니다.
- completeAfterOtp는 계좌 ID 순, transfer는 계좌번호 순으로 잠급니다. 하지만 새 락 모드(송금 NO KEY UPDATE, 수신 KEY SHARE)에서는 NO KEY UPDATE끼리만 충돌하고, 한 트랜잭션은 NO KEY UPDATE를 하나만 가집니다. 그래서 두 정렬 기준이 달라도 교착이 생기지 않습니다.

### 조회 비용
- 받을 PENDING_OTP 조회에는 V12 부분 인덱스(status, created_at)와 V13 to_account_id 복합 인덱스가 있습니다.
- 해지가 FOR UPDATE를 잡은 동안 전체 테이블을 훑을 걱정은 없습니다.
