# 작업 명세

## 요구사항 구체화

명세 상태: 확정
원문 요청: 별도 EC2, 복제 EC2, 입금 비동기까지로 진행시키면 될 것 같아.
(직전 대화에서 제안한 "EC2에서 무너지는 상황을 만드는 부하 테스트 계획"의 세 가지 선택에 대한 답이다: 부하 발생기는 같은 AZ의 별도 EC2, 측정 대상은 운영과 같은 사양의 복제 EC2, 핫 계좌 개선은 입금 비동기 반영까지.)
요청 해석: 운영과 같은 t3.small 단일 인스턴스 구성에서 부하를 올려 실제로 무너지는 지점과 원인을 지표로 증명하고, 핫 계좌 경합을 입금(수신 측) 비동기 반영으로 개선한 뒤 같은 조건에서 재측정해 개선 전후 수치를 남긴다. Q-01에 따라 **이 작업은 측정 환경·시나리오·개선 전 기준선까지**이며 앱 코드는 바꾸지 않는다. 입금 비동기 반영과 재측정은 이 작업의 결과를 근거로 후속 작업에서 명세를 확정한다.
조사한 사실:
- 운영 구성: `infra/terraform/envs/dev` → `modules/ec2`, t3.small(2 vCPU·2GB), gp3 20GB, AL2023, CPU 크레딧 `unlimited`(2026-09-27 `aws ec2 describe-instance-credit-specifications`로 확인). api·postgres·redis·prometheus·grafana·caddy가 한 대(`infra/compose/docker-compose.prod.yml`). 인바운드 80/443 공개, SSH 없음·SSM 접근.
- `modules/ec2`는 EIP·GitHub OIDC 배포 역할까지 만들고 user_data가 배치 cron(01~04시 KST)을 등록한다. perf 대상에 그대로 쓰면 공개 포트·배포 역할·측정 중 배치 자동 실행이 따라온다.
- 운영 이미지: backend-cd 마지막 성공 배포(2026-09-17, run 35197030438)의 이미지는 커밋 `490ed107ae325866110b81d9ed6acbb79978aa54` 태그다(GHCR 익명 pull 가능, 2026-09-27 manifest 200 확인). 운영 인스턴스 ID는 state와 같아(`i-0b71df18394cf8010`) 재생성되지 않았다. 운영에서 실제로 도는 이미지는 운영 접속 없이 확인하지 않는다. 이후 main 커밋의 backend-cd는 SSM 배포 단계에서 실패해(`InvalidInstanceId`) 운영에 반영되지 않았다. `490ed10`..`HEAD` 사이 `apps/jbank-api` 변경은 Dockerfile 위치 이동뿐이다. Compose의 `caddy:2`·`postgres:16`·`redis:7`은 떠다니는 태그다.
- api: `-Xmx512m -XX:MaxMetaspaceSize=128m`. Hikari 풀 설정 없음(기본 10), Tomcat 스레드 설정 없음(기본 200), `server.tomcat.mbeanregistry.enabled` 설정 없음(기본 false → Tomcat 스레드 지표 미노출). `application.yml`·`application-prod.yml`.
- 관측: Prometheus는 api만 수집(`observability/prometheus.prod.yml`). Grafana 대시보드 `jbank-transfer.json`에 이체 p50/95/99·TPS·에러율·Hikari·`db_lock_wait_seconds` 패널이 있다. 호스트·컨테이너·PostgreSQL 지표는 없다. 로그는 ECS JSON 콘솔 출력. PG 느린 쿼리·락 대기 로그 설정 없음. Compose에 로그 로테이션 설정 없음.
- 이체(`TransferService.transfer`)는 발신·수신 두 계좌를 계좌번호 오름차순으로 `SELECT ... FOR UPDATE` 한다. 수신 계좌 하나로 이체가 몰리면 모든 요청이 그 행 락에서 직렬화된다. `db.lock.wait` 타이머가 `AccountRepository`의 락 조회 두 곳에 붙어 있다. 멱등키는 unique 인덱스라 중복 거래는 구조적으로 생기지 않는다.
- 입금 API(`DepositService`)는 본인 계좌에만 가능하다. "여러 사람이 한 계좌로 입금"하는 핫 계좌 상황은 이체 API의 수신 측으로 재현한다.
- 이체 금액이 `jbank.transfer.otp.threshold-amount`(기본 1천만 원)를 넘으면 OTP 대기로 빠진다. 부하 시나리오 금액은 그 이하로 둔다.
- 액세스 토큰 TTL 15분(`JwtTokenProvider`). 기존 k6는 setup()에서 한 번만 로그인한다. 로그인 5회 실패 시 30분 잠금(`LoginAttemptService`).
- `perf/sql/seed-10m.sql`의 시드 고객은 비밀번호 해시뿐 아니라 암호화 컬럼(주민번호·전화번호)도 placeholder라 로그인 시 복호화에서 실패한다. 로그인 가능한 고객은 가입 API로 만들어야 한다(`perf/run-10m.sh` 방식). 시드는 `transactions`만 넣고 `ledger_entries`는 넣지 않으며 계좌 잔액 캐시는 고정값이다. 거래가 1천 건 이상 있으면 시드 재실행을 거부한다.
- 원장 대사(`LedgerReconciliationTasklet`)는 계좌별 원장 합과 `current_balance_cache`를 비교하고 불일치를 로그로만 남긴다. 시드 직후 상태에서는 시드 계좌 약 10만 개가 전부 불일치로 나온다.
- 배치 잡(대사·CTR·FDS)에는 incrementer가 없어 같은 잡 인자로 두 번 실행하면 `JobInstanceAlreadyCompleteException`으로 거부된다. `run-batch.sh`는 `docker-compose.prod.yml`에 고정되어 있고 대사에는 잡 인자를 넘기지 않는다. CTR·FDS는 `runDate` 하루치 거래만 처리한다(시드는 365일 분산, 하루 약 2.7만 건).
- 기존 k6: `perf/k6/transfer.js`(계좌 2개 왕복, 초당 100건 30초), `read-endpoints.js`. 모두 NFR-PERF-001(이체 p95 200ms, 초당 100건) 대비 16~20배 여유로 통과해 한계에 닿은 적이 없다.

답변 후 재점검한 추가 사항(사용자 결정이 아닌 기술 선택, 근거와 함께 기록):
- perf 환경은 `modules/ec2`를 재사용하지 않고 perf 전용 모듈로 만든다. 공개 인바운드·EIP·OIDC 배포 역할·배치 cron이 측정 조건과 보안에 맞지 않기 때문이다. 인스턴스 사양·AMI 계열·디스크·CPU 크레딧 모드(`unlimited`, 운영 확인값)·Compose 서비스 구성은 운영과 같게 둔다. Terraform state는 perf 환경 디렉터리의 로컬 state로 둔다(일회성 환경, 원격 state 불필요). state 파일은 커밋하지 않는다.
- 측정 경로는 운영과 같이 caddy(TLS) → api로 둔다. 공인 도메인이 없으므로 caddy `tls internal`(자체 서명) 인증서를 쓰고 k6는 인증서 검증을 끈다.
- Prometheus·Grafana는 대상에서 빼고 부하 발생기에 둔다. 관측 도구가 대상 자원을 쓰면 측정이 오염되기 때문이다. 이 때문에 대상의 메모리 압박은 운영보다 낮다(가설 E 한계로 기록).
- Tomcat 스레드 지표를 위해 대상 api에 `SERVER_TOMCAT_MBEANREGISTRY_ENABLED=true`를 켠다. 지표 노출만 바꾸는 설정이며 운영과의 차이로 기록한다.
- 배치 실행 계획은 느린 쿼리 로그로 얻을 수 없으므로, 부하 측정이 끝난 뒤 느린 쿼리 로그에 찍힌 배치 쿼리를 `EXPLAIN (ANALYZE, BUFFERS)`로 따로 실행해 얻는다. `auto_explain`은 측정 중 오버헤드를 더하므로 쓰지 않는다.
- 준비 순서(모든 문서에서 이 순서로 통일): 시드 적재 → 준비(가입·입금 API) → 기준 대사(불일치 계좌 목록, 전체 차변 합·대변 합 저장) → postgres 중지 → PG 데이터 복사본 생성.
- 대사 판정은 시드와 준비 입금의 영향을 빼기 위해 "기준 대사"를 쓴다. 입금은 원장에 대변 한 줄만 남기므로(`DepositService`) 전체 차변·대변은 기준 상태부터 다르다. 회차 판정: (1) 계좌 단위 — 기준 목록에 없던 새 불일치 계좌 수. 기준 목록에 있던 시드 계좌가 측정 중 거래에 쓰였다면 그 계좌의 원장 증가분과 잔액 증가분이 같은지. (2) 전체 — 측정 경계 이후 새로 생긴 원장 행의 차변 합 = 대변 합(측정 부하는 이체만 만들므로 같아야 한다). 대사 잡의 전체 판정은 기준값 대비 변화로 기록한다.
- 측정 경계: 매 회차 측정 시작 직전(예열 이후)의 `transactions`·`ledger_entries` ID 최댓값을 기록하고, 정합성 비교는 그 이후 행만 대상으로 한다. 예열 중 생긴 거래는 비교에서 뺀다.
- 디스크: 복사본 생성 전에 PG 데이터 크기(`pg_database_size`)와 디스크 여유를 확인한다. 복사본을 만든 뒤 남는 여유가 측정 중 로그 증가를 감당하지 못하면 진행을 멈추고, 복사본용 별도 볼륨 같은 대안(운영과의 차이가 됨)을 사용자에게 묻는다.
- 배치 재실행은 오케스트레이터가 perf Compose 파일로 `docker compose run`을 직접 호출하고 회차마다 고유한 잡 인자 `perfRun=<시나리오>-<회차>-<단계>`를 더한다. CTR·FDS의 `runDate`는 측정일(KST)로 유지한다. `run-batch.sh`는 운영 스크립트라 바꾸지 않는다.
- "무너짐" 기준은 기존 NFR-PERF-001(p95 200ms)과 기존 k6 threshold(오류율 1%)를 그대로 쓴다.
- (Q-07, 1차 측정 후 추가) `/actuator/prometheus`는 공개 경로가 아니라 인증 없이 긁으면 401이다. 앱 코드를 바꾸지 않기 위해 대상에 metrics-proxy를 두고 perf 전용 계정으로 로그인해 대리 수집한다. 1차 측정에서 이 수집이 api와 같은 Tomcat 작업 스레드를 타서 포화 구간에 끊겼으므로, api의 관리 엔드포인트를 별도 관리 포트(`MANAGEMENT_SERVER_PORT`, 자체 커넥터·스레드)로 분리하고 프록시 수집·컨테이너 헬스체크·target.sh와 run-ec2.py의 readiness 확인을 모두 그 포트로 옮긴다. 둘 다 운영과의 차이로 기록한다.
- (Q-07, 계획 리뷰 4회차) 프록시 로그인(`/api/v1/auth/login`)은 본 포트에만 있어 포화 구간에 실패할 수 있다. 프록시는 (1) 재로그인에 실패해도 만료 전인 기존 쿠키를 계속 쓰고, (2) 재로그인은 쿠키 발급 후 5분부터 시도해 성공할 때만 교체하며, (3) 매 회차 측정 경계를 기록할 때 target.sh `boundary` 단계가 metrics-proxy 컨테이너를 재시작해 새로 로그인시키고, 프록시 `/metrics`가 200을 돌려주는 것을 확인한 뒤에만 측정을 시작한다(확인 실패 시 그 회차는 시작하지 않고 실패로 기록). (2)와 (3)을 함께 적용하면 측정 구간 내내 만료 전 쿠키가 유지된다. 재시작 공백은 15초 미만이며 측정 시작 전이다.
- (Q-07) 관리 포트 번호는 9095로 한다. 호스트에 매핑하지 않는다(8081은 cAdvisor가 사용). 호스트 쪽 readiness 확인은 `docker compose exec api`로 컨테이너 안에서 조회한다.
- (Q-07, 계획 리뷰 4회차) 관리 포트를 분리하면 Tomcat ThreadPool 지표가 본 커넥터와 관리 커넥터로 나뉜다. Tomcat 지표(대시보드·분석)는 본 커넥터(`name="http-nio-8080"`)로 한정한다.
- (Q-07, 계획 리뷰 4회차) 지표 결측 판정은 "수집 대상별 연속성"으로 정의한다. 대상별 대표 지표 — api `hikaricp_connections_active`, target-node `node_cpu_seconds_total`, target-cadvisor `container_memory_working_set_bytes`, target-postgres `pg_up`, loadgen-node `node_cpu_seconds_total`, k6 `k6_http_reqs_total` — 와 각 job의 `up`을 측정 구간에서 5초 단위로 보고, 샘플이 없거나 `up=0`인 구간이 15초를 넘으면 결측이다. 이벤트가 없으면 원래 값이 없는 패널(URI별 백분위, 오류율, 락 대기 평균, relogin 등)은 결측 판정에서 뺀다. 결측이 있는 회차는 무효로 표시하고 대표값에서 빼며, 추가 측정은 아래 "반복·변동" 규칙을 따른다.
- (Q-07, 계획 리뷰 4회차) 재로그인 기준 시각은 setup이 사용자별로 기록한 토큰 발급 시각이다(setup 소요 시간과 무관하게 만료 전 재로그인 보장).
- (Q-07) 1차 측정 결과(`perf/results/ec2-baseline/first-pass/`로 옮김)는 결함이 있는 기록으로 보존하고, 기준선 수치는 재측정 결과만 쓴다. 1차의 확인된 사실(메모리 스래싱 사고, CTR 전체 스캔 등)은 재측정 결과와 함께 인용할 수 있다.

## 목표

운영과 같은 사양의 EC2에서 핵심 시나리오 4개(S1·S2·S3·S5)로 서비스가 무너지는 요청률과 그 원인을 지표·로그로 증명하고, 후속 개선 작업이 같은 조건으로 비교할 수 있는 재현 가능한 측정 환경과 개선 전 기준선을 남긴다.

## 범위

- perf 전용 Terraform 환경: 대상 EC2 1대(운영 동일 사양) + 부하 발생 EC2 1대(같은 AZ), 내부 통신 전용 보안그룹, SSM 접근. 측정 때만 생성·삭제.
- 대상용 Compose 구성(운영 파일 기반, 관측 도구 제외·exporter 추가·caddy 내부 TLS·PG 로그 설정·Tomcat 지표·로그 로테이션), perf 전용 비밀값 생성 절차.
- 부하 발생기용 Prometheus·Grafana·node_exporter 구성과 대시보드(부하량·API·JVM·호스트·컨테이너·PG 한 화면).
- 가입·입금 API로 발신 고객·로그인 전용 고객·핫 수신 계좌를 만드는 준비 스크립트.
- k6 시나리오 S1·S2·S3·S5, 측정 오케스트레이터(복원·예열·측정·수집·대사·정합성 확인).
- 개선 전 기준선 측정(각 3회)과 결과·원자료·병목 분석 기록, `perf/README.md` 절차 갱신, 개발일지.

## 완료 기준

- REQ-01~13이 모두 아래 증거로 확인된다.
- perf 환경이 최종적으로 destroy되어 잔여 리소스가 0건이다.
- 기존 필수 검사(`verify`: 백엔드 테스트·spotless, 프론트 lint·타입·Jest·빌드, 하네스 테스트)가 통과한다.

## 하지 않을 일

- 운영(`envs/dev`) 인프라·도메인·데이터 변경, 운영 대상 부하, 운영 인스턴스 접속.
- S4 로그인 폭주, S6 1시간 soak(Q-04).
- 인스턴스 사양 변경 비교.
- CI 워크플로 변경. backend-cd의 SSM 배포 실패 조사는 별도 작업.

## 성능 테스트

- 필요 여부와 이유: 필요. 이 작업의 목적이 개선 전 한계와 병목을 측정하는 것이다.
- 측정 대상과 실행 명령: 이체 `/api/v1/transfers`, 조회계(거래내역·잔액·계좌 상세·고객 계좌 목록), 로그인. `perf/run-ec2.sh s1|s2|s3|s5`.
- 측정 환경·데이터 규모·부하·반복 횟수: "측정 조건" 표.
- 지표와 판정: 이번 작업은 개선 전 기준선이라 "통과 목표"가 아니라 "무너짐 판정 기준"을 쓴다(측정 조건 표). 측정 유효 조건은 REQ-11.
- 변경 전 결과와 측정 조건: 이 작업의 산출물이 곧 후속 작업의 변경 전 결과다. EC2 기준 이전 측정은 없다(로컬 측정은 조건이 달라 비교하지 않는다).
- 결과·로그 저장 위치: `perf/results/ec2-baseline/`.

## 추가 맥락

- 병목 가설: A 핫 계좌 락→커넥션 풀 고갈과 조회 API 전파, B 풀 10·스레드 200 비율과 스파이크 회복 지연, C 로그인 BCrypt CPU(이번 범위에서는 S1 로그인 10%로만 관측), D 배치와 온라인 경합(배치는 `runDate` 하루치만 처리하므로 "1천만 건 전체 스캔"이 아니라 인덱스 유무에 따른 하루치 조회 비용을 본다. CTR은 현금성 거래·금액 기준이라 1,000원 perf 이체는 대상이 아니며, 1차에서 대상 0건인데도 전체를 읽었다), E 2GB 메모리 OOM(관측 도구 분리로 운영보다 낙관적).
- 후속 작업(입금 비동기 반영)은 이 작업의 가설 A 결과로 명세를 확정한다. 가설 A가 관측되지 않으면 후속 작업의 방향을 사용자와 다시 정한다.
- 예상 비용: 측정할 때만 생성(Q-03). 대상 t3.small(unlimited 초과 크레딧 요금 포함)과 c7i.large를 합쳐 시간당 수백 원 수준. 실제 사용 시간·비용을 결과에 기록한다.
- 운영 backend-cd가 2026-09-27 SSM 단계에서 `InvalidInstanceId`로 실패했다. 이 작업 범위 밖이며 별도로 알린다.
